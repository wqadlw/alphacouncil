## 二、为什么发生 / 为什么这样设计

### 2.1 `outcome` 是**分类**而不是数字 —— 所以红线 10 由**数据模型**保证

红线 10 要求"坏决策+好结果时**不显示盈利数字**"。如果表里存收益率，
"不显示"就只是一条**渲染时的隐藏规则** —— 而**已经存在的数字会泄漏**：
日志里、导出里、将来任何一个新增的 API 字段里。

所以 `outcome` 是枚举 `good` / `bad` / `failed`。**"不显示"不是靠界面自律，是没有数字可显示。**

`failed` 是一等值，它存在的意义是**禁止"失败但…"这类措辞**（ADR-0014 第 3 条）。

### 2.2 「结果分到期前必须留空」**下沉到数据库**

`项目总纲` 的硬门禁本来只能靠领域层自觉。但 ISO-8601 时间戳**可字典序比较**，
所以把到期时刻复制进 review 行（`due_at_snapshot`），就能让绕过领域层的裸 SQL 也被挡：

```sql
CHECK (outcome IS NULL OR reviewed_at >= due_at_snapshot)
```

**这是"能移就必须移"（宪法 0.2）最干净的一个实例**：一条本来靠自觉的纪律，
现在是一行 `CHECK`，而**没有一个测试需要信任任何人的自觉**。
测试 `TestTheGateSurvivesBypassingTheDomain` 走裸 SQL 证明第二次拦截真的生效。

### 2.3 两个"看起来矛盾、其实不是"的结论

| A | B |
|---|---|
| 「是否已复盘」**绝不**从 `reviews` 推断（ADR-0014 硬规则） | `review_count` **可以**从 `reviews` 数出来 |
| 从**可变**存储推断状态 → 不可靠 | 从 **append-only** 存储数行数 → 可靠 |

两条都写进了注释和迁移文件头，因为**下一个人会以为其中一条是笔误，然后"顺手统一"掉其中一条**。

### 2.4 一个 CHECK 报错，暴露的是**语义没定义清**

状态表的 `reviewed_at >= due_at` CHECK 挡住了"只写过程分、不写结果分"。

我原本以为「写了过程分就算复盘过」，**schema 说不。schema 是对的** ——
「是否已复盘」问的是**复盘完成了没有**，而半份复盘不是复盘。
于是把 `reviewed_at` 改成**只在写入结果分时盖章**，含义是"已完成"。

> **约束报错时先怀疑概念，再怀疑约束。**

## 三、这道防线教会了什么

### 3.1 ⭐ 今天**第三次**因为控制台乱码差点做错东西

第一次读 ADR-0014 时，乱码把

> `reviews.outcome` **允许** `failed` 为一等值

压成了"**不把** `failed` 作为一个值"。**差一个「许」字，方向完全相反** ——
枚举会设计反，变异 M2 测的就是这一条。回原文核对才发现。

三次的共同点都是**乱码**（fsrs 三态 / ADR-0027 的 LangGraph 状态 / 这次的 `failed`）。
已写进 `.ai/agent-guide.md` §3.1。**读中文文件内容必须用 read 工具，不能凭乱码 grep 下判断。**

### 3.2 ⭐ 变异 harness 自己坏了两处，**而且第一处是"全部报 0 个测试"**

第一轮跑出来六条全是 `HARNESS ERROR · 目标没收集到任何测试`。
但摘要行写的是 `1 failed, 6 passed` —— **六个变异其实全部被抓住了**。

坏在解析器：`"1 failed, 6 passed"` 按空格切开后 `parts[1]` 是 `"failed,"`（**带逗号**），
不等于 `"failed"`，于是收集数算成 0。

> 这正是 README 规则 8 的**上一层版本**：一个坏掉的仪器报告"没有信号"，
> 而不是"我把这个信号丢了"。如果当时照着 `0/6` 往下走，
> 就会把一个**全部通过**的变异轮记成全部失败；反过来如果只看"没报失败"，
> 就会把一个真的全坏的 harness 记成全过。**两种读法都会撒谎。**

第二处：M6 的锚点指错了文件（`record()` 的盖章逻辑在仓储层，不在领域层）。

**harness 收集到 0 个测试必须判为 harness 错误** —— 这条从 0002 就该有，今天又验证了一次。

### 3.3 ⭐ `S-05` 的前缀表**第一次运行就抓到漏登记**

`CODE_PATTERN` 是硬编码的前缀表，**没有 `REVIEW`**。四个码在枚举里、在文档里，
却全都"未登记"。

> 漏一个前缀的后果是**安静的**：文档行还在，只是永远匹配不上。
> 是 `S-05` 把它变成了一声响。**这正是它存在的理由。**

### 3.4 顺带发现的两处**账本漂移**（都不致命，但都不该存在）

| 漂移 | 发现方式 |
|---|---|
| `.ai/error-codes.md` 有**两个 §2.6** | 插入新章节时撞见 |
| **`S-13` 在代码里有、在这张表里没有** | 同上。**而 `S-12` 看不到它** —— S-12 查的是 `README.md`，S-05 查的是 `ErrorCode` 枚举，`CHECK_*` 这批码**两个都不在** |
| 红线评测基线的 `partial/none` 是 `2/8`，实测 `4/6` | 读数字时。**钉住它的测试只比 `pass` 和 `total`** |

后两条都补上了，并**把测试的断言补全到四个数** —— 一个没人检查的数就是一个会漂的数。
基线里记下了我自己**算错两次**的账（`partial 2/8` 那次，以及本次漏把红线 10 的
`none → partial` 这步没算进去）。

### 3.5 ⭐ 一个新先例，写了理由

`domain/review.py` 是 **`src/` 里第一个带中文字面量的文件** —— 一直以来界面文案都在 `frontend/`。

四象限的警示文案放在领域层而不放 `ReviewPage.tsx`，理由是：
**那句话是产品政策，不是呈现。** 红线 10 禁止在这里美化，
而 UI 自己写那句警告，离"congratulations, good call!"只差一次马虎的 PR。
放在规则旁边，措辞和规则在**同一个 diff 里**被评审，而且
`test_every_quadrant_has_a_line_and_none_mentions_a_number` 才有东西可守。

`pyproject.toml` 的豁免**只给这一个文件**（不是 `src/**`），`RUF001` 在别处照常生效。

## 五、附记：GitHub 推送（同一日，接 spec 020 之后）

上一轮记为**阻塞**的推送已解决。过程本身有两条值得留下来的教训。

### 5.1 悬空 ref 的真正原因，和当时猜的不一样

当时记的是「`refs/remotes/origin/main` 指向 `fe9750b9`，而这个对象在本仓库里不存在」。
**这个诊断是错的。** 一次 `git fetch` 之后，git 直接把它快进到了真实的 `74e497f`
—— 说明 `fe9750b` **一直是个有效祖先**，只是 `origin/main` 这个 ref 停在了
上一位 agent 手工 `update-ref` 写进去的地方，从没被 fetch 校正过。

> **"对象不存在"和"ref 没更新"在症状上很像**（`git status` 都报
> `does not point to a valid object!`），但修法完全不同：
> 前者要恢复对象，后者只要 fetch。当时正因为**不敢猜 SHA** 才没动手 ——
> 那个谨慎是对的，但**理由记错了**，会让下一个人去干"恢复对象"这种无用功。

### 5.2 ⭐ 远端是**同一批工作的重复记录**，这解释了历史里那次 force-push

fetch 之后发现本地与远端**分叉**（本地 9 个 / 远端 3 个），普通 push 会被拒。

| | 远端 | 本地 | 内容 |
|---|---|---|---|
| K1 | `fe9750b` | `2a783b1` | 消息相同、日期相同 |
| K2 | `f44c50f` → `74e497f` | `08d6a3c` | **树逐字节一致** |

**远端那一对同消息的 K2 提交，正是"amend 后 force-push"留下的痕迹。**

而真正决定能不能安全 force 的，不是"看起来像重复"，而是这一个检查：

```
git diff --name-status origin/main main | ^D
```

输出只有一行：`docs/adr/0001-agent-orchestration-langgraph.md` ——
**唯一"远端有、本地没有"的文件，是 spec 016 里刻意 `git rm` 的重复 ADR**。
也就是说 **`main` 是 `origin/main` 的内容超集**，force 不会丢任何东西。

于是用 `--force-with-lease=main:74e497f`（**远端一动就中止**，不是裸 `--force`），
并先把 `74e497f` 存进 `refs/backup/origin-main-2026-09-28` 让被丢弃的提交仍可达。

**没有选择 merge**：那会在历史里留下"同一件事做了两遍"，
而两遍的内容是一样的 —— 对读历史的人是误导，不是保全。

> **教训**：把 `origin/main` 手工 `update-ref` 到一个"以为对"的 SHA，
> 代价是远端和本地长出两条平行历史，而**只有真的 fetch 一次才能发现**。
> 宁可 `--force-with-lease`，不要裸 `--force`；宁可先做一次"会不会丢东西"的
> 机械检查，也不要凭"看起来像重复"下结论。

### 5.3 代理

`clash-verge` 在跑，mixed 端口 **`127.0.0.1:7897`**。已写进**本仓库**的
`.git/config`（`http.proxy`），没动用户全局 —— 以后 `git push` / `fetch` /
`ls-remote` **不需要任何额外参数**。直连 `github.com:443` 仍被墙，所以这个代理不是可选项。

**`gh` 是否可用：未验证**（不再需要它）。
