# 2026-09-29 · S-14：让「每个源文件都被 git 跟踪」成为门禁，而不是一次手写检查（spec 032）

> 起因：**主人说「你决定」**，我决定先做两件「把已经存在的能力变成不可绕过的护栏」的事。
> 上一件是 npm 许可扫描（spec 031），这是第二件。
> 执行：OpenCode（Codex）· 模型：Space Bunny Free

---

## 一、手写检查和门禁的差别，是它会不会被跳过

`.ai/status.md` 记着 **S-14**。spec 027 那轮我手写过一次等价检查，跑完发现「198 个文件全被跟踪」，
记成完成。

⭐ **但那是一次执行，不是一条规则。** 它没有 `CHECK_*` 代码、没有优先级、没有「META 与实现
必须一致」的测试、没有豁免机制、也没有在文档清单里占一行。下一次谁都能不跑它 ——
而**没人会注意到没人跑它**，因为没跑和跑了的输出一样干净。

这和 spec 031 是同一句话的第二个应用：**门禁的价值在于不能被跳过，
而不能被跳过不是靠自觉，是靠它在清单上占一行、缺了就红。**

## 二、⭐ 真正要防的缺陷有两个，不是一个

第一个显而易见：**新写的文件没 `git add`**，本地一切正常，克隆出来就没了。

第二个危险得多，而且 **`git status` 看不见**：

> 一条写得太宽的 `.gitignore` 规则，会把源文件**藏起来**。

spec 025 §7.1 已经记录过：`.gitignore` 里 `data/` **没有前导斜杠**，所以它不只匹配根目录，
也匹配任何层级 —— 包括 `backend/src/alphacouncil/**/data/`。那种情况下文件是
「未跟踪**且**被忽略」，而 `git status` 默认不显示被忽略的文件。

⭐ **只查「未跟踪」是不够的：那恰恰是最需要被看见的那一种。** 所以三个信号：

| 信号 | 命令 | 判定 |
|---|---|---|
| 已跟踪 | `git ls-files` | 静默 |
| 未跟踪且**未**被忽略 | `git ls-files --others --exclude-standard` | ⭐ **error** |
| 未跟踪但**被**忽略 | `git ls-files --others --ignored --exclude-standard` | ⭐ **warning** |

被忽略的源文件是 warning 而不是 error，因为 `.venv`、`node_modules`、`__pycache__`、`dist`
都被忽略且都是对的 —— ⭐ 一个会误报的护栏会被关掉（和 spec 031 §2.2 同一个理由）。

## 三、不是 git 仓库时要说「跳过」，不能报通过

`CheckResult.skipped` 的文档写着：*a check with nothing to scan must say so rather than
report a clean bill of health*。tarball 里没有 `.git`、CI 上还没 checkout 完 ——
此时报「0 个问题」就是撒谎。

⭐ 而这一条不是假设：变异检查发现，**第二个 skip 分支（仓库内 git 失败）本来一个测试都没有**。
补上之后才明白它有多重要：git 失败时如果往下走，三个列表都是空的，于是**每一个源文件都被
报成未跟踪** —— 干净检出和坏掉的 git 变成同一份 200 条错误。

## 四、⭐ 我在 spec 里写错了一句，而它是假的

spec 032 §2 我写过：

> 规则只走 `backend/`（跳过 `_SKIP_DIRS`）与 `frontend/src` / `frontend/e2e`，
> **所以一条 warn 出现在这里，只可能意味着某条 ignore 规则盖住了源码。**

规则第一次跑真实仓库就给了它一个反例：

```
warning CHECK_IGNORED_SOURCE  backend/.pytest_cache/README.md
```

⭐ **工具缓存就住在被扫的树里面**，而且好几个都带一个 `README.md`。

**教训不是「warn 该改成 error」，而是：「圈定了范围，所以只可能」这种推理，
必须由范围本身兑现，而范围里住着什么不由我说了算。**

修在根上：`_SKIP_DIRS` 加缓存目录（并**提升为公开 `SKIP_DIRS`**，因为两个模块要用它 ——
⭐ 复制一份就会漂移，而漂移之后 warn 会为一种没人写下来的理由响起）。

那句话留在 spec 里并划掉，**不删** —— 删掉一条错的断言，下一个读者要重新发现它，
而重来的成本里恰好丢掉了最便宜的部分：它是错的、上线几分钟就被发现、修法属于范围而不属于严重度。

## 五、⭐ 变异检查第一轮 3/6，而两个存活暴露的是**我的 fixture**

| # | 变异 | 结果 |
|---|---|---|
| 1 | 不再报未跟踪 | killed |
| 2 | 不再报被忽略（`git status` 看不见的那类） | killed |
| 3 | 工具缓存目录回到源文件范围 | **SURVIVED** |
| 4 | skip 分支不说原因 | killed |
| 5 | 把所有文件当成已跟踪 | killed |
| 6 | 把扫描范围收窄到已发布包 | **SURVIVED** |

* ⭐ **变异 3 存活是因为 fixture 调了 `git add -A`** —— 那些文件是**已跟踪**而不是被忽略，
  所以跳过列表**根本没被问到**。测试断言了一件真话，但说的是另一件事。
* ⭐ **变异 6 存活是因为每个 fixture 都在 `backend/src/alphacouncil/` 下** ——
  那**就是** `ctx.product`。一条完全不看 `checks/` 和 `frontend/e2e/` 的规则能全过。

**第二轮 6/7，而那一个存活是弱杀**：变异后的文件根本不能解析，pytest 报 **error**，
而我的脚本把它算成了 killed。⭐ **文件解析不了，就证明不了任何测试察觉了行为变化，
只证明了我打不出正确的变异。** 脚本现在**先编译每个变异**，编译不过的一律记为「未测」。

**最终 7/7**，且补的那条测试就是第三节点名的那条「仓库内 git 失败」。

* 真实仓库：201 个源文件，唯一一条 error 就是**本轮新写的规则文件本身还没 add** —— ⭐ 它报的第一件事是自己
* S-05 / S-12 双向校验通过（两个新 `CHECK_*` 已登记 · README §3 已加 S-14 行，计数从 12 改成 14）

## 七、明确不做

* **不做**检查文件内容有没有进过 git 历史（慢，且与本规则无关）
* **不做**把「被忽略的源文件」升成 error —— 有合法例外，而会误报的护栏会被关掉
* **不做**扫 `.ai/**`
* **不做**把 registry 测试里的规则数量改成常量 —— ⭐ 改成从 `RULES` 派生，
  那样加一条规则不必记得回来改这个数字，而更重要的是**这个数字不会再和 runner 报的那个悄悄不一致**
