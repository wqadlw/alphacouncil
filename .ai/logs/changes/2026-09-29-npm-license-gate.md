## 一、⭐ 门禁已经在承诺一件它没有做的事

`constitution.md` 的 L-06 与 ADR-0024 都写着「依赖许可扫描」，门禁第 6 步也确实在跑
`scripts/check_licenses.py`，退出码也确实拦得住东西。

但那个脚本第 115 行是 `for dist in distributions()` —— `importlib.metadata.distributions()`
**只枚举 Python 包**。前端有 **209 个 npm 包**（真实数字见第二节），**从来没有被门禁看过一眼**。

我手扫过一次，结论是「314 宽松 / 24 MPL-2.0 / 0 传染性」。
⭐ **手扫不构成护栏**：结论会过期，而过期的护栏比没有更坏，因为它让人以为有人在看。

这和 `regressions/0005` 是同一类 —— 规范承诺过、门禁没兑现，中间靠一个人的记性。

## 二、调研，以及它改掉的设计

三条结论，其中两条直接推翻了我原本的写法。

**1. `license-checker` 是事实标准，但本篇不用它。**
它的 `--production` 语义提醒了一件更重要的事：**devDependencies 里的 AGPL 不产生义务**，
因为构建工具、测试运行器、linter **不会随产品发布**。我们这个项目是 Vite 打包的桌面应用，
`dependencies` 会进产物，`devDependencies` 不会 —— 「随产品发布」的边界是真实存在的。

不用它的三条理由：

1. ⭐ **词汇表只能有一个。** 项目已经手写了 Python 侧（`PERMISSIVE` / `WEAK_COPYLEFT` /
   `Verdict`）。再引入一个自带判断逻辑的扫描器，就有了**两个**「这算不算可以」的答案。
   与其绕路，不如让 `classify()` 变对，然后两边共用它。
2. 依赖纪律要求新增依赖有理由，而**一个许可扫描器本身也是依赖** —— 它的价值恰恰在于
   「依赖清单是可信的」。
3. 离线确定性。门禁不该依赖一次网络解析。

**2. ⭐ 真实的坑：`OR` 表达式。** 调研里有一个具体案例 —— `jszip` 的许可证字段是
`(MIT OR GPL-3.0-or-later)`，而一个朴素检测器判错了（ProGet 就把它标成 MIT 不合规）。

**`OR` 意味着你可以选一个**，选 MIT 义务就全部结清。一个只判断「字符串里有没有 GPL」
的扫描器，会把一个你完全可以用的包判成传染性。

⭐ **这比漏报严重得多。** 一个误报的护栏会怎样？**第一次被误报的人会把它关掉。**
护栏的价值不在于它从不误报，而在于它一直还在跑。

本项目的第一个真实表达式就是 `dompurify -> (MPL-2.0 OR Apache-2.0)`，而**旧规则判 `warn`、
新规则判 `ok`**。

**3. SPDX 是规范词汇表，但不是每个字段都符合它** —— `SEE LICENSE IN …`、
`{"type": …, "url": …}`、`Apache-2.0 WITH LLVM-exception` 都是现实里出现的写法。
解析必须承认「看不懂」，而不是猜。

## 三、⭐ `classify()` 从子串匹配变成表达式解析

| 表达式 | 语义 | 判定 |
|---|---|---|
| `MIT` | 单选 | `ok` |
| `MIT OR GPL-3.0-or-later` | **你可以选一个** | ⭐ `ok`（选 MIT） |
| `MIT AND GPL-3.0-only` | **两个义务同时成立** | ⭐ `fail` |
| `Apache-2.0 WITH LLVM-exception` | 例外**放宽**条款 | 按基础许可 → `ok` |
| `UNLICENSED` / 空 / `SEE LICENSE IN …` | 看不懂 | `warn`（**不是 `ok`**） |

**为什么 `AND` 取最严格而 `OR` 取最宽松**：`OR` 是**授权人的选择权**，选宽松的那个，
所有义务一次性结清；`AND` 是**叠加**，选宽松的那个**不能取消**另一个，宽松分支在 `AND` 里
不构成豁免。

⚠️ **`WITH` 按基础许可判定是刻意的简化**，理由写在代码注释里：例外的作用是**放宽**，
把例外当成加重条件会让 `Apache-2.0 WITH LLVM-exception`（一个非常宽松的组合）变成误报，
而**误报是这个门禁最不能犯的错**。例外原文完整保留在报告里。

另有一处顺序规则写进了注释：**字段分隔符 `|` 优先于 `OR` / `AND`**。`_licence_text()`
把 `License`、`License-Expression`、分类器用 ` | ` 拼起来，那**不是**一个表达式，
而是**几个候选**；多个候选时**取最严格**，因为每个声明许可证的字段都是一次声明，
其中一次传染性声明是需要回应的声明。

## 四、「随产品发布」的边界：production 闭包

按调研的结论，`devDependencies` 不发布。但**传递依赖**会让人搞错边界：一个只在
`devDependencies` 里的包，它的传递依赖也不发布。所以要算**闭包**而不是数顶层依赖。

⭐ 而且闭包用**两个信号**，因为各有一半看不见：

1. **声明** —— 顺着 `dependencies` 走，这能找到**被提升到顶层**的传递依赖
   （它们在顶层，没有嵌套可观察）
2. **物理嵌套** —— 位于已发布包目录**之内**，这不需要任何声明。npm 嵌套一个包的原因
   正是它的父包需要它，⭐ **所以目录是证据，而 `dependencies` 字段只是一份声称**
   （spec 031 §8：门禁扫的是磁盘上真实装的东西）。失败的 `npm ci` 或手改过的 lockfile
   会让声称与树不一致

解析不到的依赖名**显式报成 `warn`**，绝不静默丢弃：⭐ **一个失败方式和成功无法区分的扫描器
不是扫描器**，而丢弃恰好会让数字好看、缺口无人察觉。

**只有随产品发布的 `FAIL` 才让门禁返回 1。** dev 里的 GPL 会照常打印出来 ——
「不发布」是会过期的事实，把一个依赖挪进 `dependencies` 就过期了，而这行就是发现它的东西。

## 五、⭐ 我在这篇里犯的错

**1. `StrEnum` 让 `min`/`max` 按字符串排序。** 我建了严重度排名表**却没把它作为 `key` 传**，
于是 `"fail" < "ok" < "warn"`：`OR` 取最严、`AND` 取最松，两个运算符**同时颠倒**。
⭐ 合法、类型正确、完全反了。

**2. 排名表方向反了。** 修好第 1 个之后，**七个失配**同时存在 —— ⭐ 一个原因、七个症状，
这正是诊断正确的证据（七个看起来独立的失败不可能有七个原因）。循环里 `OR→min` 是为
**严格度**刻度写的，而我按**宽松度**编了号。

**3. 我的测试脚手架把期望写成 `'OK'` 而枚举值是 `'ok'`**，八个用例全部报 BAD。
⭐ **一个把所有东西都报成失败的脚手架，计数仍然是对的** —— 只看计数会读成「用例坏了」
而不是「期望值写错」。⭐ **永远读行，不要读计数。**

**4. 我把自己刚写错过一次的中文串又抄了一遍**当 `oldString`，匹配不上。后来全部改成按行定位。

**5. ⭐ 护栏在写盘前 `return`，文件一个字没变，而我下一步以为它已经写了** ——
于是下一步替换了一个还不包含 npm 助手的文件，引用了不存在的符号。
⭐ **护栏拦住的是那一次写盘，别的什么都不拦**。

**6. ⭐ 一个检查排在它所检查的替换之后。** 我在切片替换之后再去找一段注释，而切片**已经**
把它删了 —— 这个断言永远不可能通过。顺序错了的断言教人忽略断言。

**7. ⭐ 我把 `✗` 换成了 ASCII 的 `x`，"修好"了编码问题。** 而
`test_console_encoding.py::TestTheLicenceGate` 存在的全部理由就是 `✗`
（regression 0004：cp936 控制台上崩溃）。⭐ **删掉出问题的字符等于把问题藏起来**；
该改的是让终端能显示它，而 `use_utf8()` 早就做了这件事。

**8. `main()` 绕过 `scan()` 直接读子系统**，把既有测试依赖的替换点弄没了 ——
两个既有测试开始断言真实安装的东西。⭐ **失败的是测试，错的却是我的重构**：
那个替换点不是偶然，它是那两个测试不用装一个传染性包就能运行的原因。

**9. `is_relative_to` 按路径分量比较，我拿两个文件路径比**，所以永远是 False ——
而我 debug 脚本里写了 `.parent`，所以打印出 True。⭐ **诊断信息比代码更对。**

**10. 同一个错误有两个调用点，我只改了一个**，另一半继续静默出错。
⭐ **修复后 grep 模式，不是 grep 那一行。**

**11. 我用 shell 拼含转义的 Python 脚本，被转义规则绊倒两次** —— 违反了自己定的规矩
（「含 `\n`/引号的 Python 一律用 `write` 成文件」），第三次改成 `write`。
