# 2026-09-28 · J5 教训转卡：让「每条教训生成一条调度项」成为结构（spec 030）

> 起因：你最初说的是「要可以记录任何和金融股市相关的**知识和经验**」。
> spec 026-028 补上了**知识**（记下来 → 找得到 → 会自己回来找你），
> **经验**这一半一直没有入口 —— 而 `constitution.md` 第 7 条早就把要求写死了。
> 执行：OpenCode（Codex）· 模型：Space Bunny Free

## 一、⭐ 兑现点：红线 7 从 `partial` 升到 `full`

它自己记着的缺口：

> **机制有了，「每条教训自动生成」还没有。** 本项目**没有「教训」这个类型**，
> J5「教训转卡」未开工，所以**没有任何东西保证一条教训会走进队列** ——
> 全是用户手动排程的。

三个字现在都是假的，而第三个是红线本身：

| | 之前 | 现在 |
|---|---|---|
| 有「教训」这个类型吗 | 没有 | `lessons` 表，**而且不可变**（有触发器） |
| 入队是自动的吗 | 全是手动 | `record_lesson()` 里**无条件、紧挨着** |
| 有东西保证它吗 | 没有 | 一条**会失效就报错**的测试 |

**门禁数字**：`guarded 6 → 7` · `pass_rate 0.400 → 0.467` · `full 6 → 7` ·
`partial 5 → 4` · `eval.py` **仍退出 1**（`threshold` 是 1.0，八条还没强制）。

⭐ **基线是「刻意」更新的，不是重算的。** 钉基线的测试原话：

> guarded count is 7, baseline says 6 (2026-09-28).
> **If that is progress, update the baseline deliberately; if it is a break, fix the verifier.**

之所以能断定是「进展」而不是「漂移」：**`pass` 是真正被强制的数字，`full` 只是声称。**
如果我只把 `coverage` 改成 `full` 而 `pass` 没动，那才是一条标着「已强制」而实际没被
强制的红线，**文档在自相矛盾**。而这次 `pass` 动了 —— **数字没动就证明该动的东西没动。**

## 二、⭐⭐ 本 spec 自己被纠正过一次

第一稿把教训放进 `cards`：放松 `source_url` / `source_title` 为可空、加一个
`review_id`，让出处变成「URL **或** 复盘」。听起来很有道理 —— provenance rule 不但
没松，还更强了，因为一次复盘比一个链接更说明你当时怎么想的。

然后我去读 `0003_knowledge_cards.up.sql`，发现两个 `NOT NULL` **在 SQLite 里改不掉**
（要重建整张表，而它被三张表外键引用）。

**但重建不是重点，重点在我自己写过的话里。** `status.md` · spec 026 那行的诊断：

```
`cards` 表被 `source_url` 必填 + `source_title` 必填 + 前端硬编码单只 6 位代码
三条锁死 → 宏观判断、方法论、教训、读书笔记全都记不下
```

⭐ **教训就是当初建笔记的原因之一。** 为了让它回去而放松 `cards` 的出处规则，
是把 spec 026 整个反过来，然后还要为这份特权付一次表重建。

**教训没有 URL 可给。这不是缺陷，这是它的定义** —— 它的出处是一次真实发生过的、
你自己的判断失误。所以它有自己的表，而 `cards` 的两条 CHECK **一个字未动**，
并且有测试把这件事变成可执行的（`test_cards_carry_no_review_id` 断言那一列**不存在**）。

## 三、⭐ 四张表，以及一个可推导的「缺席」

| 表 | 是什么 |
|---|---|
| `lessons` | 教训本身。**不可变** |
| `lesson_schedule` | 「现在怎么样」的真源 |
| `lesson_reviews` | append-only 流水 |
| `lesson_promotions` | append-only，转卡的记录 |

⭐ **`lesson_reviews` 没有 `reset` —— 而这不是抄漏了，是推导出来的。**

spec 028 发现：**笔记可变**，所以队列里的笔记被改写后，FSRS 的记忆强度还挂在
**已经不存在的文本**上 —— 那是排程器在说谎。于是 `note_reviews` 多了一个第三态。

**卡片不可变，所以它永远不需要 `reset`。教训也是不可变的，所以它也不需要。**
现在三套流水：**两张不可变的两套没有 `reset`，一张可变的有。**
⭐ 这个不对称不是巧合，是「教训和卡片同一类」的直接证据。

⭐ **然后我发现这个推理的前提当时只是一个约定。** `lessons` 没有守卫触发器 ——
一个未来的 `update_lesson()` 会静默成功，把记忆强度留在不存在的文本上，
**正是 spec 028 为笔记修掉的那个失败**。推理是对的，前提没被钉住。
所以加了两个触发器，让不可变成为**结构性的**。

「缺席」本身要用测试钉住，而且钉两次：枚举里没有 `reset`（管这个词表），
**数据库的 `CHECK` 拒收 `'reset'` 字符串**（管真正让它不存在的那一层）。

## 四、⭐⭐ 「转」这个字就是全部：一次事务，而且**反向测**

`POST /reviews/{decision_id}/lesson` 在一个事务里写三行：教训、调度项、
以及 `outcome='enrolled'` 的流水行（**没有评分** —— 被强制入队的人还没回忆过任何东西，
替他记一个 `good` 等于把他没做的判断写成了他做过的）。

⭐ **API 里没有「入队」这个动词，而它的缺席就是保证。** 这个产品里每一个队列
都有显式入队接口，唯独这个没有 —— 因为对教训来说入队不是可选的，
暴露一个「只建教训不入队」的口子就是暴露一个破坏红线 7 的口子。

⭐ **测试是反的**：造一个 BEFORE INSERT 触发器**拒绝**写 `lesson_schedule`，
然后记一条教训，**必须失败，而且教训行也必须不存在**。

正向断言（「调度行在不在」）只描述了今天的形状 —— 它在「insert 被挪进另一个事务」
「insert 被包进某个分支」「insert 被 fixture 顶替」这三种情况下**都会继续通过**。
反向断言问的是红线那句话本身：**它有可能不在吗？** 不可能。

⚠️ 而 `pytest.raises` 必须是**外层**上下文管理器（regression 0006）：
反过来 pytest 会吞掉异常，事务看不到失败，于是**把半截写入提交** ——
测试会通过，而它断言的是反面。

## 五、⭐ 转卡要出处，而这个要求是**推导**出来的

一张卡片必须有 `source_url` + `source_title`（红线 4）。一条教训**两者都没有**。所以：

> **「我拿不出出处」= 这条已经是一条教训了，它还不是卡片。**

这不是新规则，是既有约束的推论。而它恰好是对的：**「转卡」是一个判断动作，
不是一次数据搬运。** 记下了但还不敢署名的想法由 spec 026 的笔记装着 ——
那是它本来就该去的地方。而**拒绝什么都不会丢**：教训已经记下、已经在队列上。

所以那个 400 的文案是产品，不是报错：

> 转成卡片要给出处：一个链接和它的标题。**拿不出出处就说明这条还只是一条教训 ——
> 它已经记下来了，不会丢。**

⭐ **转卡之后教训继续留在自己的队列上。** 红线 7 不能有「转了卡就不用再复习了」
这种分支 —— 那种条款会把保证变回建议，**而且它是隐形的**，因为队列看起来还是对的。
有测试钉住这一条。

## 六、⭐ 顺带修了一个已经失败过两次的规则

`check_error_codes.py` 自己的注释写着：

> ⚠️ **Adding a prefix here is a two-place edit**, and getting it wrong is quiet
> ⭐ It happened again on 2026-09-28 with `NOTE_*` (spec 026), and the comment above
> had already predicted it verbatim. **A rule that says "this is a two-place edit" and
> is still got wrong is a rule that wants to be a single-place edit**

⭐ **然后它发生了第三次**（`LESSON_*`）：我读了那条注释、加了文档表格、**跳过了那个 pattern**。
一条能预测自己错误、然后仍然被重复犯的注释不是建议，**是形状不对的证据**。

所以前缀清单现在**从文档自己的 §2 标题推导**，没有第二份要忘的东西。两个细节：

- **按长度降序**，让 `DATA_SOURCE` 排在 `DATA` 前面 —— 而这个例外现在是结构性的。
- **§2.8 一个标题里有两个前缀**（`MIGRATION_*` / `STORAGE_*`），所以推导取标题里
  **每一个** token。「取第一个」的读法会静默丢掉 `STORAGE`。

**没有回退**：找不到 §2 标题时模式匹配不到任何东西，于是每个码都被报出来 ——
**响亮地失败**。回退到旧的硬编码清单，正好会把这个改动要消除的静默行为恢复回来。

⭐ **然后我为这个修复写的测试，抓出了修复里的一个真 bug**：前缀的字符类
`[A-Z0-9]*` **匹配不到下划线**，所以 `` `DATA_SOURCE_*` `` 这个标题**产不出任何 token**。
它一直潜伏，是因为文档里同时有 `` `DATA_*` ``，于是每个 `DATA_SOURCE_*` 错误码
都被**偶然**识别成 `DATA` + `_SOURCE_...` —— 一个靠巧合得到的正确答案，
**正是能通过评审的那种形状**。

⭐ 我还改正了规则里一条**夸大自己机制**的注释：它说排序防止 `DATA` 匹配掉
`DATA_SOURCE_RATE_LIMITED` 的一部分。**它做不到** —— 后缀类是贪婪的，两种顺序都能全匹配。
**留一条夸大的理由在源码里比不留更糟**：下一个读者会以为顺序真的承重，
于是不会去找真正的原因。

## 十、界面：教训记在哪里，为什么那里

> ⚠️ 此节是后补的。写本上面的变更日志时界面还没有，而且我在
> 日志里写了「界面完全没有」—— **台账里说一件已经完成的事没做，比从未提过更坏**：
> 看的人会去又建一个。

**记在复盘页上，下面是那条复盘** —— 而不是单独一页。
教训是**u4ece一次复盘里揘导出来的**，而一个需要你去「找」的页面，
是大多数人不会去的页面。这与 spec 029 把「记一条」放在知识库页、
而不是藏进一个菜单里，是同一个理由。

表单在复盘**存在之后**才出现（`LESSON_REVIEW_MISSING` 是 409）——
教训是「这次复盘教出来的东西」，在复盘写之前它无所挂，
而挂到「还没到期的那一次」上会把它定日到一个还没发生的时刻。

**表单里有一句必须在的话**：「记下就入队 —— 这是红线 7 要求的，
所以**没有「入队」这个按钮可点**」。因为一个被告知「已经在队列上」
、却看不到任何队列控件的人，会合理地问一句。一行字去掉了这个屏幕唯一能提出的疑问。

## 十一、队列：一个「该复习」，不是两个

队列里现在有两种东西，选择是一个视图里都有，还是两个视图分开去。

⭐ **一个。** 两个队列要分开去看，这正是这个产品在别处都拒绝的碎化；
而读者体验上，一条笔记和一条教训不是两种**打断的方式** —— 两者都是
「你写过的东西回来了」。差别在**为什么回来**，而为什么属于行内一个小标签
（「从一次复盘来的」），而不是第二个要去的地方。

⭐ **那个标签不是装饰。** 笔记在这个队列里，是因为**你要求**被提醒；
教训在里面，是因为**红线 7 让入队变成了自动**。把它们渲染成一个无区别的列表，
会让一个**没有人要求的打断**看起来像一件**忘了的待办** —— 那就是「你欠 N 条」
的感觉，从另一条路达到的。

组内顺序：**笔记在前，教训在后**，各自保持自己的 `due_at` 排序。
合并成一个按日期排的列表，会声称两者可以互换—— 而行内那个标签说它们不可以。

行里没有的（每一条都有测试钉着）：**无计数** · **无标题**（行里展示教训本身那句话）·
**无优先级** · **无「入队」按钮**（它没有端点）。

## 十五、⭐⭐ 把项目拉起来看效果 —— 抓到一个测试套件抓不到的真 bug

主人说「把项目拉起来我看看效果」。**这一步抓到了前面所有测试都漏掉的东西。**

### 15.1 症状

```
GET /api/v1/decision-reviews/due   ->  []
```

写完复盘之后立刻变空。而复盘页**唯一**的列表端点就是「到期」这个。

### 15.2 ⭐ 所以 `f71fd3b` 里那个 composer，在真实应用里不可达

| 时刻 | 决策在哪 | 表单 |
|---|---|---|
| 写复盘**前** | 在到期队列里 | **不显示**（还没有复盘 —— 这部分是对的，而且服务端是 409） |
| 写复盘**后** | **离开**队列（`due_reviews` 按 `reviewed_at IS NULL` 过滤，regression 0007 的修复） | **永远不出现** |

**没有第二条路。** 而 E2E 全绿 —— 因为 fixture 把一条**已复盘**的决策放进了
**到期**队列，**那是服务端永远不可能返回的状态**。

⭐ **这比 F-47 更狠。** F-47 是一次全绿藏了一个未 mock 的请求；这一次是
**一次全绿藏了这个 spec 的主角**。fixture 和测试互相印证，而**两者都不和产品印证**。

⭐ 顺带一说：**这个洞不是我开的**。同一个缺口意味着**一条你已经复盘过的决策在复盘页上
是看不见的** —— 而 `项目总纲` §2.1 要的正是「反哺」：把学到的东西喂回下一次决策。
你无法回看一次已经写完的复盘。spec 030 是**走进去**，不是**开出来**。

### 15.3 修

1. **`GET /api/v1/decision-reviews/recent`** —— 已复盘的决策，最近的在前。**无计数、
   不按过程分或结果排序**（⭐ 按「你当时做得多差」给自己的复盘排序，是红线 11 在一个
   没人看着的地方）。
2. **`/recent` 的 `is_due` 永远是 `false`**。⭐ 我第一版沿用了到期端点的算法
   （`as_of >= due_at`），demo 里于是给一条**已经打过分**的决策摆出 1-5 分按钮 ——
   **这个字段不是装饰，它决定页面走哪个分支**。
3. **页面合并两个列表，到期的在前**，按 id 去重（一条决策可以既到期又已打分）。
4. ⭐ **第三个渲染分支，因为第二个分支的文案变成了假的。** 一条已复盘的决策落进
   「没到期，所以结果那一栏不存在」—— 对它而言那是**假的**。而我上一轮加的那句
   「你已经复盘过了」**让情况更糟而不是更好**：之前是一句错的说明，但没有按钮；
   加上一句真话之后，页面变成**自相矛盾**。
5. ⭐ **打分按钮改为按「是否已打分」而不是按 `is_due` 控制**，而且**显示**那个分数。
   浏览器显示的是**连续两行自相矛盾**：「都不会再变」正上方是五个能改它的按钮。
   显示分数是因为读者来这里是为了看自己当时的推理 —— **一个把自己要谈的数字藏起来的
   页面没有回答那个问题**。而且那是**他自己的**分，系统从不给人打分。

### 15.4 三个新错误，全是「凭印象写」

| 错误 | 真相 |
|---|---|
| `recent_reviews` 只 SELECT 两列 | `_row_to_state` 读五列 → `IndexError: No item with that key` |
| `Review.outcome` 传了字符串 | 要的是 `Outcome` 枚举 → `AttributeError: 'str' has no attribute 'value'` |
| `const graded` 放在 `previous` 之前 | `TS2448: used before declaration` |

⭐ **第二次那个尤其值得记：traceback 指向的是消费值的那个 helper，不是写错的那一行。**
一次报错指向栈底的 helper，通常是调用点的某个假设错了 —— **沿 traceback 往上找
比往下找更快**。而 `const graded` 那条，**一个 `any` 或一个 `!` 能同时消掉两个报错，
并把排序 bug 留在原地**。

### 15.5 fixture 也被修了，因为它在说谎

`/due` 现在返回**空**（这是真实情况），已复盘的那条搬到 `/recent`。
并加了两条测试：一条断言分数是**显示**而不是按钮，一条断言 composer
**只能通过已复盘这条路到达** —— 也就是坏掉的那条路。

⭐ 第二条的形状是关键：fixture 里 `/due` 故意是空的，所以如果 composer 将来又只能
靠一个服务端不可能返回的队列到达，这条测试会**红**，而不是让功能悄悄消失。
