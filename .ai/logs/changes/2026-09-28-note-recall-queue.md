# 2026-09-28 · 笔记的复习队列：可变的笔记如何挂在一个不可变的排程上（spec 028）

> 接 spec 026（记下来）与 spec 027（找得到）。第三环是**会自己回来找你** ——
> 规范 §A2 的原话：「收藏 500 篇文章不等于拥有知识。SRS 才是把信息转化为长期记忆的机制。」
> 执行：OpenCode（Codex）· 模型：Space Bunny Free

---

## 一、⭐⭐ 本轮真正的设计问题不是"抄一份 card_schedule"

`domain/scheduling.py` **已经是通用的**（`ScheduleState`/`ReviewRating`/`defer_due`/
`rating_to_fsrs` 都不含 card 类型），**domain 层零改动即可复用**。

要想清楚的是一句话：

> **卡片是不可变的，笔记是可变的。**

| | 卡片 | 笔记 |
|---|---|---|
| 正文能改吗 | **不能**（K1 刻意不给编辑动词） | **能**（spec 026 的 `PATCH`） |
| 「我当时复习的那条」 | 永远是同一条 | **可能已经不是了** |

⭐ **所以队列里的笔记被改写之后，FSRS 的记忆强度还挂在已经不存在的文本上。**
假设：9 月入队评了 3 次 `good`，10 月正文整段重写，11 月到期 resurfacing 时
用户被要求回忆**一段他从没复习过的文字**，而排程器以为他记得很牢。

⭐ **那是排程器在说谎。** 而本项目的立论是「你的记录是你唯一能信的东西」——
**一个会说谎的排程器比没有排程器更坏。**

→ **改写 = 重启排程**（`outcome = 'reset'`），**复习流水一行不删**。

### 1.1 重启必须留痕，所以 outcome 加第三态

因为「我复习过 5 次，为什么今天又回来了」**必须能回答**。
重启只改 `note_schedule` 而不写流水，那次重写就在历史里消失了 ——
而本产品的核心命题是「投资无法从经验中学习，因为没有记录」，
**学习的尝试史就是这个产品本身**。

```text
reviewed  我重读了，然后评分
deferred  还没想清楚（想法还没定），记忆强度一个字节都不动
reset     笔记被改写，排程重启；没有评分，也没有耗时
```

`reset` 与 `deferred` 的区别不是"程度"，是**方向**：deferred 往后推，reset 往回退。

### 1.2 ⭐ 而这反过来证明了分开建表是对的

`reset` 是**笔记独有的** —— 卡片不可变，所以它永远不需要。
**如果两者真的一样，`reset` 就该是两者的共同能力，而它不是。**
这条不对称是「不并进 `card_schedule`」最强的证据。

## 二、⭐ 三个决定，都写在代码注释里

### 2.1 入队**永远显式**

把「我写过的每条笔记」都塞进队列 = 一个**永远清不完的欠账**，
而「你欠 N 条」正是红线拒绝的那种感觉。

### 2.2 ⭐ 复习时**显示全文**，不藏标题考记忆

Anki 藏答案、只给提示词。对笔记**不适用**：
**笔记的标题不是一个好的提示词。**「关于流动性的一点想法」不告诉你该回忆什么，
只测你能不能从自己写的标题里猜出内容 —— **那测不出记忆，只测运气。**
而卡片的主张**本身就是**完整的提示词（一句话判断），所以卡片可以藏。

这个区别改变 `again` 的含义：

| | `again` 的含义 |
|---|---|
| 卡片 | 「我回忆不起来这条主张」 |
| 笔记 | 「**我的想法已经变了**」 |

⭐ 对笔记来说后者是**这个产品最想听到的信号**：一条笔记该被改写、标记、或收敛。
把两种含义混在一句 UI 文案里，等于**把最有价值的那次反馈说成了"你忘了"**。
E2E 对渲染出的按钮断言「忘 / 失败 / 重来 / 错误」四个词都不出现。

### 2.3 检索**只过滤不重排**（沿用 spec 027）· 队列**不含任何数字**

`/due` 返回**裸数组**，没有 `remaining` 字段 —— 而且 API 层有测试断言这一点，
因为「加个计数」是一行改动、什么都不会坏。

## 三、⭐⭐ 测试抓出的**六个真 bug**

每一个都是先写测试、测试红了才发现的（不是评审发现的）：

| # | bug | 怎么发现的 |
|---|---|---|
| 1 | `note_reviews.id` **同毫秒碰撞** → `UNIQUE constraint failed` | 测试跑得比一毫秒快 |
| 2 | ⭐ **`state_json` 被双重编码** —— `_fresh_fsrs_card` 已返回 JSON 字符串，再 `json.dumps` 一次，`json_type` 变成 `text` 而非 `object` | 四个改写测试全红 |
| 3 | ⭐ **`fsrs_card_id` 没有跟着重置** —— 列里是 1，payload 里是 2，**两者互相矛盾而 schema 允许** | 断言 payload 变了之后又断言 id 也变 |
| 4 | ⭐ **404 守卫是死代码** —— `get_by_id` 是**抛异常**而不是返回空行，所以 `if not ...` 永不执行 | 变异「改成 500」**测试照样全绿** |
| 5 | `GET /due` 被 `GET /{note_id}` 吞掉 → 「没有这条笔记：due」 | 路由顺序测试**第一次运行就红** |
| 6 | 错误类没在 `api/errors.py` 登记 → 所有失败都是**没有 code 的 400** | 客户端读 `["code"]` 抛 KeyError |

⭐ #3 值得单列：它**只有**一个测试能抓到 —— 断言 payload 与 id **两半都变了**。
只断言 payload 会漏，因为「换了张新卡」和「旧卡改了到期日」在 payload 层面都能通过。
而这是**从卡片仓储复制 SQL 造成的**：卡片的 review 复用同一个 FSRS 卡（id 不变），
所以那条 UPDATE 正确地不写 id；**只有 reset 才换卡**。

⭐ #4 是最值得记的一个：**一个能让变异持续通过的变异，比一个失败的测试信息量更大** ——
它说明那道守卫是装饰品。而它持续通过的原因是我把 `get_by_id` 当成"返回可能为空的读取"，
而它的文档字符串第一行就写着「One note, or refuse」。

## 四、⭐ 变异 15/15，抓出一个**不是变异的变异**（诚实记下）

15 条注入全部抓住。三条在第一轮漏了，其中一条值得单列：

⭐ **「把 404 改成 500」测试全绿 —— 而理由是那段代码根本不会执行**（见 §三 #4）。
补的测试直接绕过仓储往表里插坏行 / 直接断言行数存活，而不是靠"整套测试跑得快"。

⭐ **一个「不是变异」的变异**：第一次我把「同毫秒碰撞」写成"删掉防碰撞检查"，
测试**全绿**。查下来是：碰撞只在两次复习落在同一毫秒时才发作，**那是运气不是性质** ——
慢机器上不发作。补的测试改成"边生成边写入 200 次，然后数行数"，
断言的是**存活**而不是"唯一"（`_new_id` 只保证"不在表里"，不保证两次调用返回不同值，
因为它不记住自己返回过什么 —— 那是设计，不是 bug）。

| **404 用 `detail`、400 用带 code 的信封** | 继承的不对称，客户端要知道 `NOTE_*` 的 400 看 `code`、404 看 `detail` |
