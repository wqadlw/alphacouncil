## 一、⭐ 先说结论：这条差距不是「样式不够好看」，是**一条被违反 255 次的规则**

`FRONTEND_STYLE_GUIDE.md` §2.2 是一张**裁定过**的表（两份规范冲突时它说了算），
2026-09-28 就进了仓库。而实测：

| | 实测 |
|---|---|
| `text-[17px]` | **全项目 1 处** ⭐ 而且那一处是页面 `<h1>`，§2.2 规定 **22/30** |
| `text-[11px]` + `[12px]` + `[13px]` | **255 处** |
| `text-[9px]` | 1 处 —— ⭐ **低于表里每一个下限**，连 11px 徽章那行都不到 |

⭐ **规格自己的诊断就是这个。** §0 写着「字号分配没有规则，于是全用小字」，
而 §0 同时说那十二个组件「0 个」——**它在描述 2026-09-28 的仓库，而那句话在今天仍然成立。**

⚠️ 而且 106 个 `text-[12px]` 里 **53 个在 `<p>` 上**。§2.2 对「正文散文」那一行标的是
⛔ **不允许 11/12px**，判据一句话是「**要读成段落的字不得小于 13px；表格与标签可以小，
因为它们不是段落**」。⇒ **53 处正在违反规格自己的禁令**，不是「风格偏小」。

## 二、⭐ 为什么必须变成「一个家」，而不是继续手写

⭐ grep 判不了 `text-[11px]` —— **grep 不知道这段字是表头还是散文**。
而 §2.2 的判据恰恰是关于「这段字**是什么**」的。

⇒ 所以可机械化的那条规则是反过来的，而且更强：**组件里不写任何字号**。
七个（现在是八个）类住在 `globals.css` 里，判断从「每次调用点」移到「写这个类时，一次」。

⭐ **迁移脚本只做确定的那部分，规格外的 6 个尺寸一律不猜**：

```
11px → type-badge    13px → type-prose    12px → (<p> 上) prose / 否则 meta
DEFERRED to a human — §2.2 has no row for these: 16
```

⭐ **「15px 有 7 处，其中 4 处本来就带 `serif`」这件事本身是结论**：
主张那一行不是被忽略，是**一直被当成 15px 在凑**。迁移把它落到 17 / 20。

## 三、⭐ 迁移过程中被推翻的三个判断（都不是「优化」，是**规格说错了**）

| 我原来的写法 | 推翻它的 | 结果 |
|---|---|---|
| `InstrumentPage` 的**「我为什么关注它」**用 `serif text-[16px]`，注释写「一句引用，所以规则 1 成立」 | ⭐ §2.2 有「理由」这一行：**正文散文 13/20，sans**，⛔ 11/12px；§2.1 的衬线清单是「标题与主张」 | 改成 `.type-prose`，**并且把 `serif` 摘掉**而不是让它被覆盖 ⭐ 让 diff 说清发生了什么，而不是留一个不再起作用的类 |
| `RetrospectivePage` 的**理由**用 `serif text-[18px]`，比它上方的**判语**还大一档 | 同上：判语是 17–20 衬线，理由是 13/20 无衬线 | ⭐ **层级被反了**，改了之后判语 20px、理由 13px |
| `.type-claim*` 里带 `font-family: var(--font-serif)`（规格字面上是这么写的） | ⭐ **主张不总是文字**：`RetrospectivePage` 的评分、`StopLossPrompt` 的年数都带 `num`（mono，等宽数字） | 拆成「`.type-*` 只管大小，`.serif` 管人声」。⭐ 否则三个数字会被静默改成宋体，diff 里看不出来 |

## 九、⭐⭐ 本轮最贵的一个错误：**我把「函数零调用者」当成了「能力不存在」**

⭐ 阶段 C 的 spec 原本写着：「`cards_repo.list_events()` **已存在但零调用者**；`GET /cards/{id}/events`
**不存在**」⇒ **数据在库里、屏幕上没有**。

子 agent 逐行核实后发现**这个前提是错的**：

- `card_events` **早就在接口上了**，走的是私有的 `_load_events()` → `CardRow.events` →
  `CardRead.events`（`routes/cards.py:156-162` 的字段 + `:188-196` 的 mapper）
- ⭐ **而前端已经在渲染它**（`CardSection.tsx:379-393`）
- API 测试也钉死了这条路径（`test_cards_api.py:365`）
- `list_events()` 真的零调用者 —— ⭐ **但它是那条已通路径的私有镜像 `_load_events()` 的公开版本**

⇒ **「函数零调用者」与「这个能力不存在」是两回事。** 我用「有没有一个公开函数被调」
当判据，而正确判据是 **数据有没有出现在响应体与屏幕上**。

⭐ 这个错误的代价不只是 spec 写错：照它做会**新建一个重复端点**，而真正的缺口
（通用组件 + 其余六张 append-only 表的适配器）反而没人做。⇒ 阶段 C 的计划已改写（spec §五·C.2）。

⭐ 同一次核实还照出三条**会让我写错代码**的事实：

1. `backlinks_for` 返回 **`list[str]`（裸 note id）**，不是行对象 —— `test_notes.py:501`
   的注释记着上一版曾断言成写路径的形状 `[row.note.id …]`。
2. `ORDER BY from_note_id` 是**按 id 字符串**排序，id 形如 `note_<millis>` ⇒ 字典序≈时间序
   **仅在毫秒位数相同时成立** ⇒ 不要在文档里写「按时间排序」。
3. **`NOTE_NOT_FOUND` 不在 `errors.py` 的状态码表里** ⇒ 不显式 `try/except` 会返回 **400 而非 404**。
