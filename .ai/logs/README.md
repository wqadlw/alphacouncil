# 台账目录（Append-Only）

本目录存放**不可篡改的历史记录**。

## 纪律

1. **只追加，不修改，不删除。** 包括错别字也不改——历史就是历史。
2. 需要更正时，**追加一条更正记录**，说明「原记录 X 有误，实际为 Y，原因是 Z」。
3. 每条记录必须包含日期、范围、结论。

> 这条纪律来自真实教训：曾经出现过「文档声称已修复、实际未修复」的情况，导致后续排查建立在错误前提上。**台账的价值在于它不可被美化。**

## 子目录

### `review/` —— 审查与验证记录

| 文件命名 | 内容 |
|---|---|
| `YYYY-MM-DD-<范围>.md` | Reviewer 的审查记录（P0/P1/P2 问题清单） |
| `YYYY-MM-DD-<功能名>-verification.md` | Tester 的验收验证报告 |

### `changes/` —— 变更与审批记录

| 用途 | 说明 |
|---|---|
| 依赖新增审批 | 说明为什么现有依赖做不到、替代方案对比、维护活跃度证据 |
| 阻塞记录 | Developer 卡住时记录阻塞点，避免绕过问题 |
| 重大变更 | 影响既有架构的改动，需与 ADR 呼应 |
| ⭐ **治理文件修订** | **改 `.ai/constitution.md` / `.ai/README.md` 本身** —— 宪法附则要求"开一条记录 + 人工确认"。命名：`YYYY-MM-DD-constitution-v<N>.md` |

> **⚠️ 改宪法必须开记录，且记录里必须有一节「未做（不假装做过）」。** 例见 `2026-09-26-constitution-v3.md` §4。

## 模板

### 审查记录

```markdown
# 审查记录：<范围>

- 审查时间：YYYY-MM-DD
- 审查范围：<commit range 或文件列表>
- 审查结论：通过 / 有条件通过 / 不通过

## P0
（无）

## P1
### P1-1 · <问题简述>
- 位置：`path/to/file.py:88`
- 现象：...
- 影响：...
- 证据：<可复现的命令或测试>
- 建议：...

## P2
...

## 已确认无问题的项
- ...
```

### 依赖新增审批

```markdown
# 依赖审批：<包名> <版本>

- 申请日期：YYYY-MM-DD
- 申请角色：Developer

## 为什么现有依赖做不到
...

## 替代方案对比
| 方案 | 优点 | 缺点 |
|---|---|---|

## 维护活跃度证据
- Star：·
- 最近提交：·
- Issue 响应：·

## 引入成本
- 安装体积：·
- 传递依赖数：·

## 结论
待人工确认 / 已批准 / 已拒绝
```

### 变更记录（治理文件修订 / 重大变更）

```markdown
# 变更记录：<标题>

- 日期：YYYY-MM-DD
- 类型：治理文件修订（`docs`）/ 架构变更 / …
- 范围：<涉及文件清单>
- 依据：<宪法附则 / ADR 编号>

## 1. 为什么改
<触发原因；如果是修正既有设计，必须写明"原设计是什么、错在哪">

## 2. 改了什么
<逐条对照表；每条注明依据>

## 3. 未改的（有意保留）
<避免"重写"掩盖改动>

## 4. ⚠️ 未做（不假装做过）
<未完成项一律显式列出>

## 5. 下一步
```
