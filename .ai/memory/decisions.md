## ADR-0001 · Agent 编排选用 LangGraph

- **日期**：2026-09-25
- **状态**：✅ **已采纳**（理由已于 2026-09-26 修订）

> ⚠️ **理由修订**：原文写的是"投研流程需要条件分支 / 回路 / 人工中断"。
> **现行定位已变** —— agent 不再是"研究流程"，而是**只做抽取与核算的工人**（宪法第一条红线 15）。
> **选型结论不变**（仍用 LangGraph），但用途变为：**规格 → 实现 → 审查 → 验证 → 归档 的开发流水线**，以及**受限抽取流水线**。

**背景**
需要在多 Agent 框架中选型。候选：LangGraph（42257★）、AutoGen（61152★）、CrewAI（59006★）、Agno（42335★）、OpenAI Agents SDK（29693★）。

**决策**
选用 LangGraph 作为编排主干。

**理由**
1. 需要**条件分支**、**回路**（Critic 质疑后重做）、**人工中断点**——这三点是图模型的原生能力。
2. 状态显式声明（TypedDict），便于测试与调试。
3. **`checkpointer` 支持可中断可恢复** —— 对长流程是必需的。

**被否决的方案**
- **CrewAI**：抽象层高。**"角色自由聊"无法复现、无法评测** —— 我们要的是确定性阶段。
- **AutoGen**：对话式编排对「可控流程」支持较弱。

**影响**
- 需要显式设计 State 结构，前期成本略高。
- 换来的是流程可测试、可中断、可观测。

## ADR-0002 · 检索框架选用 LlamaIndex

- **日期**：2026-09-25
- **状态**：⛔ **已废弃**（2026-09-26，见 ADR-0006）

> # ⛔ 本决策已废弃，请勿据此实现
>
> **废弃理由**：这是 v1 方向性错误的一部分 —— 当时把"智能检索层"当成产品的技术卖点。
> **我们的产品是决策记录系统，不是检索框架。**
> 现行检索能力仅为**知识层的一个功能**（K4），规模是个人级（几千张卡片），
> **用 SQLite FTS5 + 向量扩展即可**，不需要独立检索框架。
> **LlamaIndex 已从宪法技术栈中移除**（宪法第三条 3.1）。

**背景**
候选：LlamaIndex（52313★）、Haystack（26596★）、自研检索管线。

**决策**
选用 LlamaIndex 作为检索框架底座。

**理由**
1. 检索侧组件最完整：索引、检索器、重排、评估（含 RAGAS 集成）齐全。
2. 组件可替换，便于按需接入 Qdrant / BM25 / 自定义重排。
3. 与 LangGraph 可组合（Agent 通过工具调用检索层，不耦合）。

**被否决的方案**
- **Haystack**：管线模型清晰，但生态与社区规模小于 LlamaIndex。
- **自研**：可控性最高，但重复造轮子，且不利于展示「基于成熟框架」这一要求。

**影响**
- 检索层对外暴露统一接口，内部实现可替换。

## ADR-0003 · 采用四路混合检索而非单路向量检索

- **日期**：2026-09-25
- **状态**：⛔ **已废弃**（2026-09-26，见 ADR-0006）

> # ⛔ 本决策已废弃，请勿据此实现
>
> **废弃理由**：四路召回（稠密 / 稀疏 / 图 / 结构化）+ RRF 融合是为"投研问答"设计的。
> **我们的产品不回答"这家公司怎么样"这类问题** —— 它记录"你当时怎么想的"。
> 个人级知识卡片（几千张）**不需要四路召回**。

**背景**
投研问题分为四类：语义型、精确型、关系型、聚合型。单路稠密向量检索在其中三类上表现不佳。

**决策**
实现四路召回（稠密向量 / 稀疏词法 / 图 / 结构化），以 RRF 融合后重排。

**理由**
1. 四类问题本质不同，不存在单一索引能同时最优。
2. RRF 无需调参，鲁棒性好于加权求和。
3. **这是本项目的技术差异化所在**——多数 RAG 项目止步于向量检索。

**被否决的方案**
- **单路向量 + 更好的 embedding**：换模型无法解决关系型与聚合型问题。
- **加权分数融合**：需要为每路调权重，泛化差。

**影响**
- 系统复杂度上升，需要统一的结果结构（含各路排名）。
- 必须配套评测集，否则无法证明改进（见 constitution 第四条）。

## ADR-0004 · 向量库选用 Qdrant

- **日期**：2026-09-25
- **状态**：⛔ **已废弃**（2026-09-26，见 ADR-0006）

> # ⛔ 本决策已废弃，请勿据此实现
>
> **废弃理由**：**我们是桌面程序，不是一个要运维的服务器。**
> 引入 Qdrant 意味着用户要跑 Docker —— 与"双击安装就能用"直接冲突（宪法第三条）。
> 个人级数据规模用 **SQLite + FTS5**（必要时加向量扩展）即可，**零额外进程**。

**背景**
候选：Qdrant（34809★）、Milvus（46253★）、Chroma（29371★）、pgvector（23156★）。

**决策**
选用 Qdrant。

**理由**
1. Rust 实现，单机性能好，Docker 一键起，部署成本低。
2. **原生支持稀疏向量**，可在同一系统内实现稠密 + 稀疏混合检索，避免引入两套存储。
3. payload 过滤能力强，适合「按公司代码 + 日期范围」预过滤。

**被否决的方案**
- **Milvus**：功能更强但部署重（依赖 etcd、MinIO），个人项目性价比低。
- **Chroma**：轻量但生产特性弱，不适合展示工程能力。
- **pgvector**：若已用 Postgres 则很划算，但稀疏检索支持弱于 Qdrant。

**影响**
- 需额外维护一个 Qdrant 服务（docker-compose 解决）。

## ADR-0005 · 采用规格驱动的多角色 Agent 开发流程

- **日期**：2026-09-25
- **状态**：✅ **已采纳**（2026-09-26 强化）

> ⚠️ **强化**：2026-09-26 把流程纪律**从"开发框架文档"提升为"项目宪法"**（宪法 v2.0 第二条、第九条），
> 并新增四条：**新增机制的门槛** · **单一命令入口** · **「完成」= `make check` 通过** · **不虚构**。
> 来源：`references/deep-dives/01-wealthfolio.md`（wealthfolio `AGENTS.md`）· `02-anki.md`（`CLAUDE.md`）。

**背景**
本项目由 AI Agent 主导开发。无约束的 Agent 生成会导致代码风格分裂、测试缺失、自我验证失效。

**决策**
采用三层开发框架：规格层（spec）+ 角色层（architect/developer/tester/reviewer）+ 质量层（pre-commit + CI + 台账）。

**理由**
1. 规格先行避免 Agent 自由发挥。
2. **实现与测试分离**，避免「自己验自己」。
3. **Reviewer 只读**，保持审查独立性。
4. 台账 Append-Only，保证可追溯。

**被否决的方案**
- **让 Agent 自由开发 + 事后审查**：返工成本高，且审查容易流于形式。

**影响**
- 前期流程成本上升。
- 换来的是可维护性与可审查性——这正是开源社区审查所要求的。

## ADR-0006 · 检索层方案整体作废（取代 ADR-0002 / 0003 / 0004）

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **取代**：ADR-0002 · ADR-0003 · ADR-0004

**背景**
v1 把"基于成熟框架构建的智能检索层"当作项目的技术差异化与面试重点。
2026-09-25 主人明确重申：**「记住我们是一个面向实战的股市知识管理系统」** —— 检索是手段，不是产品。

**决策**
1. **移除 LlamaIndex / Qdrant / LightRAG**，从宪法技术栈中删除。
2. **取消"检索层"作为独立阶段**（原 `specs/002` 已标废弃）。
3. 检索能力降级为**知识层的一个功能（K4）**：用 **SQLite FTS5**（+ 必要时的向量扩展）实现，**零额外进程**。

**理由**
1. **定位错误**：产品核心资产是**用户的认知与决策记录**，不是"系统的检索能力"。
2. **形态冲突**：我们是**桌面程序**，不能要求用户跑 Docker。
3. **规模不匹配**：个人级知识卡片（几千张）用不上四路召回 + RRF。

**被否决的方案**
- **保留检索层但降级**：会持续吸引注意力与工时，不如整体作废。

**影响**
- 删除三个 ADR，节省大量工时。
- **代价**：简历上少了一个"技术亮点" → 由 **agent 工程能力**（编排 / 可观测 / 评测 / 权限边界）替代，见 ADR-0009。

## ADR-0007 · 交付形态：Windows 桌面程序（pywebview）

- **日期**：2026-09-26
- **状态**：✅ 已采纳

**背景**
主人明确：**「我是准备做一个程序出来的，就是有 exe 安装包的那种」**。不是网页，不是服务器部署。

**决策**
`Python(FastAPI) + React(Vite) + pywebview(WebView2) + PyInstaller(--onedir) + Inno Setup` → `AlphaCouncil-Setup.exe`

**理由**
1. **本机已实测跑通**：最小程序打包后 **20MB**，冻结自检 `frozen=True` / `http=200` / `webview_backend=winforms+WebView2 OK`，窗口真实打开。
2. **pywebview 复用系统 WebView2**（本机已装 153.0.4234.48）→ 不用自带浏览器内核。

**被否决的方案**
- **Tauri**：本机 `rustc`/`cargo` **未安装**，需 MSVC 编译链（Rust ~1.5GB + VS Build Tools 3–6GB，需管理员）。**架构已把外壳做成可替换**，将来换 Tauri 只换外壳。
- **Electron**：自带 Chromium（+200MB 起），且仍需 Python sidecar，**3 层进程**。

**影响**
- 前端从 Next.js 改为 Vite + React（见 ADR-0008）。
- 数据库必须放 `%LOCALAPPDATA%`（Program Files 不可写）。
- 必须做**单实例锁**与**随机空闲端口**。

- **日期**：2026-09-26
- **状态**：✅ 已采纳

## ADR-0010 · Agent 权限边界：工具权限四档

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/01-wealthfolio.md` §6

**背景**
agent 会写进产品里。红线 1 是「不做预测增强」—— **这条红线必须延伸到 agent 身上**，否则 agent 会成为绕过红线的后门。

**决策**
工具分四档（**代码层面保证，不是提示词**）：

| 档 | 工具 | 权限 |
|---|---|---|
| ① 只读 | `get_price` · `get_financials` · `search_cards` · `get_decision` … | 无 |
| ② 抽取草稿 | `draft_facts_from_filing`（**强制带页码**）· `draft_claim_tags` … | **只返回草稿，绝不落库** |
| ③ 提交 | `commit_facts` · `commit_claim_tags` | 需写权限 + 用户确认 |
| ④ **永久不做** | **写入/修改决策记录 · 删除 · 改关注池理由 · 导出备份 · 改密钥** | ❌ 永不对 agent 开放 |

**理由**
1. **提示词可以被绕过，工具不存在不能。**
2. ⚠️ **第 ④ 档最关键的一条：决策记录必须由用户亲手写。**
   **如果 agent 能替用户写决策，整个产品就塌了**（用户不再需要面对自己）—— 红线 13「索取在先」。

**影响**
- 工具目录（`catalog`）需要两份：应用内助手（只读 + 草稿）vs 外部 MCP（全部，按 scope 过滤）。
- 审计日志必须脱敏：**记"做了什么"，不记"内容是什么"**。

## ADR-0011 · 决策日志主键 = 服务端生成的时间戳

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/02-anki.md`（anki `revlog`，`revlog/mod.rs:17-27`）

**背景**
红线 4 是「**结果之前记录**」。但如果客户端可以传 `id`，用户就能把一条决策写成"三个月前"。

**决策**
1. 决策日志主键 = **记录时刻的毫秒时间戳，由服务端生成**；**API schema 中不暴露该字段**。
2. 日志表**只追加，无 UPDATE / DELETE**；"改变想法" = 追加一条新记录。
3. 日志带**类型枚举**（对质回答 / 预览浏览 / 手动改期 / 改规则），并提供**"是否参与统计"的显式判定**。
4. **只有"对质回答"参与重复检测统计** —— 改期、预览、改规则都不算。

**理由**
1. **主键即时间戳 = 物理保证**：无法伪造"我在结果出来前就这么想了"（anki 同源设计）。
2. **不提供过滤判定，统计数字就会假** —— 例如"你这句'越跌越买'说过 3 次"可能把"你上周把问题推迟了两次"也算进去。
3. **改期（回避）本身必须是一条正式记录**（对应红线 5）。

**影响**
- 需要一个 `is_counted()` 类的判定函数，并有单元测试覆盖。
- 必填字段（理由 / 反面证据 / 失效条件）在**数据库层 `NOT NULL` + 非空校验**。

## ADR-0012 · 数据库迁移纪律

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/01-wealthfolio.md` §4（51 个迁移 + 21KB 验证报告）

**背景**
桌面程序要升级数据库。用户的数据**只有一份**，迁移失败 = 数据可能损坏。

**决策**
1. **已发布的迁移永不编辑**，只追加新迁移。
2. **每个迁移必须可回滚**（有 `downgrade`）；确实不可逆时必须显式声明。
3. **执行迁移前先做已验证快照**：`VACUUM INTO` → 记录 SHA-256 → 界面显示"升级前的备份"。
4. **迁移失败时**：保留快照路径 + 显示在错误详情 + 提供"重试"按钮。
5. ⚠️ **迁移连接必须用 `temp_store = FILE`**。
6. **迁移期间 `synchronous = FULL`**；**显示启动屏而非冻结窗口**；**功能门控直到就绪**。

**理由**
1. wealthfolio 实测：`temp_store = MEMORY` 下百万行 UPDATE 峰值分配 **2,046 MiB**，`FILE` 仅 **76 MiB**；`VACUUM` 峰值 **2,571 MiB**。
   ⚠️ **注意：`temp_store = DEFAULT` 在该构建下也等于内存** —— 光删掉显式 MEMORY 设置没用。
2. **每次重试生成新的唯一快照，已有快照字节级不变** → 可追溯。

**被否决的方案**
- **引入专门的备份库**：按宪法 §2.2（新增机制的门槛），SQLite 自带的 `VACUUM INTO` 已够用，**不新增机制**。

**影响**
- 需要 `make migrate` 相关目标与集成测试。
- 首次启动的"升级"路径必须有测试覆盖（不能只测全新安装）。

## ADR-0013 · `thesis.md` 是版本序列的渲染视图（不是原地重写的文件）

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/06-mem0.md` 决定（过渡必须被捕获）+ `04-langfuse.md`（SCD-2，`schema.prisma:658-685`）
- **修正**：改原设计（"`thesis.md` 是原地重写的文件，开头写 what changed 靠人肉纪律"）

**背景**
原设计把"活论点"实现成一个**被原地重写的 Markdown 文件**，"开头写 what changed"靠人肉纪律。
后果：**"这句话你说过 3 次"无法查询** —— 因为旧版本已被覆盖。而**这恰好是产品的核心亮点之一**（决策层的间隔重复）。

**决策**
1. **真源是 `thesis_versions` 表**（SCD-2 版本化）：

   | 列 | 说明 |
   |---|---|
   | `id` | 版本 id |
   | `thesis_id` | 归属的论点 |
   | `old_text` / `new_text` | 变更前后（**内联旧值**，不靠读上一条推断） |
   | `because` | **为什么改**（必填） |
   | `valid_from` / `valid_to` | 有效期区间；**复合主键含 `valid_from`** |

2. **`thesis.md` 只是渲染视图** —— "what changed" **自动生成**。
3. **三层笔记架构保留**，但**第三层从"文件"改为"版本序列 + 视图"**。
4. 补 mem0 缺的两个增量：**① 立场标注**（supporting / challenging / neutral）**② "活文档"概念**。

**理由**
1. **过渡必须被捕获**："新状态 + 它替代了什么"。
   `Bad: "User prefers oat milk lattes"` / `Good: "User switched from almond milk to oat milk lattes after developing an almond sensitivity"`
2. **只有版本序列化，"重复检测"才可查询** —— 覆盖式文件永远答不出"你说过几次"。
3. **旧值内联**（`old_value` + `new_value` 同一行）→ 不依赖"读上一条"推断前值（推断会在并发/乱序时出错）。

**被否决的方案**
- **保留文件 + git 当版本控制**：git 是**代码**的版本控制，不适合做**查询**（"这句话出现过几次"要遍历历史）。
- **只存 `new_text`，旧值靠前一条**：多一次查询，且乱序时错误。

**影响**
- `thesis.md` 需要渲染器 + 一致性检查（视图与表不一致 = 缺陷）。
- 论点页要显示**版本 Diff**（对应"我在变成谁"）。

## ADR-0014 · `decisions` / `reviews` / `decision_review_state` 三表分离

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/11-open-science.md` 决定 7（`docs/reproducibility-cases/README.md:51-57`）

**背景**
原设计里"决策的原始记录"与"复盘结论"在同一处 —— 复盘会**回写决策**。
这与红线 4（结果之前记录）直接冲突：**回写会污染"当时怎么想的"这一不可再生的证据。**

**决策**
物理分离为三张表：

| 表 | 性质 | 说明 |
|---|---|---|
| `decisions` | **append-only** | 用户当时写下的原始记录，**永不修改** |
| `reviews` | 可多条 | 复盘结论（**一条决策可以复盘多次**） |
| `decision_review_state` | **唯一真源** | "是否已复盘"**只在这里** |

**⚠️ 硬规则**：**"是否已复盘"绝不从 `reviews` 是否存在推断。**

**理由**
1. **回写会破坏红线 4** —— 而红线 4 是整个产品的地基（"在结果之前写下的文字，是唯一不可被未来污染的过去"）。
2. **"是否已复盘"是一个状态，不是一个派生量** —— 派生量会被"删除一条 review"之类的操作悄悄改变。
3. **`reviews.outcome` 允许 `failed` 为一等值** —— 禁止"失败但…"这类把亏损包装成收获的措辞（红线 10）。

**被否决的方案**
- **单表 + 状态字段**：`decisions.status = 'reviewed'` 看起来够用，但**复盘内容仍无处安放**（多条复盘会互相覆盖）。
- **用 `reviews` 行数当状态**：见上，派生量不可靠。

**影响**
- 复盘页要显示"第 N 次复盘"。
- 需要一个 `is_reviewed()` 判定函数（读 `decision_review_state`，不读 `reviews`）。

## ADR-0015 · 数据取值四态（`ok` / `no_data` / `error` / `unavailable`）

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/10-akshare.md` 决定 1（`SKILL.md:794-797`）+ `11-open-science.md` 决定 3（`README.md:150, 181`）
- **修正**：改原设计（"成功 / 失败"两态 → 先扩到三态 → 再补第四态）

**背景**
原设计只有"成功/失败"。**最危险的失败模式**是：把"接口坏了"当成"确实没有数据" ——
**产品安静地失效，用户基于错误前提做决策。**

**决策**
四态，且**业务结果与系统故障必须在类型层面就不同**：

| 态 | 含义 | 类型 |
|---|---|---|
| `ok` | 有数据 | — |
| `no_data(reason)` | **确实没有**（业务结果） | `NoDataError(ValueError)` |
| `error(code)` | **取数失败**（系统故障） | `DataFetchError(RuntimeError)` |
| ⭐ `unavailable` | **存在但无法验证** | 显式标记 |

**理由**
1. **`unavailable` 与 `no_data` 对用户的意义完全不同**：
   `no_data` = "不存在"（用户不会想它）；**`unavailable` = "存在，但我们没法确认"（用户必须知道这里有个洞）**。
2. ⚠️ **JSON 解析错误是 `ValueError` 的子类** —— **不显式包装就会被当成"确实没有数据"**。这是实测踩到的坑。
3. **禁止启发式默认值** —— "无法判断"时必须抛错或标 `unavailable`，**绝不返回"看起来合理"的数**。

**被否决的方案**
- **统一返回 `Optional`（None = 没数据）**：无法区分"确实没有"与"取数失败"。
- **返回空表 + 日志**：日志用户看不到，产品仍会静默失效。

**影响**
- 所有数据接口的返回类型需要显式四态。
- 错误码见 `.ai/error-codes.md` §2.2。

## ADR-0016 · SQLite CHECK 约束外置 + append-only 触发器

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/11-open-science.md` 决定 9/10（`prisma/sqlite-check-constraints.json:1-30`）
- **修正**：改原设计（"数据契约靠文档写死 + 单元测试"→ 补数据库层强制）

**背景**
"只增不改"如果只写在文档里，**代码写错了数据库不会拦**。数据契约如果只靠单元测试，**测试没跑到就漏了**。
对应宪法 0.2 的判据：**能不能把这条规则从 ① 文档移到 ④ 数据库？能移就必须移。**

**决策**

1. **append-only 用触发器强制**（所有日志类表）：

   ```sql
   CREATE TRIGGER <table>_no_update BEFORE UPDATE ON <table>
   BEGIN SELECT RAISE(ABORT, '<table> is append-only'); END;
   CREATE TRIGGER <table>_no_delete BEFORE DELETE ON <table>
   BEGIN SELECT RAISE(ABORT, '<table> is append-only'); END;
   ```

2. **CHECK 约束外置成 JSON 清单**（不散落在迁移脚本里），覆盖五类：
   标识非空（用 `trim` 防纯空白）· 枚举白名单 · JSON 有效性+类型+长度 · 长度上限 · **条件必填**。
3. **条件必填的标准写法**：`kind != 'text' OR quote IS NOT NULL`（**不用 `CASE WHEN`** —— 避免方言差异）。
4. **约束命名**：`<table>_<aspect>_check`。
5. **红线 6 的数据库表达**：`CHECK (outcome IS NOT NULL OR result_score IS NULL)`。
6. **红线 4 的数据库表达**：`CHECK (length(trim(rationale)) > 0 AND length(trim(counter_evidence)) > 0)`。

**理由**
1. **违反时代价从"评审提醒"变成"数据库报错"** —— 这是第 ④ 层。
2. **外置成清单**：SQLite 通过 SQLAlchemy/Alembic 表达约束的能力有限，且约束散落在迁移里难以审查。
3. **条件必填用 `OR` 而非 `CASE WHEN`**：跨方言兼容 + 可读性。

**被否决的方案**
- **只在 Pydantic 层校验**：绕过 API 直接写库就失效了。
- **只在测试里校验**：测试没覆盖到的路径就漏了。

**影响**
- 需要一份约束清单文件 + 一个"清单 → SQL"的生成/校验步骤。
- 需要集成测试验证"违反约束时确实抛错"（否则约束可能写错语法而静默失效）。

## ADR-0017 · 标的主键 = `(market, code)`；失效条件 = 结构化谓词

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/10-akshare.md` 决定 4/11/12
- **修正**：改原设计（"标的主键 = `code`" · "失效条件是自由文本"）

**背景**
1. **`000001` 在沪市是上证指数、深市是平安银行** —— 代码→市场是**一对多**。
2. 失效条件（"营收同比转负就重评"）如果是自由文本，**就没有"数据触发"，只能靠用户自觉 —— 而用户不会自觉**。

**决策**
1. **标的主键 = `(market, code)`**。
2. **禁止"从代码推断市场"作为唯一依据** —— 市场标识必须来自**显式输入或数据源返回**；
   推断**只能用于校验**（矛盾时抛错），**不能用于补全**。
3. ⭐ **`000xxx` 是"歧义段"不是"矛盾"**（`sh000001`=上证指数 vs `sz000001`=平安银行）→ **必须让用户选市场，不能猜**。
4. **Ticker 归一化**：`re.match` **整串锚定**（禁止 `re.search` 捞 6 位）· **前后缀二选一**（`SH000001.SZ` 拒绝）· **解析失败抛错不返空**。
5. **失效条件 = 结构化谓词** `{metric, operator, threshold, as_of}`；自由文本只能作**补充说明**，**判定必须走谓词**。
6. **财务数据存 `period_end` + `announced_at`**，查询用 `announced_at <= as_of`。
7. **行业/板块归属与指数成分存变更历史**；**没有历史时点数据时必须显式报错，不能用当前快照代替**。

**理由**
1. **主键错 = 数据串台** —— 这是最不可原谅的数据错误（而且**不会报错**，只会安静地给出另一个公司的数据）。
2. **谓词化才有"数据触发"** —— 产品亮点 ③（数据驱动对质）的实现前提。
3. **用当前快照做历史研究 = 前视偏差**。

**被否决的方案**
- **`code` 加前缀编码市场**（`sh000001`）：可行但**存的是字符串而不是两个字段**，查询与约束都更难表达。
- **失效条件用自然语言 + LLM 判定**：违反红线 15（agent 不做判断生成），且不可复现。

**影响**
- 所有涉及标的的表都要改成复合主键。
- 关注池输入框需要"歧义时让用户选"的交互。
- 失效条件的编辑 UI 需要一个谓词编辑器（**不是文本框**）。

## ADR-0018 · 检查与修复子系统（`Issue.available_fixes` 可以为空）

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/08-portfolio-performance.md`（`checks/{Check,Checker,Issue,QuickFix}.java`）+ `05-openspec.md` 决定 13（诊断信封）

**背景**
"报告问题"不够 —— 用户看到一个警告却不知道怎么办，等于没报告。
但反过来，**假装所有问题都能自动修，比不能修更糟**。

**决策**
1. 采用 `Check` → `Issue` → `Fix` 三段结构：

   ```
   Issue(date, entity, amount, label, available_fixes)
   Fix(kind: AUTO | MANUAL | SUGGEST, ...)
   ```

2. ⭐ **`available_fixes` 可以为空** —— 诚实：不是所有问题都能自动修。
3. ⭐ **凡涉及"用户必须亲手做"的操作（写决策 / 打分 / 改理由），`fix.kind` 必须是 `MANUAL`** —— 否则就绕过了红线 13。
4. **检查分两类**（见 ADR-0016 与宪法第十二条）：
   - `data/`（运行时扫库，24 条清单）
   - `static/`（编译期扫代码，AST 级）
5. **统一诊断信封** `{severity, code, message, target?, fix?}`，`fix` 是一句可执行建议。

**理由**
1. **"报告问题 + 怎么修"** 才是完整的检查。
2. **`MANUAL` 是合法形态** —— 这直接服务红线 13（有些事必须用户自己做）。
3. **两类检查不可互相替代** —— "某段代码不该存在"这类缺陷**测试永远抓不住**。

**被否决的方案**
- **只做 `data/` 检查**：抓不住"代码反模式"（裸 HTTP / 布尔状态 / 预测字段）。
- **所有 `fix` 都必须是自动的**：会导致"为了能自动修而放宽检查"。

**影响**
- 需要检查框架 + 两类脚本 + fixture 测试。
- 检查结果需要 UI 呈现（`MANUAL` 类要明确告诉用户"这一步需要你来做"）。

## ADR-0019 · 数据源唯一入口 + 限流/熔断/降级差异表

- **日期**：2026-09-26
- **状态**：✅ 已采纳
- **来源**：`references/deep-dives/10-akshare.md` 决定 7/9/10（`SKILL.md:362-374, 763-773`）
- **修正**：改原设计（"三源互备 + 缓存优先 + 熔断"只有原则，没有实现）

**背景**
原设计只有原则句。实测：**东财连续请求会触发限流**；**45000+ 请求导致 IP 级封禁 20+ 小时**。
**"限流必须是一个函数，不能是'请大家记得加 sleep'。"**

**决策**
1. ⭐ **所有外部数据访问走唯一入口函数**，内置：**串行化 + 最小间隔 + 随机抖动 + 会话复用 + 默认 UA + 熔断 + 缓存**。
2. ⭐ **时间戳在 `finally` 里更新** —— **失败也算一次访问**，否则连续失败会变成轰炸。
3. ⭐ **403 不重试**（风控信号，重试只会加重）。
4. **禁止在业务代码里裸调 `httpx` / `requests` / `urlopen`** → 由静态检查 `no-raw-http` 拦截。
5. **限流与封 IP 分成两个错误码**（恢复策略不同：降速 vs 等 20 小时）。
6. ⭐ **降级路径表必须写"与主源的差异"**，且**差异必须能被程序读到**（不是只写在文档里）。
7. **优先级按"封禁风险"排序，不按"数据丰富度"**：腾讯 → 交易所官方 → 新浪/巨潮 → 东财末位。
8. **同一域名的不同子域风控面不同** —— 精确到子域，不说"某站被封了"。

**理由**
1. **限流是横切关注点**，散落在各处必然有人忘。
2. **`finally` 更新时间戳**是"防止失败变轰炸"的关键细节 —— 只在成功时更新会导致失败时无限重试。
3. **403 是风控信号不是网络抖动** —— 重试会加重封禁。
4. **降级差异必须程序可读** —— 否则用户拿到的是"看起来完整但不完整"的数据（**最危险的失败模式**）。

**被否决的方案**
- **引入 akshare 等第三方库代管**：给 exe 增重，且**它自己把它移除了**（中间层增加故障点）。
- **在每个调用点各自加 `sleep`**：必然有人忘。

**影响**
- 需要 `providers/` 层 + 唯一入口 + 静态检查脚本。
- 需要 `.ai/data-sources.md` 作为数据边界与降级差异的真源。

## ADR-0020 · 数据层：能力路由、四态降级与失败语义

| **T-10** | ⭐ **只存基础事实，派生指标现算**；例外：FSRS 调度状态（有状态累积量） | ⚠️ 部分 —— `Quote` 存 `adj_factor` 而非复权价序列 |
| **T-11** | ⭐ **取数失败时保留上轮有效缓存**（不清空）+ **标明数据陈旧** | ✅ `DataResult.stale` + `router._recall()` |
| **T-12** | **缓存层数上限 3**；改动缓存读写路径时**必须在 PR 列出受影响缓存层** | ⚠️ 当前 1 层（`MemoryCache`），磁盘层属 S1 持久化 |
| **T-13** | ⭐ **失败路径必须 fail-closed，不静默返回错误金融结果** | ✅ `DataResult` 构造即校验（ok 必须有值、error 必须有码） |
| **T-14** | **"无法说明根因的掩盖式修复"（加延时 / 重试 / 强制刷新 / 吞异常）不得合并** | 流程类 —— 见 ADR-0026 |
| **T-15** | **"需用户重启或手动清数据才能正确显示"不得合并** | 流程类 —— 见 ADR-0026 |
| **T-20** | J1 验收补**"编辑态不得泄漏到新建态"**；I1 验收补**"切换标的后不得显示上一标的数据"** | ❌ 未实现（需写进 `specs/` S2 · S4） |

**理由**
1. **能力必须可被程序读到，不能只写在文档里** —— 否则"配置了三源"与"三源真能用"会被混为一谈，页面就会承诺它画不出来的图。
2. **边界转换只在一处发生** —— 日期格式（`20260918` vs `2026-09-18`）与单位（手 vs 股、万元 vs 元）是**同一个类别的错误**：错一次，错一片。把它们钉在 `providers/` 层，上游就永远看不到源的格式。
3. **`stale` 必须显式** —— 降级本身没错，**静默降级才是灾难**（`.ai/data-sources.md` §5）。

**被否决的方案**
- **接入 TSP 的数据源**：全需 API Key，违反零注册（用户不该为了用工具再去注册账号）。
- **把能力矩阵写在配置文件里**：配置可以写"我支持日线"，但**无法表达"这个源实际上取不到"**。能力必须是**代码内可执行的真源**。

**影响**
- 新增数据源 = 注册一个 `ProviderCapabilities`，**不是加一个 `if`**。
- `.ai/data-sources.md` 需要新增「批量失败语义」列与「已知口径不一致清单」。
- **T-02 的 `candidates` / `pending` 与 T-08 交易日探针是本 ADR 最大的未完成项**，列入 S1 后续。

## ADR-0021 · 知识库模仿「记忆」，不模仿「文件系统」

- **日期**：2026-09-26
- **状态**：✅ 已采纳 · ❌ 未实现（K1 / K3 / T1 / J4 全部未开始）
- **来源**：`references/deep-dives/13-supermemo.md` 决定 S-01 ~ S-11
- ⚠️ **本篇是全系列唯一"读文档不读代码"的（L2 级）** —— SuperMemo 闭源。**只能借概念，不能声称看过实现。**

**背景**
我们的知识库原本是个**文件柜**：按时间排序、只进不出、把"重复"一律当错误。
SuperMemo 的「知识漏斗」（`web → selection → extract → cloze → stabilize → apply → convergence`）暴露出我们**缺三段**：③ cloze · ④ stabilize（claim 不能独立调度）· ⑥ convergence（没有出口）。

**决策**

| 编号 | 决定 | 实现 |
|---|---|---|
| **S-01** | 三层笔记**补第四层出口 `converged`**（已收敛）—— 处理完的材料移出待处理队列，默认不再显示 | ❌ |
| **S-02** | ⭐ **claim（digest）是独立的可调度单元**：有自己的优先级与复习周期；`thesis.md` 只是它的视图 | ❌ |
| **S-03** | 知识条目加 **`priority`** 字段（用户可调 + 系统可推）；**默认排序按优先级，不按创建时间** | ❌ |
| **S-04** | ⭐ J4 重复检测**改为两问**：① 同上下文重复 → 提醒 ② **跨上下文语义重复 → 提议合并** | ❌ |
| **S-05** | 待处理队列加**第三态「已推迟」**（带到期时间）—— "暂不处理"是特性不是拖延 | ❌ |
| **S-06** | T1 今日页明确为 **「TO DO 分支」**：与已整理知识**分离**，且**条数必须能收敛** | ❌ |
| **S-07** | ⭐⭐ **知识库模仿记忆，不模仿文件系统**：卡片至少有 `priority` / `stability` / `retrievability` 三个**独立**维度 | ❌ |
| **S-08** | **允许"只在创作阶段"的知识碎片存在**，不强制成文；两阶段都要有对应状态 | ❌ |
| **S-09** | **来源（reference）与 claim 分离存储**（多对多） | ❌ |
| **S-10** | 新增知识库健康指标：**收敛率**（`converged / captured`） | ❌ |
| **S-11** | ⚠️ **诚实边界写进解读**：本篇是唯一 L2 级，**只能借概念，不能声称看过实现** | ✅ 已在解读文件与本表标注 |

**理由**
1. ⭐ **没有出口的知识库会膨胀到没人打开。** 这是"文件柜"与"记忆"的分界：记忆会自动遗忘不重要的东西，文件柜不会。
2. **`priority` 与 `stability` 必须独立** —— 重要性高但记得牢的东西，和重要但总忘的东西，需要**不同的调度**。合成一个分数就再也分不开。
3. **"重复"有两种** —— 同上下文重复（你在重复自己）**要提醒**；跨上下文语义重复（同一个洞见在不同场景被重新发现）**是收敛信号，该提议合并**。原设计把后者也当错误，方向错了。

**被否决的方案**
- **auto-postpone（SuperMemo 的自动推迟）**：可能让用户**永远看不到某些材料** → **撞红线 10**（必须让用户面对不舒服的数据）。**明确不采纳。**
- **保留"按创建时间排序"**：时间顺序与重要性无关，会让"最重要的东西"沉底。

**影响**
- `thesis.md` 的渲染视图要能按 `priority` 排序，不只是按版本。
- **K3 需要一个我们自己的状态机**：fsrs 库的 `State` 只有 `Learning / Review / Relearning` 三态，**没有"已推迟"，也没有"已收敛"** —— 这两个态必须由我们的表实现（实测见 `.ai/logs/changes/2026-09-26-s1-data-layer.md`）。
- `.ai/status.md` 要加「收敛率」指标。

## ADR-0022 · K1 卡片新增 `origin` / `priority` / `status`，以及第三种录入通道

- **日期**：2026-09-26
- **状态**：✅ 已采纳 · ❌ 未实现
- **来源**：`AlphaCouncil-基础功能打磨与AI桥接.md`（第一部分字段表 · 第三部分问财桥接）
- **关联**：ADR-0010（工具权限四档）· ADR-0021（S-01 / S-03）

**背景**
问财桥接（`iwencai.com`）是**第三种录入通道**：写提示词 → 复制 → 问财返回结构化 → 粘贴导入。
**但问财返回的是"判断"，不是"事实"** —— 直接入库就等于让 AI 替用户做判断，**撞红线 15**。
需要一个**字段级的隔离机制**。

**决策**

| 字段 | 类型 | 说明 |
|---|---|---|
| `origin` | enum | ⭐ **新增**：`user_written` / `extracted` / **`ai_generated`** |
| `priority` | int 1–5 | ⭐ **新增**（S-03）：默认 3，用户可调 |
| `status` | enum | ⭐ **新增**（S-01）：`active` / `converged` |

**`ai_generated` 的三条硬约束**：
1. **不能当证据** —— 不进 supporting / challenging 统计；
2. **不进 FSRS** —— 不占用复习队列；
3. **要升级为证据，必须用户点「核对来源」** —— 打开原始来源、确认数字一致，才能把 `origin` 改成 `user_written`，**且这次修改留痕**。

**理由**
1. **`origin` 是红线 15 的字段级实现** —— 提示词可以被绕过，**字段不能**。
2. ⚠️ **`origin` 可变，与 append-only 冲突** —— 所以"核对来源"**必须留痕**（记一条升级记录），而不是静默改字段。
3. **`priority` 与 `status` 是 S-01 / S-03 的载体** —— 没有这两个字段，"模仿记忆"只是口号。

**被否决的方案**
- **不设 `origin`，靠用户自己记得** —— 用户不会记得，而且**三个月后的自己更不会**。
- **`ai_generated` 直接不可入库** —— 会让桥接失去价值；**隔离 + 可升级**比"禁止"更实用。

**影响**
- RAG 导出的**三条硬约束**：单向只出不进 · 无 `source_url` 不导出 · **必带 `origin`**（不标 `origin` 的导出是危险的）。
- 需要一张 `origin_upgrades` 留痕表（**待设计**）。
- 6 个提示词模板：财务 / 事件 / 行业 / 估值 / 风险 / **论点证伪**。
- ⚠️ **最大风险未实测**：问财能否稳定返回结构化表格 —— **必须先做一次人工实验**（列入 S2.5 前置）。

## ADR-0023 · 补齐 12 项「知识管理系统基本功能」

- **日期**：2026-09-26
- **状态**：✅ 已采纳 · ❌ 未实现
- **来源**：`references/research/08-金融知识管理系统调研.md` 决定 F-01 ~ F-08

**背景**
**自省**：前 12 篇深度解读**全部按「能力维度」找**（间隔重复 / 决策日志 / PIT…），**从没按「产品相似度」找同类**。
结果：**基本盘被当成不言自明** —— 而基本盘不做，**创新没有载体**。

**决策**

| 编号 | 决定 |
|---|---|
| **F-01** | ⭐⭐ **补 12 项基本功能**：编辑器 · 附件（图片/PDF）· 模板 · 批量导入 · 属性视图 · 命令面板 · 快捷键 · 回收站 · 本地备份 · 批量操作 · 快速捕获 · 保存的查询 —— **列入 P0 或 P0.5** |
| **F-02** | **属性视图（表格）必须有** —— 决策日志、卡片列表都要能切表格 |
| **F-03** | **模板系统**（决策 / 卡片 / 复盘模板，用户可改） |
| **F-04** | **批量导入**（Markdown / CSV），**导入必须带 provenance 校验**（无来源的标 `verification: pending`） |
| **F-05** | **证据等级 L1–L4** 加进 provenance |
| **F-06** | **`content_type`（`fact` / `interpretation` / `open_question`）** 作为 `claim_type` 之外的**第二维度** |
| **F-07** | **知识回写协议（RWP）**：四条通道（教训→卡片 / 决策→模式 / 复盘→失效条件库 / 事件→行业地图） |
| **F-08** | **决策 `action` 枚举**：`buy / add / hold / trim / exit` |

**理由**
1. **护城河未被推翻**：11 个同类项目（**全 0–9★**）**没有一个同时具备** FSRS 决策层 / 二维评分 / 重复检测 / PIT / 三源互备 —— 但它们**全是"模板 + 提示词"，没有一个是真的程序**。**我们的优势是"真的做出来"，前提是基本盘得在。**
2. **F-07 是"闭环"的机制化** —— 没有 RWP，"知识反哺决策"只是流程图上的箭头。

**被否决的方案**
- **只做创新功能，基本盘后补** —— 用户连"新建一张卡片"都别扭时，不会用你的间隔重复。
- ⚠️ **不采纳同类项目里的「太难」第三选项** —— **给冲动留后门**（对应 S-05 的"已推迟"是**带到期时间**的推迟，不是无限期逃避）。

**影响**
- 12 项缺口**只需引 3 个库**（见 ADR-0024），不是 12 个。
- 路线图需要重排：F-01 的 12 项要插入 P0 / P0.5。

## ADR-0024 · 依赖选型与许可证红线

- **日期**：2026-09-26
- **状态**：✅ 已采纳 · ⚠️ 部分实现（`L-06` 检查脚本未写）
- **来源**：`references/research/09-基础功能可复用库选型.md` 决定 L-01 ~ L-06

**背景**
主人问「**GitHub 有没有好的项目，我们用一下**」。
**结论：整体项目一个都不能用** —— 知识管理头部项目 **100% 是 AGPL / GPL / BSL**：
AppFlowy 76,935★（AGPL）· AFFiNE 72,985★ · Joplin 56,481★（AGPL）· **思源 46,511★（AGPL）**· **Logseq 45,055★（AGPL）**· outline 40,708★（BSL）· Trilium 37,989★（AGPL）· Zettlr 13,581★（GPL）。
**这不是巧合，是许可决定的** —— AGPL 正是用来保护它们商业版的。

**决策**

| 编号 | 决定 |
|---|---|
| **L-01** | **不采用任何现成 PKM 项目做底座**（许可 + 形态 + 护城河三重理由） |
| **L-02** | ⭐ **用库补 12 项基础功能**：编辑器 **Milkdown** · 表格 **TanStack Table** · 附件 **Uppy + pdf.js** · 图谱 **react-force-graph** · 检索 **SQLite FTS5** |
| **L-03** | **图表用 lightweight-charts，但只做折线/柱状，不做交互式 K 线** |
| **L-04** | ⚠️ **中文全文检索必须做分词**（SQLite FTS5 默认对中文无效）→ 需实测 `jieba` 还是 `trigram` |
| **L-05** | 同类项目的**模板与字段设计可直接用**（`the-investor360` MIT · `Hardtech-VC-OS` Apache-2.0），**须保留版权声明** |
| **L-06** | ⭐ 新增依赖**必须过许可证检查**（`make check` 加一项：扫描依赖许可，**出现 AGPL / GPL 即失败**） |

**理由**
1. **三个硬理由**：① 许可传染 ② 形态与栈不符（它们是 Web/Electron 应用，我们是 pywebview 桌面程序）③ **用它们 = 放弃唯一差异**。
2. **MIT / Apache-2.0 可参考；GPL / AGPL 传染性，绝不可抄代码** —— **只借机制，自己重写。**
3. ⭐ **L-06 把许可从"人工审查"变成"CI 红灯"** —— 符合宪法 0.2（能往第 ④ 层移就必须移）。

**被否决的方案**
- **用思源 / Logseq 做底座再改**：AGPL 传染，且等于把产品的核心（知识组织）交给别人的架构决定。

**影响**
- 依赖许可检查脚本列入 `.ai/checks/static/`（**未实现**）。
- L-04 的中文分词方案**未实测** —— 是 K4 的关键风险。

## ADR-0025 · 前端资源规格与视觉纪律

- **日期**：2026-09-26
- **状态**：✅ 已采纳 · ❌ 未实现（前端工程未开始）
- **来源**：`AlphaCouncil-前端资源与打磨规格.md` 决定 V-01 ~ V-08

**背景**
主人要求「**可视化还要打磨优化 · 组件还要打磨优化 · SVG 图标用开源的 · 组件也是开源的 · 动画也是**」。
**"打磨"必须落成可检查的数值与禁令**，否则它就是一句形容词。

**决策**

| 编号 | 决定 |
|---|---|
| **V-01** | **组件底座不换**（shadcn/ui + Radix）—— **打磨 = 改规格不改库** |
| **V-02** | ⭐ **图标 = Lucide + Tabler（补，MIT）+ 自绘金融图标**；描边分三档（**1.5 / 1.25 / 1**） |
| **V-03** | ⭐ **动画 = auto-animate（主）+ motion（辅）**；**明确排除 GSAP**（**非 OSI 开源**） |
| **V-04** | ⭐ **动画四级规范 + 六条禁令**（尤其**禁止数字滚动 count-up**） |
| **V-05** | **必须补 12 个组件**（DataTable / StatCard / CommandPalette / Drawer / Popover / Select / DatePicker / Toast / EmptyState / Progress / Skeleton / Divider） |
| **V-06** | **可视化保持 lightweight-charts + Recharts + visx**；**uPlot 为备选**（体积超预算时）；**排除 Tremor**（星数低 + 停更近 1 年） |
| **V-07** | ⭐ **图表规范新增五条**，含「**禁止为视觉冲击截断 Y 轴**」 |
| **V-08** | ✅ **已定（2026-09-26，主人授权"你来决定"）**：⭐ **只做日线/周线的收盘价静态走势**，**不做**分时 / 技术指标 / 实时刷新 / 交互缩放（**判据：历史走势是事实，分时盯盘是诱惑**） |

**配套硬规格**（可检查，不是形容词）：
- **三条绝对不能做**：圆角 > 4px · 任何 `box-shadow` · 彩色胶囊 Badge
- **动画四级**：L0 数据无动画 · L1 微反馈 100–120ms · L2 状态过渡 180–220ms · L3 列表增删 200ms
- **六禁**：入场动画 · shimmer · ⭐ **数字滚动 count-up** · 弹跳 · 视差 · 图表入场
- **图表五条**：走 token 禁默认色板 · 刻度 11px `tabular-nums` · ⭐ **禁止截断 Y 轴** · tooltip 必显"数据截止日" · 空数据显"暂无 + 原因"

**理由**
1. **动效只用来"说明状态变了"，不用来"吸引注意"** —— count-up 数字滚动是最典型的"用动效制造兴奋"，与红线 9（不展示成绩）同源。
2. ⭐ **禁止截断 Y 轴是金融图表的职业底线** —— 截断能让 2% 的波动看起来像崩盘，这是**用视觉撒谎**。
3. **"打磨"的判据是"能不能被检查"** —— 所以 V-04 与 V-07 全是数值和禁令。

**被否决的方案**
- **GSAP**：非 OSI 开源许可 → 与 ADR-0024 的 L-06 冲突。
- **Tremor**：3,633★ 且停更近 1 年。
- **换掉 shadcn/ui**：问题不在库，在**我们没写规格**。

**影响**
- 前端工程需要一份"组件规格表"（12 个组件的尺寸 / 状态 / 空状态）。
- ✅ **V-08 已拍板 = 方案 A**（2026-09-26）—— **只做日线/周线静态走势**。**边界必须写死**（§七 的"允许 / 禁止"两列），否则会慢慢滑向 C。
- ⚠️ **未实测**：auto-animate / motion 的实际集成与体积 · uPlot 是否真需要（取决于 exe 体积预算）。

## ADR-0026 · 审查纪律补充（来源 TSP 复审实践）

- **日期**：2026-09-26
- **状态**：✅ 已采纳 · ⚠️ 部分实现
- **来源**：`references/deep-dives/12-tick-stock-panel.md` 决定 T-14 ~ T-19
- **关联**：ADR-0005（规格驱动流程）· 宪法第九条

**背景**
TSP 的复审实践里有四条**我们原本没有的纪律**，且每一条都对应一个**真实的失败模式**。

**决策**

| 编号 | 决定 | 实现 |
|---|---|---|
| **T-14** | ⭐ **"无法说明根因的掩盖式修复"（加延时 / 重试 / 强制刷新 / 吞异常）不得合并** | ❌ 需写进 `agent-guide.md` |
| **T-15** | ⭐ **"需用户重启或手动清数据才能正确显示"不得合并** | ❌ 同上 |
| **T-16** | 复审时：**不看最后 commit，看完整 diff**；**问题引用最新行号**；**全部解决且无新增才能改结论** | ⚠️ 部分 |
| **T-17** | **复审输出模板**（结论 / 阻断 / 非阻断 / 已验证 / 剩余风险）→ 落到 `.ai/logs/review/` | ❌ 未实现（目录只有 README） |
| **T-18** | **至少运行受影响模块的测试**（不只跑新加的单个测试）；**提交前 `git diff --check`** | ⚠️ 部分（`make check` 未实现） |
| **T-19** | ⭐ **`make check` 输出必须列出"跑了哪些 / 跳过了哪些"** —— **绿灯不等于完成** | ❌ 未实现 |

**理由**
1. ⭐ **T-14 与 T-15 是"反掩盖"条款** —— 它们拦截的正是最舒服的那种"修复"：**看起来好了，但没人知道为什么好。**
2. **T-19 直击"绿灯幻觉"** —— 覆盖率 80% 可能只是"跑了一小部分"，必须显式列出**跳过了什么**。
3. **T-16 的"不看最后 commit"** —— 只看最后 commit 会漏掉中间引入的问题。

**被否决的方案**
- **只在 reviewer 的提示词里写这些** —— 提示词会被忽略，**模板和门禁不会**。

**影响**
- `.ai/logs/review/` 需要一个输出模板。
- `make check` 需要输出"跑了哪些 / 跳过哪些"。
- `.ai/agents/reviewer.md` 需要补 T-14 / T-15 / T-16。

## ADR-0027 · 技术栈锁定表与实现现状的差异：agent 三件套已采纳未实现

- **日期**：2026-09-28
- **状态**：✅ 已采纳（记录差异本身）· ❌ 所记录的技术**未实现**
- **发现方式**：重写 `docs/ARCHITECTURE.md` 时**我自己写错了一句话**，纠正过程中发现的更大问题。见 `.ai/regressions/0005`
- **依据**：宪法第三条（技术栈锁定）· ADR-0001 · `.ai/specs/003-agent-orchestration/spec.md` 顶部横幅

### 背景

宪法第三条有一张"已锁定选型"表。**逐行与仓库对照**（2026-09-28）：

| 宪法第三条写的 | 仓库实际 | 判定 |
|---|---|---|
| Agent 编排 **LangGraph** ≥ 0.2 | `pyproject.toml` **无此依赖**；无 `graph/` 包；全仓零 import | ✅ 已采纳 · ❌ 未实现 |
| Agent 可观测 **Langfuse**（数据模型） | 无 langfuse 依赖；`core/trace.py` **手搓了它的数据模型**（本地 JSONL） | ✅ 已采纳 · ✅ 以"降级"方式实现（宪法原文允许"可替换/降级"） |
| Agent 工具协议 **fastmcp** | 无依赖、无 MCP server | ✅ 已采纳 · ❌ 未实现 |
| 记忆调度 **py-fsrs** | 实际包名是 **`fsrs`**；`py-fsrs` **在 PyPI 上不存在** | ⚠️ **宪法这一行名字是错的** |
| 数据 **SQLite + SQLAlchemy 2 + Alembic** | `storage/` 在裸 `sqlite3` 上**手搓**了迁移器；`sqlalchemy` / `aiosqlite` 仍声明在 `pyproject.toml` 里，**全仓零 import** | ⚠️ **实现已超越原选型，宪法与残留依赖都没更新** |

**所以真相既不是"已移除"，也不是"已实现"，而是第三种状态：已采纳、写在宪法里、但从未落地。**

### 决策

1. **不撤回 ADR-0001。** LangGraph 仍是已采纳的编排选型。撤回它等于宣称
   "我们做过 agent 编排然后放弃了"，而事实是**一次都没开始**。
2. **在宪法第三条表下方加一段状态标注**（不改表格内容），逐行标出
   「已采纳未实现 / 名字有误 / 已被实现超越」，并指向本 ADR。
3. **agent 三件套的启用条件写死**，避免它长期停在"看起来快做了"的状态：
   - 出现**一个必须有运行期 agent 才能实现的产品能力**（当前已交付的 S1–S4 / K1 / K2 都不需要），**且**
   - **`make eval` 存在且能跑出通过率**（简历验收①的第二块，至今未做）。
   两条**同时**满足才动手装依赖。在此之前，**开发流水线由 `.ai/` 的书面纪律承载**，
   这不是"还没来得及"，是一个明确的选择。
4. **删除 `docs/adr/` 这份重复存储**，只留一个指向本文件的 README。
   两个 ADR 存储不是"要维护的东西"，是"不该存在的东西"。

### 为什么第 3 条是关键

`spec 003` 自己的横幅已经写明：agent 是"**只是数据的搬运工**…**不是产品差异化核心**"。
既然如此，就不该让它在路线图上看起来像一条即将开始的工程。

append-only 台账 · 宪法 · 逐变更 spec · 12 条静态检查 · 变异检查过的回归 · 可回放 trace。
**不能展示**"我交付了一条 agent 流水线"，因为运行期没有 agent。
`make eval` 正是把前者从"叙述"变成"可测量"的那一块。

## ADR-0028 · 两处偏离 `13-supermemo.md`：`retrievability` 不计算 · 队列不按 priority 排

- **日期**：2026-09-28
- **状态**：✅ 已采纳（记录偏离本身）
- **发现方式**：写 K3 的复习界面时，逐条对照 `references/deep-dives/13-supermemo.md`，
  发现 spec 018 的两处实现与已采纳的解读不一致
- **依据**：宪法红线 9（不展示「成绩」）· 红线 11（不鼓励频繁操作）

### 背景

ADR-0021 归并了 `13-supermemo.md` 的 11 条决定。其中两条与 K3 的实现直接冲突：

| 解读 | 原文 | spec 018 的实现 |
|---|---|---|
| **S-07** | 卡片至少有 `priority` / `stability` / `retrievability` 三个**独立**维度 | 只实现两个；**`retrievability` 完全不计算** |
| **S-03** | 知识条目加 `priority`；**默认排序按优先级，不按创建时间** | 复习队列只按 `due_at` 排，**不排 priority** |

### 决策

**1. `retrievability` 不计算。**

它是「你此刻能记住它的概率」—— **关于用户记忆的成绩**，不是关于世界的事实。
红线 9 明文禁止展示成绩，而一个永远不显示的数字，没人会去要求它存在。

S-07 的真正主张是"三个维度**互相独立**、不要互相推导"，这一点**我们遵守**：
`priority` 不参与 FSRS 计算，`stability` 不影响队列顺序。缺的只是第三个数字本身。

**2. 复习队列只按到期时间排。**

S-03 讲的是**知识条目列表**（标的页第 ② 块的展示顺序）—— 在那里仍然成立。

但把 priority 套到**复习队列**上，会让用户在"都已到期"的卡里先做重要的那条。
听起来合理，可它把「我的积压有多严重」变成了一个用户能感觉到的**排名** ——
而红线 11 反对的正是这个。**S-03 要的是"别按时间排"，我们要的是"别按任何东西打分"。**

### 影响

- `ScheduleRead` / `ReviewReceipt` **没有**任何成绩字段，
  由 `test_reviews_api.py::TestTheResponseCarriesNoScore` 枚举字段钉住
- `fsrs.Scheduler.get_card_retrievability` 存在但**从不调用**，
  由 `test_scheduling.py` 的 **AST 级**测试钉住（用 AST 不用字符串，
  因为两个模块的 docstring 都要**故意提到**这个方法名来说明我们不用它）
- 复习页的 E2E 断言页面上**不出现**百分数 / 正确率 / 连续天数 / 进度分数
- 标的页的卡片列表顺序**不受本条影响**（S-03 在那里仍然成立）

### 遗留

- **S-07 的第三维度仍是空的。** 如果将来产品上出现"该不该现在复习这张卡"这类
  需要内部调度理由的场景，`retrievability` 可以在**不展示**的前提下被计算 ——
  但那需要另开一条 ADR 说清"算但不显示"与"不算"的区别。
- **S-03 在标的页是否已实现，本次没有核查**（K1 的列表顺序不在 K3 范围内）。
  已登记进 `status.md` §五。

### 遗留

- **`fsrs` 已声明未 import**，`py-fsrs` 的名字错误只在宪法里改了，ADR-0001 附近没有第二处提过它

## ADR-0029 · 「结果分到期前必须留空」下沉为数据库 `CHECK`

- **日期**：2026-09-28
- **状态**：✅ 已采纳（spec 020 · 迁移 0006）
- **来源**：`AlphaCouncil-项目总纲.md` P0-3 + 宪法第零条 0.2「能移就必须移」

**背景**

`项目总纲` P0-3 的硬门禁：

> **结果分在到期前必须留空**（不许提前打分，否则就是用结果污染决策评价）。

按常规做法这只是一条领域层校验 —— 调用方经过 `domain/review.py` 就够了。
但领域层校验是**自觉**：任何绕过它的写入（新脚本、临时查询、未来的第二个入口）
都能提前写下结果分，而这条规则**恰恰是最不该被绕过的那条**（提前打分就是后见之明）。

**决策**

把到期时刻从 `decision_review_state` **复制**进 review 行（`due_at_snapshot`），
并让数据库比较两者：

```sql
CONSTRAINT reviews_not_scored_early_check
    CHECK (outcome IS NULL OR reviewed_at >= due_at_snapshot)
```

**可行是因为 ISO-8601 时间戳是可字典序比较的字符串** —— 于是「时间上的先后」
变成了 SQLite 能执行的布尔表达式。

领域层的同一校验**保留**，但理由变了：它不再负责安全，只负责**给出我们自己的
错误码和可读消息**（`REVIEW_NOT_DUE`），而不是让调用方收到一个裸 `IntegrityError`。

**理由**

1. **这是 0.2 最干净的一个实例。** 一条本来只能靠自觉的纪律，变成了一行 `CHECK`，
   而**没有一个测试需要信任任何人的自觉** ——
   `TestTheGateSurvivesBypassingTheDomain` 走裸 SQL 证明第二次拦截真的生效。
2. **两道拦截的职责不同，不是冗余。** 数据库那道管**不可能被绕过**，
   领域层那道管**错误长得像不像人话**。删掉任何一道都是损失。
3. **顺带得到一个更精确的概念。** 状态表的 `reviewed_at >= due_at` CHECK 一开始
   挡住了"只写过程分"，暴露的是**「已复盘」这个词本来就没定义清** ——
   现在它只由结果分盖章，含义是「**复盘已完成**」，而半份复盘不算复盘。

**被否决的方案**

- **只在领域层校验**：够用，但对一条"最不该被绕过"的规则来说，"够用"是错的答案。
- **用触发器而非 `CHECK`**：触发器能做，但 `CHECK` 与列定义写在一起，
  读 schema 的人一眼就能看到这条门禁。**能用声明式表达就不要用过程式。**
- **不复制 `due_at`，改用触发器查状态表**：让 `CHECK` 依赖另一张表的状态 ——
  SQLite 的 `CHECK` 做不到子查询，而且那会让 review 行**不再自足**
  （一行的合法性取决于它自己看不见的东西）。

**影响**

- `reviews` **多一列** `due_at_snapshot`（冗余，但换来自足与可执行）
- 变异 **M3** 钉住：把这条 `CHECK` 改成恒真，裸 SQL 测试立刻变红
- ADR-0014 的三表分离不受影响 —— `due_at_snapshot` 是**当时的值**，
  与「是否已复盘」这个状态无关

**遗留**

- 到期日由调用方给定，**不猜**。「买满 90 天该复盘」是 `项目总纲` 的**建议**，
  判据未定义。谁来定这条规则，需要另开一条 ADR。

## ADR-0030 · 教训有自己的表，而「不可变」推导出了「没有 reset」

**日期**：2026-09-28 · **状态**：已采纳 · **相关 spec**：030（J5 教训转卡）

### 背景

`constitution.md` 第 7 条要求「每条教训必须生成一条调度项（FSRS）」，而项目里
**没有「教训」这个类型**。最省事的做法看起来是加一个 `review_id` 列、放松
`source_url` 的必填，让出处变成「URL **或** 复盘」。

### 决定

**教训是独立的一等类型**（`lessons` / `lesson_schedule` / `lesson_reviews` /
`lesson_promotions` 四张表），`cards` 的两条出处 `CHECK` **一个字不动**。

### 理由

**1. 放松 `cards` 的出处规则是把 spec 026 整个反过来。**
`status.md` 里当初建笔记的诊断是：

```
`cards` 表被 `source_url` 必填 + `source_title` 必填 + 前端硬编码单只 6 位代码
三条锁死 → 宏观判断、方法论、教训、读书笔记全都记不下
```

⭐ **教训就是那四个之一。** 为了让它回去而削弱当初建笔记的那条规则，是把一个已
解决的问题变成未解决，再付一次代价（SQLite 不能 DROP `NOT NULL`，改它意味着重建
被三张表外键引用的表）。

**2. 教训没有 URL 可给，这不是缺陷，是它的定义。** 它的出处是一次真实发生过的、
读者自己参与的判断失误 —— 那比一个 URL 更能说明「你当时怎么想的」。

**3. 不可变性是可推导的，而推导需要一个结构性的前提。**
教训**不可变**（改完它就不是那条教训了，你会写另一条），因此
`lesson_reviews` **不需要** `note_reviews` 的 `reset` 第三态。
现在三套流水：**两张不可变的两套没有 `reset`，一张可变的有。**
这个不对称不是巧合，是「教训和卡片同一类」的直接证据。

⭐ 而「不可变」一开始**只是个约定** —— `lessons` 没有守卫触发器。
推理是对的，前提没被钉住。所以补了两个 `BEFORE UPDATE` / `BEFORE DELETE` 触发器，
并让台账与 S-04 交叉核对「声明 append-only」与「真的有守卫」。

### 后果

- **红线 7 的强制手段是结构性的**：写教训与写调度项在一个事务里**无条件相邻**，
  没有「先写教训再决定要不要入队」这条代码路径。
- **「转卡」是一个独立且显式的动作**，并且**要求出处**。「我拿不出出处」推导为
  「这条已经是一条教训了，它还不是卡片」—— 而**拒绝不会丢任何东西**。
- **转卡不停止教训的排程**：红线 7 不能有「转了卡就不用再复习了」这种分支，
  而且那种分支是**隐形**的。
- 代价：第四套 FSRS 机制。**已接受** —— 前三套已经在回答同一个问题，而每套的
  不可变性不同，这正是它们必须分开的理由。

### 被拒绝的方案

| | 方案 | 为什么拒绝 |
|---|---|---|
| ❌ | `cards` 加 `review_id`，出处二选一 | 削弱 provenance rule = 推翻 spec 026 |
| ❌ | 独立 `lessons` 表但**不排程** | 不满足红线 7，那条红线仍然是 `partial` |
| ❌ | 教训可编辑 | 记忆强度会挂在不存在的文本上（spec 028 已为笔记付过这个代价） |
| ❌ | 转卡时**删除**教训的排程 | 红线 7 出现例外分支，而例外比没有功能更糟 |

## ADR-0031 · S-01 从「目录白名单」改成「模块白名单」——而且是改紧，不是改松

**日期**：2026-09-29 · **状态**：已采纳 · **相关 spec**：039（webhook 通道）· **相关**：ADR-0002（检索栈全部移除）、§7.8、§4.5

### 背景

S-01（`checks/rules/no_raw_http.py`）拦「业务代码直接 `httpx.get`」，宪法 §7.8 给了理由：

> 限流**必须是一个函数**，不能是"请大家记得加 sleep"。

而 §4.5 把这件事说全了：三源互备、东财连续请求触发限流、**「限流」与「封 IP」是两件事**、
**同一域名的不同子域风控面不同**。

⭐ **所以 S-01 真正要守的东西，逐条都是关于「数据源出口」的**：串行化、最小间隔、抖动、
会话复用、UA、熔断、缓存。而它的实现判的是**目录**：

```python
def _inside_providers(ctx, path) -> bool:
    return relative.parts[:1] == Path("providers").parts
```

**意图**是「HTTP 客户端只在被认可的地方被构造」，**实现**是「在一个目录里」。

`spec 033` 要抄 TSP 的 webhook 通道，撞在这里：不在 `providers/` 里 `import httpx` 就是 error，
而官方修复建议是「走 provider 层 —— `default_router()`」。

⭐ **那条建议对 webhook 是错的**：`default_router()` 是**行情**路由 —— 按 `Dataset` 声明能力、
按 `BatchSemantics` 处理批量失败、三源互备、带磁盘缓存。把一条飞书消息塞进去，
是让一个为「腾讯/新浪/东财的日线」设计的抽象去发通知。

### 决定

**S-01 的白名单从「`providers/` 这个目录」改成「`core/http.py` 这一个模块」，
并新增 `alphacouncil/core/http.py` 作为全项目唯一允许构造 HTTP 客户端的地方。**

```
providers/sources.py   ──build_client(user_agent=_BROWSER_UA)──▶  core/http.py
notify/webhook.py      ──build_client(user_agent=_WEBHOOK_UA)──▶  core/http.py
```

`core/http.py` 只拥有**真的通用**的部分：超时、`follow_redirects`、连接复用，
以及 ⭐ **要求调用方显式给出 `User-Agent`**。

**它不拥有缓存、熔断、抖动。** 那三样留在行情路径里，因为对 webhook 它们要么不适用、
要么有害 —— ⭐ **通知必须每条都送到，一个「省下一次重复投递」的缓存是在制造静默失败。**

### 理由

**1. ⭐ 这是把规则改紧，不是改松 —— 而且这一点是可数的。**

| | 允许构造客户端的**文件集合** |
|---|---|
| 改前 | `providers/` 下的**每一个** `.py`（今天 4 个，将来更多） |
| 改后 | **1 个**（`core/http.py`） |

`sources.py` 自己构造客户端这件事，改后**不再被允许** —— 它必须调工厂。
⭐ 规则的口子是缩小到原来的一个文件，不是扩大到第二个目录。

**2. ⭐ 一份 UA 不能两边共用，所以「一个入口」不能是「一个 client」。**

`spec 033 §2` 要求把 TSP 的 `User-Agent: TickFlow-Webhook/1.0` 重新冠名 ——
⭐ **webhook 不该冒充浏览器**，而腾讯/新浪**必须**冒充浏览器（它们拒绝陌生 UA）。
把两者塞进一个带默认 UA 的工厂，等于让其中一个撒谎。

所以共享的是**「客户端在哪里被构造」这条规则**，不是**一个构造好的 client**。
这也是为什么 `build_client` 的 `user_agent` 是**必填**而不是带默认值 ——
⭐ 带默认值的那个默认值，迟早会在某一侧变成一句谎话。

**3. 目录白名单是一种无法解释的授权。**

`providers/` 得到豁免的理由是「行情在那里」，于是**目录里将来长出的任何东西**都自动获得
直连 HTTP 的资格 —— 包括一个通知模块、一个同步任务、一个报表。⭐
**目录不是理由，模块才是。** 而 `core/http.py` 得到许可的理由可以被一句话说清：
「因为客户端只该在这里被构造」。

**4. ⭐ webhook 需要的是 §7.8 的一个子集，而说清是哪一个，比假装它需要全部更有用。**

| §7.8 的机制 | webhook | 行情 |
|---|---|---|
| 超时 / 连接复用 | 要 | 要 |
| 最小间隔 + 抖动 | 要（飞书等有 QPS 限） | 要 |
| 默认 UA | ⭐ **要，但必须是诚实的 UA** | 要（且必须**不**诚实） |
| 熔断 | 要，但语义不同（通道坏了 ≠ 数据陈旧） | 要 |
| 缓存 | ⭐ **不要 —— 有害** | 要 |

⭐ 最后一格是这次调查最值钱的一格：**如果当初没有把 webhook 塞进行情层，
就不会有人试图让通知继承数据缓存。** 那个继承一旦写进去，几乎不可能被审出来 ——
它长得太像「复用了已有的好机制」。

### 被拒绝的方案

| | 方案 | 为什么拒绝 |
|---|---|---|
| ❌ | 给 S-01 加 `notify/` 目录白名单（`spec 033` 的 A） | ⭐ P0 规则新增例外，理由是「我需要一个 HTTP 客户端」—— 不足以服人；且它把**目录**继续当成理由 |
| ❌ | webhook 走 `default_router()`，加一个 `Dataset` 成员 | 让行情抽象承担它不理解的东西；且加 `Dataset` 成员会打破两个断言**精确集合**的既有测试 |
| ❌ | 不做 webhook 通道（`spec 033` 的 C） | 少一个渠道可以接受，但**代价是这道架构问题被绕开而不是被回答** —— 下一次需要 HTTP 的东西会再撞一次 |
| ❌ | 一个带默认 UA 的共享工厂 | ⭐ 会让 webhook 冒充浏览器，或让行情用诚实 UA 然后被拒 |
| ❌ | 保持目录白名单，只加一个 P0 豁免 | 豁免理由不可复核；而**改紧**的版本是可复核的 |

### 后果

- **S-01 的三条规则全部保留**，判据从目录换成模块；`CONVENIENCE_CALLS` 仍是全项目 error
- ⭐ **`sources.py` 里那 3 行客户端构造被移走** —— 那是本次唯一的产品代码删除
- ⭐ 允许构造客户端的文件从 4 个降到 1 个，而**这个数字以后可以被测试断言**
- 代价：`core/http.py` 成为关键路径上的公共依赖，它坏了两个通道一起坏
- ⭐ 记录了一条**限制**：本 ADR 只回答「HTTP 客户端在哪里构造」。
  **webhook 的熔断语义、幂等键、重试策略仍未定义**，那是下一个 spec 的事，
  **不在这里假装已经解决** |

## ADR-0032 · ⭐ 待裁决：知识库的编辑器是不是所见即所得（Milkdown 接不接）

**日期**：2026-09-30 · **状态**：⭐ **待裁决（等主人）** · **关联 spec**：026（知识库）· 045（前端打磨）· **被谁挡住**：`HANDOFF.md` 明确「优先体验，主人反馈，再迭代，不能投入过多时间」

### 背景

`@milkdown/core` · `@milkdown/react` · `@milkdown/preset-commonmark` 三个包
**自 2026-09-28 起就在 `dependencies` 里**，是主人本轮批准的（spec 026 §3），
许可实测 MIT，V-07 的允许清单里也有它们并注明「装好未接」。

⭐ **而截至 2026-09-30，没有一个源文件 import 它们。** 构建出货 **0 字节**。

⭐ **这个决定此前没有成本数字。** spec 026 记下的不接线理由是
「所见即所得要保证书写体验和**阅读**体验同颜色」⭐ —— ⭐ **而那个前提上轮已经
不成立了**：笔记正文现在用自写的 `Markdown` 渲染 ⭐，两侧都是渲染后的文字 ⭐，
「同颜色」已经做到。⭐ 剩下的理由只有两条：「未经验证的所见即所得编辑器可能比
纯文本更糟」⭐ 与「不能投入过多时间」⭐ —— ⭐ 两条都不是「不接」，
两条都是「先量一量再决定」。

### 决定

⭐ **本 ADR 不做决定。** ⭐ 它记录**量出来的成本** ⭐ 与**一个此前无人提的障碍** ⭐，
⭐ 把选择权交回给主人。⭐ 已落地的部分只有一件：**把「已批准但没调用方」变成门禁**
（`styleguide.test.ts` 的 **V-16**）⭐ —— ⭐ 现状是唯一无法辩护的第三种状态。

### 量出来的成本（Vite 实测，2026-09-30）

| | JS | gzip |
|---|---|---|
| 基线（无 Milkdown） | 535.36 kB | 164.55 kB |
| 接上 Milkdown（`useEditor` + `Milkdown` + `commonmark`） | 898.18 kB | 275.14 kB |
| **差** | **+362.82 kB** | **+110.59 kB** |

⭐ 也就是 **JS 涨 68%** ⭐ 且 **gzip 涨 67%** ⭐ —— ⭐ 为了**一个面板**里的一个编辑器。

⭐ **第二个数字比第一个更要紧，而且此前没有人提过：**
⭐ **已批准的那三个包单独凑不出「编辑器吐出 markdown」。**
⭐ 这是从装好的 `.d.ts` 里读出来的（`@milkdown/react@7.22.2`）⭐：

| 想做的事 | 住在哪个包 | 在 `package.json` 里吗 |
|---|---|---|
| 监听改动 `listenerCtx.markdownUpdated` | `@milkdown/plugin-listener` | ⭐ **否**（传递依赖） |
| 读出全文 `getMarkdown()` | `@milkdown/utils` | ⭐ **否**（传递依赖） |
| 序列化 `Serializer` | `@milkdown/transformer` | ⭐ **否**（传递依赖） |

⭐ **所以接上它的真实成本是「+363 kB」加「+一个没批准的包」** ⭐
⭐ 或者「手写一条 `editorStateCtx` 订阅」⭐ —— ⭐ 而后者是要花的时间，
⭐ 恰好是 `HANDOFF.md` 说不要多花的那个。

⭐ 附带记下两条**读 typings 才知道、猜不出来**的 API 事实
⭐ （第一版探针两处都写错了，`tsc` 抓的）：

* `useEditor` 收的是 **getter**（`(container: HTMLElement) => Editor | undefined`）⭐
  不是实例 ⭐，且 `Editor.create()` 是 **`Promise<Editor>`**。
* ⭐ **`rootCtx` 是 DOM 根节点，不是正文** ⭐ —— 它的类型是
  `RootType = Node | undefined | null | string` ⭐，那个 `string` 是 **CSS 选择器**。
  正文在 **`defaultValueCtx`**，DOM 节点在 `rootDOMCtx`。⭐ 两个名字挨着的 slice，
  两件事。

### 三个选项（等主人选）

1. ⭐ **接。** 删掉 V-16 的豁免，真接上，接受 +363 kB，并**批准第四个包**
   （`@milkdown/plugin-listener` 最省事，MIT）。⚠️ 代价写在上面。
2. ⭐ **不接，删掉三个包。** 保留 textarea + 实时预览（现在就有），
   从 `package.json` 和 V-07 允许清单里移除。⭐ 收益：**每次构建少装三个包**、
   许可扫描少三行、⭐ 而**出货字节数一模一样**（现在是 0）。
3. ⭐ **维持现状 + 门禁。** 就是现在这个提交的状态 ⭐ —— V-16 的豁免表里
   三个包各带一条**带数字的理由**（就是上面那张表）⭐，⭐ 空白理由或过期条目
   都是红测试。⭐ 好处：**决定每天在门禁输出里可见** ⭐ 而不是躺在文档里；
   ⭐ 代价：`npm ci` 仍然装它们。

⭐ **我倾向 2**，⭐ 但这是产品决定 ⭐ —— ⭐ 1 的前提是「书写体验值 363 kB」，
⭐ 而那是主人对「知识库的第一体验」的判断，不是我的。

### 后果与不变量

* ⭐ **V-16 与本决定无关，已经落地。** ⭐ 它对三个方向都成立：① 声明了没人 import 的
  （活的：Milkdown）② import 了没声明的（**目前 0 处** ⭐ —— 68 个源文件实测）
  ③ 豁免没有理由的（防止一个字符让测试变绿）。
* ⭐ **如果选 2，V-07 的允许清单要同步减三项** ⭐ —— ⭐ 允许清单与 `package.json`
  两处，少一处就是 V-07 自己报错。
* ⭐ **不变量**：编辑体验不是这一轮的验收项。⭐ `HANDOFF.md` 的原话是
  「不能投入过多时间」⭐ —— ⭐ 上面那张成本表就是那段时间该花在哪里的答案。

## ADR-0033 - 主人决定推翻「界面不做装饰」这条立身之本

**日期**：2026-09-30　**状态**：**已采纳 · 待实施**
**推翻**：spec 045 §5.2 · §5.3 · §6 · 宪法 §3.2.1 · **V-06 两条断言** · **V-07 批准清单**

### 决定

主人在产品评估后明确说：「**我决定违反项目宪法，以我的意志为准，我要一个高级的
充满美学的产品**」。

因此本项目**不再**遵守以下四条，它们是仓库自己的立身之本：

| 原本的规则 | 出处 | 现在 |
|---|---|---|
| **禁止 `@keyframes` 语法本身存在** | `V-06` 第一条断言 | **推翻** |
| **任何组件里不许有 `animate-*` / `duration-*`** | `V-06` 第二条断言 | **推翻** |
| 六条动效禁令（入场动画 / shimmer / count-up / 弹跳过冲 / 视差粒子 / 图表入场） | 规范 §7.2 | **推翻** |
| 「界面是产品，不是 Landing Page」/ 禁止插画 | 规范 §5.2 | **推翻** |
| 依赖批准清单不含动效库 | 宪法 §3.2.1 · `V-07` | **推翻**，按需批准 |

### 代价：必须在实施前承认，不是事后追认

`V-06` 第一条断言的注释写着它为什么写成语法级：

> Stronger than grepping for `animate-` or `transition`: **if the stylesheet
> defines no `@keyframes` at all, then shimmer, count-up, fade-in-up and
> slide-in are all impossible by construction rather than by review.**

**那不是一条检查，那是把一整类效果变成不可表示。** 推翻它的代价不是「少一道门禁」，
而是这一类效果重新变成可能，而唯一的拦截点从**构造**退化成 **review** —— 而这个仓的
全部价值主张就是「不靠 review，靠构造」。

另另一条代价在产品层面，不在工程层面：

> **数字滚动是最危险的一条**：把「看数据」变成「看表演」，**且暗示收益**。

本产品首页写的是「**只优化过程，不预测涨跌**」。界面动效一旦进入「吸引注意」这个方向，
产品就在用界面做它自己红线第 1 条禁止的事。我作为执行者记录这一点，但主人已经裁决，
**我不因此停下**。

### 为什么仍然记录这条

因为「谁在什么时候、基于什么理由推翻了哪条规则」**必须可追溯**。如果这次推翻只存在于
commit message 里，六个月后 `V-06` 会变成「新增的动效断言」而不是「一次被记录的决定」，
下一个读代码的人会以为它一直是这样。

**一个不可追溯的推翻，比一条错误的规则更糟** —— 前者会让整份文档失去可信度，后者只是
要改回来。

### 实施要求（由本 ADR 产生，不是可选项）

1. `V-06` 两条断言改写为**仍然有牙齿的新形式**，**不是删掉**：改成「每一处动效必须声明
   `prefers-reduced-motion`」「动效不得作用于数据本身」。这样违反者仍被拦住，允许的范围
   变宽。
2. `V-07` 批准清单**逐名增补**，每个新包写明为什么。
3. 宪法 §3.2.1 的「明确不装」列表同步 —— 否则又是一个引用指向已消失的规则。
