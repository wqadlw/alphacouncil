## spec 060 · 记录能不能被相信

**这一轮一开始不是「加功能」。** 上一轮留了一个问题：那 4 条决策里只有 1 条是真的，
而没人能区分。先量「界面要怎么才能分出来」，⭐ 发现**库里没有任何东西能让人分出来** ——
唯一可空的列 `thesis_id` 语义是「这条决策服务的论点」(J2)，借它是对这一列说谎，
而且它长在决策行上，用它就要改已有行 ⇒ **违反只增不改，出局。**

然后量出了两件比那个问题更要紧的事。

### 一、今日页 100% 是测试噪音

实测 `GET /today` → `attention` **4 条**，真决策的条目 **0**。其中一条还对读者说
「**已越过** — MA20 现在 1291.80」，关于一条他从没打算过的判据。⭐ 而他唯一那条真决策
`as_of 2026-12-31` 未到期，⭐⭐ **所以整屏看不见他真正写的东西。**

顺带：第四条判据是 `gross_margin` — ⭐⭐ **就是 spec 058 刚从界面里删掉的那个 token。**

### 二、⭐⭐ 4 行孤儿：记录里指向不存在的决策

`decision_review_state` 的 4 行，`decision_id` 在 `decisions` 里 **0 命中**。三个候选
解释，⭐ 量掉了两个：

| 解释 | 量到的 |
|---|---|
| 有东西删了决策 ⇒ 只增不改被破 | ❌ `grep 'DELETE FROM decisions'` **零命中** |
| 外键 DEFERRABLE，父行后出现 | ❌ 实测故意插坏数据被拒 ⇒ **这个连接上外键生效** |
| 某个连接以 `foreign_keys = OFF` 打开 | ⭐ **实测裸 `sqlite3.connect()` 报 0** |

⇒ **只增不改是「谁打开了这个文件」的性质，不是这个文件的性质。**

⭐⭐ 而 `D-01` 的 docstring **早就把这个机制写对了** — 缺的是**第二个引用**：
`decisions → instruments` 有人守，`decision_review_state → decisions` **没有任何东西守。**

⭐⭐⭐ **而我照 `D-01` 那句话推理出的结论是错的** ⭐⭐⭐ — 它说 `connect_for_migration`
关着外键，实测是 **1**。⭐⭐⭐ **本会话第三次栽在同一个地方**（`cards.id` = `F-258` ·
`foreign_keys` 机制 = `D-01`）⇒ **本仓库自己的账本比我读代码得到的结论更完整，
⭐⭐ 而没读完的 docstring 不算证据。**

### 交付

| # | 东西 | 类型 |
|---|---|---|
| 1 | **`D-25 orphan-reference`** ⭐ 读 `pragma_foreign_key_list`，**17 表 21 条引用** | 数据检查 · **`warning`** |
| 2 | **`S-19 foreign-keys-not-off`** ⭐ `sqlite3.connect` / `sqlite3.Connection` 两种拼法，**类型标注不算** | 静态检查 · `error` |
| 3 | ⭐⭐⭐ **归属修复：一个根因，三个地方** | 运行器 |
| 4 | ⭐ 修 `D-01` 那句过期陈述 | 文档 |

⭐⭐⭐ **一个根因，三个地方**：四条数据规则共用 `CHECK_DATA_INTEGRITY`，而 `S-05` 要求
code 是**类别**，⭐⭐⭐ **所以 code 永远不可能认出一条规则** — ⭐⭐ 而我连着两处都去问了它：

- ⭐ `_write_human` ⭐ 字典推导取最后一个 ⇒ **门禁在 `[FAIL] D-22` 下面打印 `D-25` 的发现**
- ⭐ `_write_json` ⭐ 消费 `issues[]` 的人不知道哪条属于哪条规则
- ⭐ `rule_id_for` ⭐ ⇒ `# noqa: D-22` **会静默消掉 D-25 的发现**

⇒ **三处都删掉猜测，归属由「知道它的那一层」显式传下来。**

⭐⭐ **顺带一个只有改掉之后才看得见的顺序问题：** `_dedupe` **故意跨规则去重**，
而计数原本在去重之后 ⇒ **除第一条外的所有规则都报「clean」，明明它们都报了。**
⇒ **计数在去重之前取。**

### ⭐⭐⭐ `D-25` 为什么是 `warning`

⭐ **严重级别是量出来的，不是为了让门禁变绿。**

1. 两个工厂都强制外键 ⇒ **产品写不出孤儿**
2. 没有任何代码删决策 ⇒ **不可修**
3. `data.readonly()` 读的是**读者自己的库** ⇒ **这条规则永远不可能因为本仓库的缺陷而失败**

⇒ `error` 就是永远红，⭐⭐ **而一个永远红的门禁就是一个会被忽略的门禁**（⭐⭐ `D-01` 自己
`fix` 里警告的事）。⇒ **机制搬到 `S-19`，它关于代码，所以是 `error`。**
⭐⭐ D-25 告诉读者「你有 4 行指向不存在的决策」，⭐ S-19 保证产品不会写出第 5 行。

⭐⭐⭐ **D-25 是全仓库第一个 `warning`**（实测：没有任何其它规则构造 `Severity.WARNING`）
⇒ 运行器的 `[WARN ]` 分支在此之前是**不可达代码**。

## ⭐ 晚：从主人自己的 trace 里量出来的「知识层为什么是空的」

### ⭐⭐⭐ 先更正我自己和 `status.md`

**「trace 0 行」是错的，而且错在目录上。** trace 写的是
`%LOCALAPPDATA%\AlphaCouncil\traces`（`core/trace.py:146`），
⭐⭐⭐ 也就是**和数据库放在一起**；`.ai/traces/` 是仓库里的一个目录，
而它自己的 README 就写着那是「数据根 = 仓库根」时的默认。

实测：**30,530 条 · 9 天连续（09-27 → 10-05）· 0 条不可解析**。
⭐⭐⭐ 约束① 写的是「`.ai/traces/` ≥ 50 条」，**那个目录 0 条**，
⭐⭐⭐ **所以缺的是规范不是产品** —— 一条只能靠移动文件才能满足的约束，
⭐⭐⭐ 教会人错了事（我今天早上就照着它得出了错的结论）。

### 894 次读取是什么

| 量到 | |
|---|---|
| `GET /api/v1/notes` | **894** |
| 其中同一秒内的配对 | **35 对，间隔 7.7–15.7 ms** |
| ⇒ 真实挂载次数 | **≈ 447**（`StrictMode` 双调用，`main.tsx`） |
| 间隔 0.2–1 s 的相邻对 | **377** ⭐⭐⭐ **这是打字的形状** |

代码侧核对：`searchText` → **150ms 防抖** → `setQuery` → `[tag, query]` 是
`notes` 的 deps ⇒ **每一次打字停顿 = 一次 HTTP 往返。**
⭐ `tags` 的 deps 是 `[]`，**每次挂载取一次，不是每次按键** ——
⭐⭐ 这一条我先猜错了，查了才改口。

### ⭐⭐⭐⭐⭐ 于是那 894 次是什么

**它们是「我是不是已经写过这个」的查找。** ⭐⭐ 894 次查找，
**答案每一次都是一张空表；真实库 `notes 0` 行。**
⭐⭐⭐⭐⭐ **而一次写入都没有。**

⭐⭐⭐⭐ **⇒ 成本不在「记录」上，在「记录之前」。** ⭐⭐⭐⭐
读者做的第一件事是搜（对的直觉），⭐⭐⭐ 搜了 894 次，
⭐⭐⭐⭐⭐ **而每一次的结果都是「你什么都没记过」。** ⭐⭐⭐⭐⭐

### 顺带量到的三条

1. ⭐⭐ **`trace` 记录只有 4 个键**（`id` / `kind` / `name` / `started_at`），
   ⭐⭐ **没有状态、没有耗时、没有结果** ⇒ ⭐⭐⭐ **它连「这次查询返回了几行」都不知道。**
   ⭐⭐⭐⭐⭐ **⇒ 一个把「约束② = 用程序自己的记录验证」写进验收标准的程序，
   ⭐⭐⭐⭐⭐ 只能记录「来过」，记录不了「做了什么」。**
2. ⭐⭐ **`token_count` / `cost_usd` 两个字段存在，15,459 条 observation 里 0 条有值。**
   ⭐⭐⭐ `status.md` 说约束① 第三项「无法诚实达成」，**这个判词是对的** ——
   ⭐⭐⭐ **但理由该换：不是「没有 agent 所以没法记录」，⭐⭐⭐ 是「没有 agent 所以没有东西可记」。**
   ⭐⭐⭐⭐⭐ **仪表已经装好，在等一个被观测的东西。**
3. ⭐⭐ **15,071 条请求里 11,712 条不是产品**（`/health` 5,865 + `/v1/models` 5,847，
   ⭐⭐ 某个第三方客户端在轮询 OpenAI 兼容端点）⇒ **「9 天使用」混着大量非产品流量。**
