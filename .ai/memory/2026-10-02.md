# 2026-10-02 · spec 048：先量空库，再决定补什么

## 主人说「继续优化」，我这一段做的是同一件事：先量

上一段（spec 047）量的是「哪些能力存在而读者够不着」，量出一个死结。
这一段量的是**一个全新用户打开看到什么** —— 因为 `status.md` 的 T0 那行写着
「全新用户打开屏幕上是**五个空页面**」，而**那句话挂了很久，从来没人验证过它是否准确**。

### 量出来的第一件事：那句话不准确

对着一个**空数据库**（`ALPHACOUNCIL_DATABASE_PATH` 指到临时目录、8011 端口）
把十三个列表端点挨个打了一遍 —— **全部 `[]`**。
然后浏览器里把五页挨个截图，量每页正文字数：

| 页面 | 字数 | 空态 |
|---|---|---|
| 今日 | 360 | 合格 |
| 关注池 | 267 | 合格 |
| 知识库 | 178 | 合格 |
| **复盘** | **74** | 不合格 |
| **复习** | **62** | 不合格 |

**三个合格、两个不合格。** 不合格的那两个只说了「**为什么这个队列是空的**」，
而对新读者来说队列空的原因是**上游根本没有东西可排** —— 它们从没说过这件事。

### 量出来的第二件事，比第一件要紧得多

`status.md` K3 挂着「还差：标的页卡片的『加入复习』」。对着机器量：

```
POST /api/v1/cards                 -> 201
GET  /api/v1/review/due            -> 0 条    ← 服务端不主动贡献任何东西
POST /api/v1/cards/{id}/schedule   -> 201
GET  /api/v1/review/due            -> 1 条
grep scheduleCard                  -> api.ts:282 定义，调用者 0 个
```

**⇒ 卡片只能靠写代码进复习队列。这个视图对每一个用户都是空的。**

⚠️ 而**缺的不止是按钮** —— `GET` 端点当时**根本不存在**，
界面既不知道一张卡在不在队列里，**也不能从 `/review/due` 推断**（它只给到期的）。
⇒ 「加入复习」如果只能靠点完才知道结果，**它就是一个赌注**。

⚠️ **笔记不是这样**：`VaultPage` 有 `enrollNote` 且配了理由。
**同一个后端形状，卡片这边只有一半。**

⇒ **「零首次体验」的真正问题不在文案，在于一个空队列和一个进不去的队列。**
我上一段说「五个空页面」，那句话本身就太粗了。

## 三态，不是布尔 —— 而这一条是从笔记那个错的地方学来的

`VaultPage` 的笔记入队读状态是 `.catch(() => false)`：
**任何失败都读成「未入队」**，于是后端一停，读者看到的是一个**点了必然失败的按钮**。

卡片这边按 `error.code === 'CARD_NOT_SCHEDULED'` 判断，于是有第三态：

| 显示 | 含义 |
|---|---|
| 「复习状态取不到。」**不给按钮** | **不知道** |
| 「加入复习」+「到时会自己回来。」 | 确定没入队 |
| 「已加入复习 · 下次 …」 | 确定在队列里 |

⚠️ **笔记那条本轮没改**（属 spec 028 的地盘），已记为欠账。

## ⚠️ 我差点推翻一条项目早就做好的决定

`GET /notes/{id}/schedule` 未入队时答 **404**。我本来要照抄。
然后读到 `api/errors.py` 里已经写着理由：

```python
# K3. Both are 409 rather than 404 on purpose: the *card* exists, and what
# conflicts is the request with the card's scheduling state. Answering 404
# would tell the user their card is gone when it is sitting right there.
```

⇒ **照抄笔记会推翻一条写明理由的决定。** 用 409。
⇒ 而它**也是三态成立的原因**：409「不在队列」（正常的空，该给按钮）
vs 404「这张卡不存在」（另一个问题，按钮不该替它遮）。

## 这一段我犯的四个错，都记进了台账

1. **第三次猜字段名**（`content` 不是 `claim`，拿到 422）。
   ⚠️ 「读模型再发请求」应该是探针的第一条规矩，而不是被坑三次才补。
2. **探针的转发层两次让产品看起来有错** ——
   对所有方法都用 `get()` 转发（POST 被用读的回答答了），
   以及 abort 路由写在通用路由之后被守归零。
   ⚠️ **后者正是 `F-198` 在探针里重演一次。**
3. **照抄文档时连续两次写错字符串** ⇒ 第三版先把那段逐字节验证过再改。
4. **一条测试因为「它经过」而永远变绿** —— 「已收敛不给按钮」那条没 stub 读请求，
   所以按钮不出现的原因与「已收敛」无关，**变异 M3 因此没红**。
   ⇒ **本会话第二次「少了一个 stub 所以永远变绿」**（上一次 `0012`）。

## 附：主人的真实库今天被动过吗 —— 动了字节，没动记录

上一段（`F-196`）我用探针往主人真库里写了一行。早上第一件事是查这个。

```
alphacouncil.db   774144 -> 778240 bytes   （+4096，正好一页）
LastWriteTime     2026-10-02 12:48
```

⚠️ **字节变了不等于记录变了。** `migrate.apply()` 每次启动都跑，
而它会做一次 `VACUUM INTO` 快照 —— **一页的增量正是迁移快照的形状。**
所以去看内容：

```
watchlist_current  1 行  sh/600036  「ROE 长期 15%+，零售银行护城河…」
600036 history     1 条，last id 6
/today attention   4      due cards=0 reviews=0
cards 0 · notes 0 · lessons 0 · decisions 5
```

**与今天动手之前的基线逐项相同。**

⇒ 本轮所有写探针都跑在 **8011 + 临时库**上，脚本第一行打印两个库路径不同作为凭据
（这就是 `F-196` 那条规则的样子）。**而这一条查询本身只有 GET** ——
读不会写（trace 写的是旁边的 `traces/`，不写进库）。

⭐ **「字节变了」是一个很容易被当成事故的信号，而这一次的正确反应是先问「变了什么」。**
