## 主人说「继续优化」，我这一段做的是同一件事：先量

上一段（spec 047）量的是「哪些能力存在而读者够不着」，量出一个死结。
这一段量的是**一个全新用户打开看到什么** —— 因为 `status.md` 的 T0 那行写着
「全新用户打开屏幕上是**五个空页面**」，而**那句话挂了很久，从来没人验证过它是否准确**。

### 量出来的第一件事：那句话不准确

对着一个**空数据库**（`ALPHACOUNCIL_DATABASE_PATH` 指到临时目录、8011 端口）
把十三个列表端点挨个打了一遍 —— **全部 `[]`**。
然后浏览器里把五页挨个截图，量每页正文字数：

| 页面 | 字数 | 空态 |
|---|---|---|
| 今日 | 360 | 合格 |
| 关注池 | 267 | 合格 |
| 知识库 | 178 | 合格 |
| **复盘** | **74** | 不合格 |
| **复习** | **62** | 不合格 |

**三个合格、两个不合格。** 不合格的那两个只说了「**为什么这个队列是空的**」，
而对新读者来说队列空的原因是**上游根本没有东西可排** —— 它们从没说过这件事。

### 量出来的第二件事，比第一件要紧得多

`status.md` K3 挂着「还差：标的页卡片的『加入复习』」。对着机器量：

```
POST /api/v1/cards                 -> 201
GET  /api/v1/review/due            -> 0 条    ← 服务端不主动贡献任何东西
POST /api/v1/cards/{id}/schedule   -> 201
GET  /api/v1/review/due            -> 1 条
grep scheduleCard                  -> api.ts:282 定义，调用者 0 个
```

**⇒ 卡片只能靠写代码进复习队列。这个视图对每一个用户都是空的。**

⚠️ 而**缺的不止是按钮** —— `GET` 端点当时**根本不存在**，
界面既不知道一张卡在不在队列里，**也不能从 `/review/due` 推断**（它只给到期的）。
⇒ 「加入复习」如果只能靠点完才知道结果，**它就是一个赌注**。

⚠️ **笔记不是这样**：`VaultPage` 有 `enrollNote` 且配了理由。
**同一个后端形状，卡片这边只有一半。**

⇒ **「零首次体验」的真正问题不在文案，在于一个空队列和一个进不去的队列。**
我上一段说「五个空页面」，那句话本身就太粗了。

## 三态，不是布尔 —— 而这一条是从笔记那个错的地方学来的

`VaultPage` 的笔记入队读状态是 `.catch(() => false)`：
**任何失败都读成「未入队」**，于是后端一停，读者看到的是一个**点了必然失败的按钮**。

卡片这边按 `error.code === 'CARD_NOT_SCHEDULED'` 判断，于是有第三态：

| 显示 | 含义 |
|---|---|
| 「复习状态取不到。」**不给按钮** | **不知道** |
| 「加入复习」+「到时会自己回来。」 | 确定没入队 |
| 「已加入复习 · 下次 …」 | 确定在队列里 |

⚠️ **笔记那条本轮没改**（属 spec 028 的地盘），已记为欠账。

## ⚠️ 我差点推翻一条项目早就做好的决定

`GET /notes/{id}/schedule` 未入队时答 **404**。我本来要照抄。
然后读到 `api/errors.py` 里已经写着理由：

```python
# K3. Both are 409 rather than 404 on purpose: the *card* exists, and what
# conflicts is the request with the card's scheduling state. Answering 404
# would tell the user their card is gone when it is sitting right there.
```

⇒ **照抄笔记会推翻一条写明理由的决定。** 用 409。
⇒ 而它**也是三态成立的原因**：409「不在队列」（正常的空，该给按钮）
vs 404「这张卡不存在」（另一个问题，按钮不该替它遮）。

## 一、外部调研：四条路，三条被否决

问题具体化之后是：**前端手写着后端的枚举类型，怎么保证它不漂？**

| 方案 | 结论 |
|---|---|
| **OpenAPI codegen**（`openapi-typescript`，8.4k star） | ⛔ 要加依赖，而 `V-07` 的预算是 8 个已批包 + 3 个 milkdown，宪法 §3.2.1 要求经主人批准。⭐ **而且它会推翻 `api.ts` 1074 行的写法** —— 那份文件的价值一半在注释里 |
| **Pact 契约测试** | ⛔ 要 broker + 契约文件。**单仓单人项目上是过重的**，而且契约文件本身成了第三个要同步的地方 |
| **静态对拍：前端调用点 × 后端路由声明**（`tieline`） | ⛔ **可行但下一轮** —— 就是我前两段手搓了四次、错了三次的那件事 |
| **拿 `openapi.json` 比对手写副本** | ✅ **FastAPI 本来就吐 `openapi.json`，零依赖**，而且与本仓 `S-05`（文档↔枚举↔代码）是同一个惯用法 |

⭐ **调研最值得记的一条观察：行业里没人说「让前端手写类型」是错的 —— 错的是
「手写而没有对照」。** 所有四个方案做的都是同一件事：**在两侧之间放一个机器可读的
中间物，让差异无法悄悄存在。** 而本仓缺的正是那个中间物的**使用** ——
它一直存在（`openapi.json`，30 个枚举），只是没人在读它。

### `tieline` 有一条设计值得抄：三个桶不是一个

```
✅ 274 matched   ❌ 2 drift   ⚠️ 6 unverifiable   🟡 31 unused backend routes
```

⭐ **「后端有路由而前端没人调」与「前端调了后端没有的路由」不是同一件事** ——
前者是合法状态（health、通知 CLI、schema 端点），后者是 bug。
**混在一个桶里，要么天天红，要么被加白名单。**（S-17 要照这个来。）

## 三、`S-16`：24 个手抄枚举，零守卫

**实测基线（这是全部的发现）：**

```
openapi.json 发布 30 个枚举
其中 24 个在前端有一份手写镜像
24 个当前全部精确相符          <- 今天没有活的类型漂移
而后端加一个值时，没有任何东西会红
```

**双向都报**：后端有前端没有 → 值落进 `switch` 的 `default`，**静默**；
前端有后端没有 → 客户端等一个永远不会到的值，**那一支是死代码且看起来是对的**。

⭐ **设计里最容易做错的一处**（写在 spec §2.4，也值得抄进日志）：
**后端加一个枚举值往往是对的。** 所以这条门禁是一条**提示两侧的信息**，
不是要求前端服从后端 —— 而**豁免机制正是让「前端确实不需要这个值」成为一个可声明
答案**的东西。没有豁免，它会在第一次「后端加了个前端用不上的值」时被加白名单，
而那正是 `0012` 的形状。

⚠️ **豁免的理由必须写「它是什么」，不许写「不适用」**：一句无法被反驳的理由不是理由，
而这个文件半年后会被一个需要反驳它的人读。

### ⭐ 三张豁免表，三个不同的键 —— 这是本轮最贵的一课

| 表 | 匹配键 | 「还在吗」问的是 |
|---|---|---|
| `NOT_MIRRORED` | 后端枚举的**名字** | 后端还在发布吗 |
| `FRONTEND_ONLY` | 前端联合类型的**值集合** | 前端那个联合类型还在吗 |
| `SAME_VALUES_DIFFERENT_MEANING` | 前端联合类型的**名字** | 同上 |

第一版全塞进一张表，⭐ **一次干净的树上跑出 6 条「已豁免但不再声明」** ——
因为一个前端从不镜像的后端枚举**永远不可能有联合类型可找**。规则没判断错任何东西，
**是它自己的数据模型错了**，而输出把这件事说得足够响，形状一眼可见（`F-203` `F-204`）。
