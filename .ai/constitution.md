## 第零条 · 优先级与读法

### 0.1 冲突裁决顺序

冲突时，**按以下顺序裁决**（上位优先）：

```
产品红线（第一条）
  ↑
工程红线（本文件其余条款）
  ↑
技术栈锁定（第三条）
  ↑
代码规范 / 风格（第七条）
```

**"风格问题"永远不能升级为"红线问题"。** 审查者不得因为个人偏好把风格问题标为 P0/P1。

### 0.2 ⭐⭐ 从「纪律」到「机制」的四个层次（本宪法最重要的方法论）

> 同一个规则，可以放在四个不同的地方。**放的位置决定了它有多难被违反。**

| 层 | 载体 | 违反的代价 |
|---|---|---|
| **① 文档** | 本宪法里的一句话 | **没有代价**（靠自觉） |
| **② 检查** | 测试 / 检查脚本（事后发现） | 需要有人跑、有人看 |
| **③ 类型 / 编译期** | `satisfies never` · 两个不同的类型 · 签名强制传参 | **编译不过** |
| **④ 数据库 / 运行时** | CHECK 约束 · `RAISE(ABORT)` 触发器 · 唯一入口函数 · 状态机 | **运行直接失败** |

**结论**：
> **一条规则如果只存在于第 ① 层，它迟早会被违反 —— 不是因为有人故意，而是因为没人记得。**
> **判据：能不能把这条规则从 ① 移到 ③ 或 ④？能移就必须移。**

**本宪法中最该升级的 6 条**：

| 规则 | 现在 | 必须升到 | 对应条款 |
|---|---|---|---|
| **只增不改**（红线 4） | ① 文档 | **④ 触发器** | 5.4 |
| **决策必填字段**（理由 + 反面证据） | ① 文档 | **④ CHECK + ③ 类型** | 4.2 · 5.4 |
| **未成熟结果留空**（红线 6） | ① 文档 | **④ CHECK**（`outcome IS NULL` ⇒ `result_score IS NULL`） | 5.4 |
| **金额必须带币种** | ① 文档 | **③ 类型 + ④ CHECK** | 4.2 |
| **外部调用走唯一入口** | ① 文档 | **④ 唯一入口 + ② 静态检查** | 7.8 · `.ai/checks/static/` |
| **状态用枚举不用布尔** | ① 文档 | **③ 类型 + ② 静态检查** | 7.7 · `.ai/checks/static/` |

**新增规则时，必须写明它落在第几层。只写第 ① 层的新规则，审查时应当被质疑。**

## 第一条 · 产品红线（15 条，不可交易）

> **为什么产品红线要写进工程宪法**：这些不是"产品设计建议"，是**代码必须守住的不变量**。
> 例如红线 6（未成熟结果留空）如果只在产品文档里写，代码里就会出现 `result_score = 0`。
> **每一条都必须在实现层面有对应的强制手段。**

| # | 红线 | 实现层面的强制手段 |
|---|---|---|
| 1 | **不做预测增强**（不给速成答案） | 禁止出现"目标价 / 涨跌预测 / 买卖建议"字段与接口 |
| 2 | **只做过程优化，不优化预测** | 所有评分字段只描述"决策过程"，不描述"结果好坏" |
| 3 | **记录优先于分析** | 任何"分析"功能都必须以已存在的记录为输入 |
| 4 | **结果之前记录** | 决策记录主键 = 记录时刻的时间戳，**服务端生成，API 不接受客户端传入** |
| 5 | **过程分与结果分独立** | 两张表 / 两组字段，**不得合并为单一评分** |
| 6 | **未成熟结果留空（绝不填 0）** | 字段可空，**数据库层禁止默认值 0**；统计时显式排除 NULL |
| 7 | **教训必须能再次遇到** | 每条教训必须生成一条调度项（FSRS） |
| 8 | **功能是「拦截」不是「推荐」** | 禁止"机会推送 / 每日精选 / 异动提醒"类功能 |
| 9 | **不展示「成绩」，可以展示「事实」** | ❌ 收益率排行 / "跑赢大盘 X%" / 成就徽章 / 连续打卡；✅ 涨跌 / 估值 / 财务 / 浮盈亏 |
| 10 | **必须让用户面对不舒服的数据** | 不美化、不打折；"坏决策+好结果"时**不显示盈利数字** |
| 11 | **不鼓励频繁操作** | 禁止任何促使用户"动起来"的设计；**"写下回答花了多久"只用于自省，不做排名/打卡** |
| 12 | **必须显示「时间的成本」** | 止损触发时显示"恢复所需年数" |
| 13 | **不讨好用户**（不在用户做错事时发糖） | 满意度 / 使用时长 / 愉悦感**不是**目标函数 |
| 14 | **日常体验要顺，关键时刻才拦** | 禁止把产品做成惩罚工具（防守型红线，防止把"对抗性"推成"惩罚性"） |
| 15 | **Agent 只做抽取与核算，不做判断生成** | 见**第六条**（工具权限四档，代码层面保证） |

**红线 15 的核心**：
> **所有 agent 输出必须可追溯到来源（页码 / URL / 原文片段）或可复现计算；否则不得写入数据库。**

## 第二条 · Agent 协作规约

> **来源**：`references/deep-dives/01-wealthfolio.md`（借鉴 `wealthfolio/AGENTS.md`）+ `02-anki.md`（借鉴 `anki/CLAUDE.md`）
> **为什么需要**：项目由 agent 全程开发。没有这一条，agent 会过度设计、造重复轮子、顺手重构、把"能跑"当"通过"。

### 2.1 六条工作约定（强制）

| # | 约定 | 说明 |
|---|---|---|
| 1 | **常规实现选择从邻近代码推断** | 只在**模糊会改变范围 / 公开行为 / 数据兼容性 / 不可逆操作**时才提问。**其余不要问，直接做** |
| 2 | **最小可读改动** | 避免投机性功能与抽象。**不写"以后可能用得上"的代码** |
| 3 | **先复用，再加基础设施** | 动手前先追踪既有的 service / event / queue / 错误处理。**优先扩展它们** |
| 4 | ⭐ **新增机制必须自证必要** | 见 2.2 |
| 5 | **匹配既有风格** | **不重构无关代码，不重排相邻文件**。只清理因本次改动而变为未使用的 import / 变量 / 函数 |
| 6 | **保留他人改动；发现问题只报告，不擅自修** | 发现无关问题 → 写进台账，不改代码 |

### 2.2 ⭐ 新增机制的门槛（本宪法最强的一条）

> **在新增「迁移 / 持久化状态 / 后台任务 / 重试机制 / 同步原语」之前，必须说明：**
> **① 它防止的「具体故障」是什么（不是"为了健壮性"）**
> **② 为什么既有机制处理不了这个故障**
> **③ 它是「必需行为」还是「可选弹性」—— 未获同意不得添加可选弹性**

**没有回答这三条的 PR，一律退回。**

### 2.3 单一命令入口与「完成」的定义

- **所有命令必须定义在 `Makefile` 里。** Agent **不得**直接调用 `pytest` / `ruff` / `mypy` / 裸脚本 —— 一律走 `make <target>`。
  - 理由：命令是**接口**。绕过接口 = 绕过了所有人在用的那条路径。
- ⭐ **「完成」的定义 = `make check` 通过。** 不是"我写完了"，不是"能跑起来"。
- **不得用"能跑起来"代替"构建通过"。**

### 2.4 不虚构（对应 v1 红线 6，提升为独立条款）

- **未运行的验证，必须明确标注"未验证"。** 不得暗示已通过。
- **被阻塞或未执行的检查，必须报告并说明原因。**
- **"没有发现回归" ≠ "报告的 bug 已修复"。** 缺少根因证据时，结论必须是 **「修复未经验证」**。
- **区分三件事**：已确认的事实 / 假设 / 未验证的行为。

### 3.2 新增依赖的流程

## 第四条 · 数据契约（强制）

> **来源**：`references/deep-dives/02-anki.md`（anki 用正负号编码单位 = 反面教材）+ TSP 借鉴笔记
> **背景**：TSP 的铁律 —— **"金融数据错误经常不会报异常，但会生成看似合理的错误结果。"**

### 4.1 四类不可混用的口径

| # | 口径 | 必须显式区分 | 反例（禁止） |
|---|---|---|---|
| 1 | **百分比** | 小数制（`0.05`）vs 百分数制（`5`） | 用一个 `float` 装两种含义 |
| 2 | **复权** | 前复权 / 后复权 / 不复权 | 图上画前复权、算收益用不复权 |
| 3 | **日期** | 交易日 vs 自然日 vs 时区 | 用自然日算"N 个交易日后" |
| 4 | **股本** | 公告日**不晚于**目标交易日 | 用未来的股本算历史换手率 |

### 4.2 强制手段

- **用 Pydantic 模型强制，而不是靠注释。** 目标：**让口径错误变成类型错误，在启动期就炸。**
  ```python
  class Price(BaseModel):
      value: Decimal
      adjust: Literal["none", "qfq", "hfq"]   # 复权口径不可省
  ```
- ⭐ **禁止启发式转换。** 明确禁止 `if value < 1: value *= 100` 这类"猜单位"的写法。
- ⭐ **一个字段只编码一件事。** **禁止**用正负号同时编码"数值"和"单位"（anki 的 `interval` 就是这么做的，**我们不学**）。
- **易错计算必须抽成独立函数 + 单元测试**（如涨停价、复权换算、估值分位）。

### 4.3 领域口径（A 股）

- **涨跌停分档**：主板 ±10% · 主板 ST ±5%（2026-07-06 前）· 创业板 300/301 与科创板 688/689 ±20% · 北交所 `.BJ` ±30%
- **注册制新股无涨跌幅窗口**：沪深主板 2023-02-17 起 5 个交易日 · 创业板 2020-08-24 起 5 日 · 科创板 2019-07-22 起 5 日 · 北交所 2021-11-15 起仅首日
- **涨停价必须用整数分运算**：`((cents * numerator + 50) // 100) / 100`
- ⚠️ **以上口径的完整定义与测试用例见对应 spec**，本宪法只声明"不可违反"。

### 4.4 PIT（Point-In-Time）财务

- 按**公告日**取最新，**公告前一律空值，绝不填 0**。
- 历史财务数据**不得被后续修订覆盖** —— 保留 `announced_at`，按 `announced_at <= as_of` 查询。

### 4.5 数据源纪律

- **三源互备**（腾讯 / 新浪 / 东财）+ **本地缓存优先** + **指数退避熔断** + **失败不静默**。
- 单一数据源不可靠（已实测：**东财连续请求触发限流**）。
- **错误必须分类**（借 wealthfolio）：`Never`（终局错误，立即停）· `FailoverWithPenalty`（限流/超时 → 换源 + 记账）· `NextProvider`（该区间无数据 → 换源不记账）· `CircuitOpen`（该源已熔断 → 跳过）。
- ⭐ **"限流"与"封 IP"是两件事，恢复策略不同**：限流降速即可恢复；封 IP 要等数小时或换网络。**必须分开记录与展示。**
- ⭐ **降级路径必须写"与主源的差异"**，不是"备胎能替代主源"（例："腾讯有前复权，新浪没有"）。**差异必须能被程序读到，而不只是写在文档里。**
- ⭐ **优先级按"封禁风险"排序，不按"数据丰富度"**（腾讯 → 交易所官方 → 新浪/巨潮 → 东财末位）。
- ⭐ **同一域名的不同子域风控面不同** —— "某站被封了"这个说法不准确，必须精确到子域。

### 4.6 ⭐⭐⭐ 数据四态（不是两态）

> **"确实没有数据"与"接口坏了"必须分开。** 前者是**业务结果**，后者是**系统故障**。
> 若混为一谈，产品会**安静地失效** —— 用户以为"数据没变"，实际是**取数已经坏了**，并基于错误前提做决策。

| 态 | 含义 | 用户看到 | 实现 |
|---|---|---|---|
| `ok` | 有数据 | 数据 | — |
| `no_data(reason)` | **确实没有** | "该区间无数据" + `reason` | 返回空 + 显式原因；**`reason` 必须能区分"源不覆盖"与"确实没有"** |
| `error(code)` | **取数失败** | 错误提示 + 错误码 | 抛错（`RuntimeError` 类），**绝不返回空表** |
| ⭐ `unavailable` | **存在但无法验证** | "存在，但我们无法确认" | 显式标记 |

**为什么需要第四态 `unavailable`**：它与 `no_data` 对用户的意义**完全不同** ——
`no_data` = "不存在"（用户不会想它）；**`unavailable` = "存在，但我们没法确认"（用户必须知道这里有个洞）**。

**禁止**：把"无法判断"降级成"看起来合理"的默认值。**返回空会被误读成"确实没有"，这是最危险的失败模式。**

**实现约束**：错误类型必须让"业务结果"与"系统故障"在**类型层面就不同**（如 `ValueError` vs `RuntimeError`），
**否则调用方会把"接口坏了"当成"确实没有数据"。** 参见 `.ai/error-codes.md`。

## 第五条 · 数据库与迁移纪律

> **来源**：`references/deep-dives/01-wealthfolio.md`（51 个迁移 + 21KB 验证报告）

### 5.1 迁移

| # | 规则 | 理由 |
|---|---|---|
| 1 | ⭐ **已发布的迁移永不编辑**，只追加新迁移 | 别人的库可能已经跑过它 |
| 2 | ⭐ **每个迁移必须可回滚**（有 `downgrade`）。确实不可逆时，必须显式声明并说明理由 | 用户装错版本要能退回 |
| 3 | ⭐ **执行迁移前先做已验证快照**：`VACUUM INTO` → 记录 SHA-256 → 界面显示"升级前的备份" | 迁移失败时用户还有救 |
| 4 | **迁移失败时**：保留快照路径 + 显示在错误详情里 + 提供"重试"按钮 | 不把用户困在坏掉的库里 |
| 5 | **每次重试生成一个新的唯一快照；已有快照字节级不变** | 可追溯 |
| 6 | ⚠️ **迁移连接必须用 `temp_store = FILE`** | wealthfolio 实测：`MEMORY` 下百万行 UPDATE 峰值分配 **2,046 MiB**，`FILE` 仅 76 MiB；`VACUUM` 峰值 **2,571 MiB** |
| 7 | **迁移期间 `synchronous = FULL`**（日常用 NORMAL） | 性能换安全 |
| 8 | **迁移期间显示"启动屏"而非冻结窗口**；**功能门控直到就绪** | 用户要知道系统在干什么 |

### 5.2 数据模型

| # | 规则 | 来源 |
|---|---|---|
| 9 | ⭐ **日志类表的主键 = 记录时刻的毫秒时间戳**，服务端生成 | anki `revlog`（`revlog/mod.rs:17-27`） |
| 10 | ⭐ **日志类表只追加，无 UPDATE / DELETE**；"改变想法" = 追加一条新记录 | anki `revlog` 语义 |
| 11 | ⭐ **日志记录必须带类型枚举，并提供"是否参与统计"的显式判定** | anki `revlog/mod.rs:65-76, 119-131` |
| 12 | **互斥状态用 discriminated union**（Pydantic `Field(discriminator=...)`），让"不可能的状态"解析期就被拒 | anki `scheduler.proto:124-127` |
| 13 | **"未成熟 / 不存在"用 NULL，不用 0** | anki `cards.proto:51` + 红线 6 |
| 14 | **临时改动必须保留原始值**，退出时恢复 | anki `odue` / `odid`（`schema11.sql:46-47`） |
| 15 | ⭐⭐⭐ **标的主键必须是 `(market, code)`，不是 `code`** —— `000001` 在沪市是上证指数、深市是平安银行（**代码→市场是一对多**） | `10-akshare.md` 决定 11 |
| 16 | ⭐⭐⭐ **禁止"从代码推断市场"作为唯一依据** —— 市场标识必须来自**显式输入或数据源返回**；推断**只能用于校验**（矛盾时抛错），**不能用于补全** | 同上 |
| 17 | ⭐⭐⭐ **财务数据必须存 `period_end`（报告期）+ `announced_at`（公告日）**；**行业/板块归属与指数成分必须存变更历史**（不是当前快照）；**没有历史时点数据时必须显式报错** | `10-akshare.md` 决定 12 |
| 18 | ⭐⭐⭐ **`decisions`（原始记录）与 `reviews`（复盘结论）物理分离**；**"是否已复盘"只有一个真源**（独立状态表，**绝不从 `reviews` 是否存在推断**） | `11-open-science.md` 决定 7 |
| 19 | ⭐⭐⭐ **`reviews.outcome` 允许 `failed` 为一等值** —— 禁止"失败但…"这类把亏损包装成收获的措辞 | 同上 |
| 20 | ⭐⭐⭐ **`thesis.md` 是 `thesis_versions` 表的渲染视图**（`old_text` / `new_text` / `because` / `valid_from` / `valid_to`）—— "what changed" **自动生成**，"这句话你说过 3 次"**才可查询** | `06-mem0.md` 决定 · `04-langfuse.md`（SCD-2） |

### 5.3 数据库位置

- ⚠️ **数据库不能放在 exe 旁边**（Program Files 不可写）。
- 一律放 `%LOCALAPPDATA%\AlphaCouncil\alphacouncil.db`。
- **单实例锁**：防止两个进程同时写库。
- **端口必须随机分配**（`bind(('127.0.0.1', 0))`），写死会冲突。

### 5.4 ⭐⭐⭐ 约束与触发器（把纪律变成机制 —— 对应第零条 0.2 的 ④ 层）

> **"只增不改"如果只写在文档里，代码写错了数据库不会拦。** 必须由数据库拦。

**5.4.1 append-only 用触发器强制**

对**所有日志类表**（决策日志 / 复盘 / 论点版本 / 审计）：

```sql
CREATE TRIGGER <table>_no_update BEFORE UPDATE ON <table>
BEGIN SELECT RAISE(ABORT, '<table> is append-only: 改变想法请追加新记录'); END;

CREATE TRIGGER <table>_no_delete BEFORE DELETE ON <table>
BEGIN SELECT RAISE(ABORT, '<table> is append-only: 记录不可删除'); END;
```

**违反时是数据库报错，不是代码评审时的提醒。**

**5.4.2 CHECK 约束覆盖五类，且外置成 JSON 清单**

约束**不散落在迁移脚本里**，而是集中在一份清单中（ORM 表达能力不足时尤其必要）：

| # | 类别 | 示例 |
|---|---|---|
| 1 | 标识非空（**用 `trim` 防纯空白**） | `length(trim(code)) > 0` |
| 2 | 枚举白名单 | `outcome IN ('ok','no_data','error','unavailable')` |
| 3 | JSON 有效性 + 类型 + 长度上限 | `json_valid(predicate_json)` |
| 4 | 长度上限 | `length(reason) <= 2000` |
| 5 | ⭐ **条件必填** | `kind != 'text' OR quote IS NOT NULL` |

- 约束命名统一 `<table>_<aspect>_check`。
- **条件必填用 `A OR B IS NOT NULL` 写法，不用 `CASE WHEN`**（避免方言差异与复杂度）。

**5.4.3 必填规则与红线 6 的数据库表达**

```sql
-- 红线 6：未成熟结果留空，绝不填 0
CHECK (outcome IS NOT NULL OR result_score IS NULL)
-- 红线 4：决策必填字段（理由 + 反面证据）
CHECK (length(trim(rationale)) > 0 AND length(trim(counter_evidence)) > 0)
```

**⚠️ 反面证据是唯一能对抗确认偏差的字段，必须 NOT NULL 且非空。**

### 5.5 数据库版本检查三态

启动时比对 `user_version`：

| 情形 | 行为 |
|---|---|
| **库版本 > 程序版本** | **拒绝启动**，提示"请升级程序"（**绝不尝试降级**） |
| 库版本 < 程序版本，**有迁移路径** | 走 5.1 的迁移流程（含快照） |
| 库版本 < 程序版本，**无迁移路径** | **明确报错，不尝试** |

## 第六条 · Agent 权限边界（红线 15 的落地）

> **来源**：`references/deep-dives/01-wealthfolio.md`（`cli-mcp-agent-access.md:407-499`）
> **核心原则**：**这不是提示词约束，是代码层面的权限体系。** 提示词可以被绕过，工具不存在不能。

### 6.1 工具权限四档

| 档 | AlphaCouncil 的工具 | 权限要求 |
|---|---|---|
| **① 只读** | `get_price` · `get_financials` · `get_position` · `search_cards` · `get_decision` · `list_watchlist` | 无 |
| **② 抽取草稿** | `draft_facts_from_filing`（**强制带页码**）· `draft_claim_tags` · `draft_questions_from_history` | ⚠️ **只返回草稿，绝不落库** |
| **③ 提交** | `commit_facts` · `commit_claim_tags` | 需 `facts:write`（其本身又要求 `facts:draft`），且**用户确认后** |
| **④ 永久不做** | **写入 / 修改决策记录 · 删除任何东西 · 改动关注池理由 · 替用户托管数据备份 · 改密钥** | ❌ **永不对 agent 开放** |

> ⚠️ **第 ④ 档"替用户托管数据备份"的准确含义**（2026-09-26 修订，来源 `11-open-science.md` 决定 2）：
> **不是"不给用户数据"** —— 数据**始终是本地可直接访问的文件**，用户随时可以用任何工具打开、复制、搬走。
> **被禁止的是"由我们代管备份"** —— 一旦我们成为用户唯一的数据副本，我们就要为它的可用性负责，而这与"数据在你手里"的承诺冲突。
> 原文"导出备份"容易被误读成"产品不支持导出"，故改述。

### 6.2 ⚠️ 第 ④ 档里最关键的一条

> **决策记录必须由用户亲手写。**

理由：红线 13 是「**索取在先**」—— 用户必须先写下理由，系统才记录。
**如果 agent 能替用户写决策，整个产品就塌了**（用户不再需要面对自己）。

**这一条必须在代码层面保证（工具根本不存在），不是在提示词层面保证。**

### 6.3 审计

- **审计日志脱敏**：记录"做了什么"，**不记录"内容是什么"**（借 wealthfolio：把行参数脱敏成 `"[N rows]"`）。
- **禁止在日志中输出密钥、完整请求体、用户隐私数据。**
- 审计台账 **Append-Only**。

## 第七条 · 代码规范

### 7.1 类型注解（强制）

- **所有函数（含私有函数、测试函数）必须有完整的参数与返回值注解。**
- 禁止用 `Any` 逃避类型检查。确实无法确定时，用 `object` 并注释说明。
- 泛型必须显式标注参数。
- `mypy --strict` 必须通过。

```python
# 正确
async def fetch_quotes(codes: list[str], *, as_of: date | None = None) -> list[Quote]:
    ...

# 错误 —— 缺少返回类型，且使用 Any
def fetch_quotes(codes, as_of=None):
    ...
```

### 7.2 函数与模块

- 单个函数**不超过 50 行**（不含空行与注释）。超出即需拆分。
- 单个模块**不超过 400 行**。超出即需按职责拆分。
- 函数参数**不超过 5 个**。超出时改为传入 Pydantic 模型或 dataclass。
- 嵌套层级**不超过 3 层**。

### 7.3 异常处理（强制）

- **禁止裸 `except:`** 和 `except Exception: pass`。
- 捕获必须具体到异常类型。
- 捕获后必须二选一：**处理它**（含日志与降级逻辑）或**包装后重新抛出**（保留原始 traceback）。
- 禁止用异常控制正常流程。

```python
# 正确
try:
    quote = await client.fetch(code)
except httpx.TimeoutException as exc:
    logger.warning("quote_fetch_timeout", code=code, error=str(exc))
    raise DataUnavailableError(code) from exc

# 错误
try:
    quote = await client.fetch(code)
except Exception:
    pass
```

### 7.4 日志

- **禁止 `print()`**。一律使用 `structlog`，以结构化键值对输出。
- 日志必须包含足够的排查上下文（如 `code`、`decision_id`、`run_id`）。
- **禁止在日志中输出密钥、完整请求体、用户隐私数据**（见 6.3）。

### 7.5 分层

- **API 路由必须薄**：只做参数校验 + 调用领域层，**不写业务逻辑**。
- 领域逻辑放 `domain/`（**不依赖 FastAPI / SQLAlchemy**）；持久化与迁移放 `storage/`；数据源放 `providers/`。
- **业务逻辑不得写在路由里** —— 否则换个宿主就要重写。

### 7.6 命名与结构

- 模块、函数、变量：`snake_case`；类：`PascalCase`；常量：`UPPER_SNAKE_CASE`。
- 禁止无意义的缩写（`d`, `tmp`, `data2`）。名称必须表意。
- 公共 API 必须有 docstring（Google 风格）。
- **复杂或易错的 SQL 抽成独立 `.sql` 文件**（不内联长字符串），配单元测试。

### 7.7 ⭐⭐⭐ 状态用枚举 + 有限状态机，禁止用布尔值跟踪状态

> **"When tempted to use a boolean to track a piece of stateful data, consider enumerated strings instead."**
> **判据：需要 2 个以上布尔值描述同一个对象的状态 → 那就是状态机。**

- 状态**在设计阶段预定**，用**字符串枚举**表达（不用布尔组合，不用整数魔数）。
- **状态转移表是"数据"不是"控制流"**：写成 `{ 当前状态: { 事件: 下一状态 } }` 的嵌套结构，**不是 if/else 链**。
  → 于是它**可打印、可穷举测试、可被文档引用**。
- **未定义的事件默认"保持原状态"，不报错**（收到意外事件是常态）。
- 状态**必须暴露到 UI 的 `data-*` 属性**（如 `data-state="unreviewed"`）→ **测试断言"元素自己声明的状态"，而不是断言组件内部 state**。

**理由（这是红线 5 的支撑）**：
> **布尔组合可以被事后重新解释，枚举字符串不可以。**
> "这条决策还没复盘"如果写成 `reviewed=false, outcome_filled=false, result_scored=false`，三个布尔可以组合出 8 种状态，其中 5 种是**语义不明**的；
> 写成 `state IN ('draft','open','awaiting_outcome','reviewed','archived')` 就只有 5 种，**每一种都有名字**。

### 7.8 ⭐⭐ 外部调用必须走唯一入口

- **禁止在业务代码里直接 `httpx.get` / `requests.get` / `urlopen`** —— 所有外部数据访问必须经过**唯一入口函数**。
- 唯一入口内置：**串行化 + 最小间隔 + 随机抖动 + 会话复用 + 默认 UA + 熔断 + 缓存**。
- ⭐ **时间戳在 `finally` 里更新** —— **失败也算一次访问**，否则连续失败会变成轰炸。
- ⭐ **403 不重试**（这是风控信号，重试只会加重）。
- **静态检查脚本必须拦住裸 HTTP 调用**（`.ai/checks/static/no-raw-http.*`，见第十二条）。

**理由**：限流**必须是一个函数**，不能是"请大家记得加 sleep"。

## 第八条 · 测试要求

| 层级 | 位置 | 要求 |
|---|---|---|
| 单元测试 | `backend/tests/unit/` | 覆盖所有纯逻辑：**数据契约转换、口径计算、FSRS 调度、对质判定、重复检测** |
| 集成测试 | `backend/tests/integration/` | 覆盖 API 链路、迁移链路、数据源降级（用 mock / fixture） |
| 评测测试 | `backend/tests/eval/` | **agent 抽取质量评测**（见 8.2） |

### 8.1 硬性门禁

- 新增功能**必须**附带测试，否则不予合并。
- **整体行覆盖率不低于 80%**。
- ⭐ **`domain/` 目录覆盖率不低于 90%**（纯逻辑，最容易测，也最不能错）。
- **测试必须能独立运行**，不依赖真实外部 API（用 `respx` / `pytest-httpx` 拦截，或用 fixture）。
- **禁止为了让测试通过而修改断言。** 测试失败时，先怀疑实现，再怀疑测试。
- ⭐ **bug 修复必须附一个「修前失败、修后通过」的回归测试。**

### 8.2 agent 抽取层必须可评测

- 抽取结果**必须能核对原文**（因为强制带页码）→ 这是**唯一能把"幻觉"变成可检测的东西**。
- 必须有固定的评测集与 `make eval` 一键跑出通过率。
- **每次 agent 运行必须记录 token 数与成本。**

### 8.3 ⭐⭐⭐ 变异检查（"这个测试真的会红吗？"）

> **每个缺陷修复必须回答："如果我故意改坏，这个测试会不会红？"** 答案不确定 → **去做变异检查**。

**做法**：把修复**改回缺陷状态**，跑测试，**确认它变红**，然后恢复。

**为什么必须有这一条**：没有它，前四种缺陷固化形态（第十二条）可能是**一堆永远绿的测试**。测试无效的三种典型原因：

| 原因 | 例子 |
|---|---|
| **断言太宽** | 断言"返回了列表"，不检查内容 |
| ⭐ **期望值从被测代码读取** | `assert value == MODULE.MIN_PRICE` —— **改小下限，测试也不会变红** |
| **被另一道检查顶替** | 红是因为别的测试，不是因为这一条 |

**硬性规则**：
- ⭐ **测试的期望值必须写死**（字面量），**禁止从被测代码导入**。需要引用常量时，**在测试文件里重新写一遍并注明"这里写死，不从被测代码读"**。
- **变异检查记录**必须留档：`.ai/regressions/` 下每条回归测试写明"改坏哪里 → 哪个测试变红"。
- 一处修复若**无法被变异检查**（如"某段代码不该存在"），**它不该用测试固化，该用静态检查**（见第十二条）。

**测试命名规范**：`test_<被测对象>_<场景>_<期望结果>`

```python
def test_price_adjust_mismatch_raises_on_mixed_series() -> None: ...
def test_decision_log_rejects_client_supplied_id() -> None: ...
```

## 第九条 · 审查纪律

- ⭐ **质疑「这个机制是否需要存在」，而不只是「它是否能工作」。**（借 wealthfolio `AGENTS.md:146`）
- **审查者只读。** Reviewer **不得修改任何代码**，只能输出问题清单（含 `file:line` 与严重级别）。
- **开发者与测试者分离。** 同一个 Agent 不得既实现功能又编写该功能的验收测试。
- **台账 Append-Only。** `.ai/logs/` 下只能追加，**不得修改或删除历史条目**。
- **审查结论必须可执行。** 每条须给出：位置、现象、影响、建议方案。
- ⭐ **必须区分「已确认 / 假设 / 未验证」。**
- ⭐ **缺少根因证据时，结论必须是「修复未经验证」** —— 不得用"未发现问题"代替。
- **必须明确写出「已确认无问题的项」** —— 只列问题会让人误以为一切都糟。

**严重级别**：

| 级别 | 定义 | 处理 |
|---|---|---|
| `P0` 阻断 | 安全漏洞、数据损坏、密钥泄露、**产品红线违反** | 立即修复 |
| `P1` 严重 | 逻辑错误、测试缺失、工程红线违反、**口径混用** | 合并前必须修复 |
| `P2` 一般 | 可读性、性能、文档缺失 | 记录并排期 |

## 第十条 · 提交与协作

### 10.1 提交信息（Conventional Commits）

```
<type>(<scope>): <subject>

[body: 为什么这样改，而不是改了什么]

[footer: Closes #123]
```

允许的 `type`：`feat` `fix` `docs` `test` `refactor` `perf` `chore` `ci` `build` `revert`

```
feat(decision): make log id server-generated timestamp

Clients could previously supply an id, which allowed back-dating a
decision to before its outcome was known — defeating the whole point
of "record before the result".

Closes #42
```

### 10.2 分支与 PR

- 分支命名：`feat/<scope>-<short-desc>`、`fix/<scope>-<short-desc>`
- PR 必须包含：**改动目的** · **改动内容** · **验证方式（命令 + 结果）** · **关联 Issue**
- **PR 必须通过**：`make check` 全绿 + Reviewer 审查 + 人工确认
- **报告未执行的检查并说明原因；不得暗示已通过。**

### 10.3 规格驱动开发

**任何非平凡功能，必须先写规格，再写代码。**

```
.ai/specs/<编号>-<功能名>/
├── spec.md    # 做什么：需求、验收标准、边界
├── plan.md    # 怎么做：技术方案、涉及文件、风险
└── tasks.md   # 拆解：可独立验证的任务清单
```

**没有 `spec.md` 的功能改动，不予受理。**

### 10.4 开发过程本身也是交付物

**⚠️ 目录职责必须分清（避免重复建两套台账）**：

| 目录 | 记什么 | 给谁看 |
|---|---|---|
| `.ai/memory/decisions.md` | **架构决策记录（ADR）** —— 为什么这样设计 | **人**（下次想推翻前先读） |
| `.ai/logs/changes/` | **变更与依赖审批台账**（append-only） | 审计 |
| `.ai/logs/review/` | **审查结论台账**（append-only） | 审计 |
| `.ai/traces/` | **agent 运行 trace**：`Trace → Observation → Score` | 排错 + 计成本 + 评测 |
| `.ai/status.md` | **能力地图**：目标能力 / 当前状态（**每行以"还差什么"结尾**） | 人 + agent（知道自己在哪一步） |
| `.ai/failure-modes.md` | **失败模式清单**（跨 change，只增） | agent（**别重复踩**） |
| `.ai/error-codes.md` | **错误码命名空间**（按来源分类 + 每条标 severity + 发布后不改名） | 程序读 + 人读 |
| `.ai/checks/` | **检查脚本**：`data/`（运行时扫库）+ `static/`（编译期扫代码） | CI |
| `.ai/regressions/` | **回归记录**：每个缺陷 → 测试 + 变异检查结果 | 人（三年后还能跑） |
| `.ai/data-sources.md` | **数据边界**：覆盖 / 不覆盖 / 起点 / 口径 / 缺口 / 封禁风险 / **未接入表** | 人（别再重复调研） |

> **不新增 `decisions/` 或 `ledger/` 目录** —— 它们与上表的前两项职责重复。
> **一张台账只存在一个地方。**

**理由**：产品对用户的对抗机制（要理由 / 要反例 / 指出重复），和流水线对代码的审查机制（要规格 / 要反例 / 指出回归），**是同一件事**。
见 `AlphaCouncil-产品定义-v3.md` §3。

### 10.5 ⭐ 工作记录四段式（原三段式 → 四段式）

所有工作记录（`.ai/memory/YYYY-MM-DD.md`、`.ai/logs/changes/*`）统一四段：

| 段 | 回答 |
|---|---|
| **① 想做什么** | 意图（在动手之前写） |
| **② 做了什么** | 实际动作，**含具体文件与命令** |
| **③ 得到了什么样的结果** | 验证结果；**失败项如实记录并注明"不是代码问题"** |
| **④ 留下了什么** | 新增的 ADR / 检查 / 回归 / 未完成项；**允许写"无"，但这一节不能省略** |

> **④ 是新增的。** 理由：三段式只回答"这件事做完了吗"，四段式还回答"**这件事留下了什么**" ——
> 后者才是跨会话真正需要的。见 `11-open-science.md` 决定 19。

### 10.6 ⭐ 文案语气（UI 与文档分开）

| 场景 | 语气 |
|---|---|
| **AI 对主人说话**（对话、日志、汇报） | 可爱体贴女友风，称呼"主人" |
| **产品 UI 文案 / 可复用规范 / 文档** | **中性、功能性、不拟人化** —— 不用"我"作主语表达意见（写"系统准备响应所花的时间"，不写"我思考了一下"） |

**但问题的措辞可以直白** —— "你为什么不执行自己定的规则？"是允许的（**这是产品对用户的对抗机制，不是拟人化**）。
区别在于：**不以"我"（系统）为主语表达意见/情绪**。

**其他文案硬规则**：
- **可复用规范里禁止出现样例数据**（具体项目名 / 数据集名 / 个人邮箱 / 组织 ID / 模型名）。
- **每个纯图标按钮必须有 `aria-label` + `Tooltip`**。
- **错误信息禁止省略 / 截断 / 折叠**（"Do not ellipsize embedded messages"）；所有文案与标识符**必须换行不溢出**。

## 第十一条 · 边界与非目标

> **有些限制是故意的，不是疏忽。我们宁可说出来，也不让文档暗示相反的意思。**
>
> 理由：不写清楚"我们不做什么"，后来者会（a）以为这是遗漏并去"补上"，(b) 拿错误预期衡量进度。
> **明确的不做，比模糊的"以后再说"更专业。**

### 11.1 我们不做什么（永久）

| 非目标 | 为什么 |
|---|---|
| **不做预测增强**（目标价 / 涨跌预测 / 买卖建议） | 红线 1。预测维度边际收益被市场有效性抹平 |
| **不做选股 / 因子 / 回测** | 那是量化工作台，不是知识管理系统 |
| **不做行情终端**（分时 / 盘口 / 异动推送） | 红线 11。**注意：我们仍然做日线 / 财务 / 公告 —— 不做的是"盯盘"** |
| **不做社交 / 分享 / 排行** | 红线 9。成绩展示会强化 resulting |
| **不做云端账户 / 数据托管** | 数据必须在用户本地可直接访问的文件里 |
| **不做团队协作** | 这是个人投资者的工具 |
| **不做多语言** | 中文 A 股场景，简体中文即可 |
| **不做自动交易 / 券商对接** | 我们只做"决定之前"与"结果之后"，不碰下单 |

### 11.2 我们降低的是什么成本（重要区分）

> **我们降低的是「执行与记录」的成本，不是「判断」的成本。**

- ✅ 降低：找数据的时间 · 记录决策的摩擦 · 想起来要复盘的难度 · 跨来源信息对齐的成本。
- ❌ 不降低：判断一家公司值不值这个价 · 判断该不该卖 · **承担后果的责任**。

**任何让"判断"变轻松的改动，方向都错了** —— 那会变成红线 1。

### 11.3 已知的结构性缺陷（与生俱来，不是 bug）

| 缺陷 | 后果 |
|---|---|
| **价值延迟** | 价值要 2–3 年才显现，而用户 3 天就决定去留 |
| **反馈令人不悦** | 系统每天可能在说"你错了" |
| **索取在先** | 用户必须先写，系统才记录 —— **门槛不能降**（降了产品就没了） |
| **用户在最不理性时使用它** | 必须假设"此刻的用户不可信" |

**违反其中任一条，就已经不是这个产品。** 反例：加"每日精选机会"（→ 荐股工具）· 亏损时安慰话术（→ 安慰剂）· 连续打卡徽章（→ 用打卡替代真反馈）· 允许"稍后再答"（→ 给冲动留后门）。

### 11.4 技术上的非目标

- **不追求 exe 体积最小化到极致** —— 体积是约束，不是目标（但**每条打包排除都要写理由**，见 `.ai/release-checklist.md`）。
- **不追求离线完全可用** —— **"本地优先 ≠ 离线"**：本地存储与本地进程**不意味着离线运行**；只读连接器**仍然把查询词发给数据源**；**取消不能撤回已收到的字节**。
- **不追求零依赖** —— 只追求"每个依赖都必须挣得它的体积与维护成本"。

## 第十二条 · 缺陷的固化（五种形态，按缺陷性质选用）

> **"报告问题"不够。缺陷必须变成永久资产，否则同一个坑会再踩一次。**

| 形态 | 载体 | 生命周期 | **适用缺陷性质** |
|---|---|---|---|
| ① **写进验收标准** | `spec.md` 的 `## 已知的失败` → 对应 AC | 单 change | **验收时该检查什么** |
| ② **写进失败模式清单** | `.ai/failure-modes.md` | 跨 change，只增 | **某种思路会误导人** |
| ③ **写成回归测试 + fixture** | `.ai/regressions/` + `tests/` | **永久** | **运行时行为错了** |
| ④ **写成静态检查脚本（AST 级）** | `.ai/checks/static/` + CI | **永久** | ⭐ **某段代码不该存在**（跑不到就抓不住） |
| ⑤ **写成变异检查记录** | `.ai/regressions/`（"改坏哪里 → 哪个测试变红"） | **永久** | ⭐ **测试本身可能无效** |

**关键区分**：
- **前四种回答"缺陷该变成什么"；第五种回答"我怎么知道前四种真的有用"。**
- ⚠️ **④ 与 ③ 不能互相替代** —— **"某段代码不该存在"这类缺陷，测试永远抓不住**（测试只能证明"跑到的路径是对的"）。
  → **因此 `.ai/checks/` 必须分 `data/`（运行时扫库）与 `static/`（编译期扫代码）两类。**

**判据（与 8.3 同源）**：
> **每个缺陷修复必须回答："如果我故意改坏，这个测试会不会红？"** 答案不确定 → 去做变异检查。

**④ 类脚本的硬性要求**：脚本头部必须写明 **① 守的是哪个历史缺陷（issue 号）② 反模式示例 ③ 正确写法**；CI 位置在 **Lint 之后、Build 之前**（早失败）。

### 12.1 ⭐⭐ 红线必须三层落地（否则就只是意图）

| 层 | 载体 |
|---|---|
| **语义层** | 每条红线转成 **requirement + scenario**（写在对应 `spec.md` 里） |
| **代码层** | `.ai/checks/static/` 反模式脚本（如 `no-raw-http` · `no-boolean-state` · `no-prediction-field`） |
| **UI 层** | `data-*` 断言 + E2E（见下表） |

**可直接落地的 5 条前端 E2E 断言**：

| 断言 | 守的红线 |
|---|---|
| 亏损持仓的浮亏数字**字号 ≥ 浮盈数字** | 10（不美化） |
| "草率但奏效"的决策卡**不渲染任何金额** | 9 + 交互原则"不庆祝运气" |
| 止损提示**必含"恢复所需年数"** | 12（时间的成本） |
| 首页**不含"收益率"字样** | 9 |
| 未成熟结果区域**渲染为空**（不是 `0`，不是 `—`） | 6 |

> ⚠️ **判据：一条红线如果无法被 CI 拦住，它就只是意图。**
