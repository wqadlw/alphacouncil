### ADR-0027 里最关键的一条：启用条件

> agent 三件套（LangGraph / Langfuse 服务 / fastmcp）**同时**满足两条才动手装依赖：
> ① 出现**一个必须有运行期 agent 才能实现的产品能力**（已交付的 S1–S4 / K1 / K2 都不需要）
> **且** ② **`make eval` 存在且能跑出通过率**。
>
> 在此之前，开发流水线由 **`.ai/` 的书面纪律**承载 ——
> **这不是"还没来得及"，是一个明确的选择。**

理由：`spec 003` 自己的横幅已经写明 agent 是"只是数据的搬运工…**不是产品差异化核心**"。
既然如此，就不该让它在路线图上看起来像一条即将开始的工程。
而约束①「写进简历」真正能诚实展示的是**开发流水线**，不是运行期 agent ——
`make eval` 正是把前者从"叙述"变成"可测量"的那一块，**所以它的优先级因此上升**。

## 三、为什么没有加静态检查

> ⚠️ **2026-09-28 修订：本节的结论后来被部分推翻，规则已补（spec 017 / S-13）。**
> 原文保留，因为"当时为什么这么判"本身是信息。

宪法 2.2 三问，逐条作答：

| 问 | 答 |
|---|---|
| **具体故障？** | 我能举出的具体故障是"**我读错了一行乱码**"。静态检查抓不住读错。能抓的是"两个 ADR 文件状态不一致" |
| **既有机制为何不行？** | S-05 只管错误码三方一致，不管文档一致性。**但更关键的是：我已经删掉了第二个存储，故障的可能性随之消失** |
| **必需还是可选？** | **删除是必需的，规则是可选的**。宪法 0.2 判据"能移就必须移"指向删除 |

**诚实边界**（写进 `0005`，不藏）：结构修复**防不住下一个人重新创建 `docs/adr/`**。
真要挡住需要一条检查规则。**没做**，因为按三问它答不出"具体故障"——
这是权衡的结果，不是遗漏。**若日后真的再现，就补规则。**

### 3.1 修订：关于「答不出具体故障」这句话本身

**这个判断被同一天发生的事直接反驳了。**（见 spec 017 §三）

`0004` 修的是"开发者工具在中文控制台上无法输出"。我当时把修复放在**三个调用点**上，
并且**没有加规则** —— 理由和本节一样："这是文档问题，不是机制问题"。

**结果：同一天写出第四个工具 `scripts/eval.py` 时就又犯了一次**，
它的 `--json` 输出是 GBK，把中文字符串从中间截断。
而且 S-13 上线**第一次运行**就抓到了第五处（`smoke_market.py`，手工冒烟脚本，从未被测试跑过）。

**所以"答不出具体故障"这句话是错的。故障一直存在，而且可以点名：**
> "新写的开发者工具忘记调用修复" —— 每加一个工具就复发一次，
> 直到有一次它复发在**会被人用**的工具上。

**教训比结论重要**：我以为自己在做"结构性修复优于规则"的判断，
实际上我只是在**用三问的措辞为一个偷懒的结论背书**。
三问的第一问是"具体故障"，而"三个调用点"这个方案的具体故障我**当时就能说出来**。

**已补**：S-13 `tool-encoding`（spec 017）。
**本节保留原文**，因为"当时为什么这么判"和"后来为什么改判"都是信息。
