# spec 031 实施计划

## 一、顺序，以及为什么是这个顺序

1. **`classify()` 先变成表达式解析器**，并补齐单元测试
2. **再接 npm 扫描**，因为它复用上一步的判断
3. **最后才是门禁接线**与全量验证

⭐ **判断逻辑必须先于调用方落地。** 如果先写 npm 扫描，就会得到一段「用旧的子串
判断去扫 npm」的代码，而它跑出来的数字（很可能 0 个 FAIL）看起来完全正常 ——
⭐ **一个用错判断却给出正确数字的扫描器，比一个会报错的扫描器危险得多**，
因为它会让人以为扫描过了。

## 二、第一步：`classify()` 变成表达式解析器

保持 `classify(text: str) -> Verdict` 的签名不变 —— ⭐ **签名不变，Python 侧的调用方
一个字都不用改**，这是这个改动能保持零回归的关键。

内部拆成：

| 函数 | 职责 |
|---|---|
| `_split_top_level(expr, op)` | 按顶层 `OR` / `AND` 拆表达式 |
| `_strip_with(term)` | 去掉 `WITH <exception>`，只留基础许可 |
| `classify(text: str)` | 保留现有「多字段拼接 + 分隔符」的处理，再交给表达式判定 |

⭐ **多字段拼接要先拆开**。`_licence_text()` 会把 `License` / `License-Expression` /
分类器用 ` | ` 拼起来，那**不是**一个 SPDX 表达式，而是**几个候选**。
⭐ 把候选串当成一个表达式去解析，会得到「`MIT | License :: OSI Approved` 里含 GPL 吗」
这种毫无意义的问题。所以 `|` 优先于 `OR` / `AND` 拆分，⭐ **分隔符的优先级要写成注释里的
一条规则，否则下一个读代码的人会把顺序反过来**（而反过来不会报错）。

单支判定保留现有的 `AGPL` → `GPL` → `WEAK_COPYLEFT` → `PERMISSIVE` 顺序，
⭐ 因为那个顺序**本身就是有意的**（`AGPL` 含 `GPL` 子串，`LGPL` 不能被 `GPL` 规则吃掉），
不该在这次重构里动。

## 三、第二步：npm 扫描

```
_scan_npm(frontend: Path) -> tuple[list[Finding], int]
```

* 跳过 `node_modules/.bin`、`node_modules/.cache`
* ⭐ 跳过**本项目自己的包**（与 Python 侧的 `_SELF` 同一个道理）
* ⭐ 按 `name@version` 去重 —— 同一个包可能被装多个版本，但**每个版本只该被审一次**
* 返回「所有包」与「production 闭包里的包数」两个数字

## 四、第三步：门禁接线

`main()` 里增加两行打印与一个判断。⭐ **退出码的判断只认 production 闭包**，
这一句要写在代码注释里，并指向 spec §2.2 —— 因为「dev 里的 GPL 算不算」
是一个看起来很合理的反对意见，而它是错的。

## 五、验证顺序（不可跳步）

1. `classify` 的单元测试（含 `OR` / `AND` 同组合不同答案）
2. Python 侧现有结论不变 —— ⭐ **先证明没回归，再证明有新能力**
3. npm 侧包数 ≥ 209
4. 门禁退出码
5. ⭐ **变异检查**：`OR` 分支改成「任一支宽松就 OK」（即 `AND` 也变 `OK`），
   看测试是否变红 —— **这一条是本篇的存活/杀死分界线**
