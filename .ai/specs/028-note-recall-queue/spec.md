# spec 028 · 笔记的复习队列

> 状态：**实现中** · 2026-09-28
> 接 spec 026（笔记）与 spec 027（检索）。
> 规范的原话（`前端设计系统与功能规划` §A2）：
> **「收藏 500 篇文章不等于拥有知识。SRS 才是把信息转化为长期记忆的机制。」**
> 记下来（026）✓ 找得到（027）✓ **会自己回来找你**（本轮）

---

## 一、⭐⭐ 本轮真正的设计问题，不是"抄一份 card_schedule"

卡片复习队列（spec 018）已经建好，`domain/scheduling.py` **是通用的**
（`ScheduleState`/`ReviewRating`/`defer_due`/`rating_to_fsrs` 都不含 card 类型）。
**domain 层零改动即可复用。**

那这轮要想清楚的是什么？是这句话：

> **卡片是不可变的，笔记是可变的。**

| | 卡片 | 笔记 |
|---|---|---|
| 正文能改吗 | **不能**（K1 刻意不给编辑动词） | **能**（spec 026 的 `PATCH`） |
| 于是「我当时复习的那条」 | 永远是同一条 | **可能已经不是了** |

⭐ **所以一条在队列里的笔记被改写之后，FSRS 的记忆强度还挂在**已经不存在的文本**上。**

假设：9 月入队，评了 3 次 `good`，FSRS 算出「3 个月后复习」。
10 月我把正文整段重写。11 月它到期 resurfacing —— 用户被要求回忆
**一段他从没复习过的文字**，而排程器以为他记得很牢。

⭐ **那是排程器在说谎。** 而本项目的整个立论就是「记录必须可信」
（宪法：你的记录是你唯一能信的东西）。**一个会说谎的排程器比没有排程器更坏。**

→ **决定：改写在队列里的笔记 = 重启它的排程。**
FSRS 卡片重建成一张新的（`stability` 归零，立刻到期），
**而复习流水一行都不删**（append-only）。

---

## 二、⭐⭐ 重启本身必须留痕：所以 `ReviewOutcome` 加第三态

`note_reviews.outcome` 现在有 `reviewed` / `deferred`，要加 **`reset`**。

理由很具体：**「我复习过 5 次，为什么今天又回来了」必须能回答。**
如果重启只改 `note_schedule` 而不写流水，那次重写就在历史里消失了 ——
而本产品的核心命题是「投资无法从经验中学习，因为没有记录」，
**学习的尝试史就是这个产品本身**。重置是一次真实的调度事件，不是一次复习
（用户没有回忆任何东西），所以它是**第三个 outcome，不是第二个的特例**。

```text
reviewed  我回忆了，然后评分
deferred  现在不是时候（想法还没定），记忆强度一个字节都不动
reset     笔记被改写，排程重启；**没有评分，也没有耗时**
```

`reset` 与 `deferred` 的区别不是"程度"，是**方向**：
`deferred` 往后推，`reset` 往回退。两者都不碰记忆强度，但只有 `reset`
重建卡片。

## 三、`instr` 之外的两个决定，都写下来

### 3.1 ⭐ 入队**永远是显式的**，绝不自动

把「我写过的每条笔记」都塞进队列，会得到一个**永远清不完的欠账**，
而「你欠 N 条」正是红线拒绝的那种感觉（`项目总纲` §2.1⑤
「一句陈述，无推送、无红点、无催促词」）。

→ `POST /notes/{id}/schedule` 由用户点。**想要知识回来找你的东西，得先告诉系统哪一样。**

### 3.2 ⭐ 复习时**显示全文**，不藏标题考记忆

Anki 的做法是只给提示词、让你回忆、再揭示。对笔记**不适用**：

**笔记的标题不是一个好的提示词。** 「关于流动性的一点想法」不告诉你该回忆什么，
只测你能不能从自己写的标题里猜出内容 —— **那测不出记忆，只测运气。**
而卡片的主张**本身就是**完整的提示词（一句话判断），所以卡片可以藏。

→ 笔记复习是**重读与再确认**（re-read and re-affirm），不是记忆测验。
这个区别必须说清楚，因为 `again` 在两边的含义不同：

| | `again` 的含义 |
|---|---|
| 卡片 | 「我回忆不起来这条主张」 |
| 笔记 | 「**我的想法已经变了**」 |

⭐ 对笔记来说，「我的想法变了」是**这个产品最想听到的信号** ——
它意味着一条笔记该被改写、该被标记、或者干脆该收敛。
把两种含义混在一句 UI 文案里，就等于把最有价值的那次反馈说成了"你忘了"。

## 四、为什么不并进 `card_schedule`（沿用 spec 026 的裁定）

形状相同但**行为不同**（复习卡 = 拿主张去对出处；复习笔记 = 重读自己写过的东西，
而它随时可能被改写），而且**改已记录的 append-only 复习流水是最不该做的事**。
`reset` 这一态是**笔记独有的** —— 卡片不可变，所以它永远不需要。

⭐ 这一点反过来印证了分开是对的：**如果两者真的一样，`reset` 就该是两者的共同能力，
而它不是。**

---

## 五、`NoteScheduleRow` 为什么不是 `ScheduleRow`

`ScheduleRow` 有 `card_id` 字段。给笔记复用它，就等于让一个叫 `card_id`
的字段装着笔记 id —— **一个会被所有下游读到的类型里的谎**。

→ 新增 `NoteScheduleRow` / `NoteReviewRow`，字段叫 `note_id`。
**约 12 行重复，换一个诚实的名字。** 重复的**函数**（`defer_due`、
`rating_to_fsrs`、`parse_due`）一律复用，不复制。

## 六、验收

| # | 项 |
|---|---|
| 1 | 显式入队；重复入队被拒（不重置） |
| 2 | 到期队列按 `due_at` 升序，**不按任何紧急度评分** |
| 3 | 评分后：流水 append + 排程更新**在同一个事务里** |
| 4 | `deferred` 不碰 `state_json` 一个字节 |
| 5 | ⭐ **改写在队列里的笔记 → 排程重启 + 写一行 `reset`**，历史不丢 |
| 6 | ⭐ 不在队列里的笔记被改写 → **什么都不发生**（不产生 `reset`） |
| 7 | 推迟不能超过 90 天 |
| 8 | 队列顺序在两次调用之间稳定（`due_at, note_id`） |
| 9 | **界面不渲染任何队列计数** |
| 10 | 门禁 10/10 + 退出码 0 |
