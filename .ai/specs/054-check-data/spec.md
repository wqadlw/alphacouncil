## 二 · ⭐⭐ 三条实测出来的 schema 洞，⭐ 而声明里一个字都没提

### 2.1 `decisions` 的 `counter_evidence` CHECK 用 `trim()`，⭐ 而 `trim()` 只去空格

`CHECK (length(trim(counter_evidence)) > 0)`。实测（在**外键已满足**的前提下，
⭐ 所以是 CHECK 在回答而不是外键）：

| 值 | schema | `trim()` 看得见吗 |
|---|---|---|
| `''` | 拒绝 | — |
| `'  '` | 拒绝 | — |
| `'\t'` | ⭐ **接受** | ⭐ **看不见** |
| `'\n'` | ⭐ **接受** | ⭐ **看不见** |
| `' \t\n '` | ⭐ **接受** | ⭐ **看不见** |
| `'　'`（全角空格） | ⭐ **接受** | ⭐ **看不见** |
| `'\x0c'`（换页符） | ⭐ **接受** | ⭐ **看不见** |
| 真正的文字 | 接受 | 不 ⭐ 且正确 |

⭐⭐⭐ **一条决策的「反面证据」只有一个 tab，⭐ 现在就在库里，⭐ 而 schema 的 CHECK 与
D-07 的第一版都不会说一句话。**

⇒ D-07 改用 `replace()` 显式去掉六种空白 ⭐ ⭐ **并把 schema 那个洞报给主人**
（⭐ 改它要动一条守着红线 4 的约束，⭐ 那是主人的决定，⭐ 不是本轮能顺手做的）。

### 2.2 `decisions` 有复合外键 `(market, code) -> instruments`，⭐ 所以 D-01 的对象不可达

实测：`PRAGMA foreign_keys = 1`（产品连接上开着）、17 张表有外键、
⭐ **插入一条指向不存在标的的决策被直接拒**（`on_delete=NO ACTION`，⭐ 所以删 instrument 也被拒）。

⇒ ⭐⭐ **D-01 要找的悬空引用，是这个数据库拿不到的状态。** ⭐ 而我第一版的 docstring 写着
「schema 没有提供这个保证，⭐ 迁移里也没有外键声明」⭐ —— ⭐ **两句话都是假的，⭐ 两句我都没量。**

⇒ 所以 D-01 保留在注册表里，⭐ **每次运行都发一条 `note`** ⭐⭐ 说清「外键在，⭐ 所以这个问题
问不出来」⭐⭐ 而不是安静通过。⭐ 一道安静通过的门读作「数据是干净的」，
⭐⭐ 而真相是「这个问题不成立」。

### 2.3 `audit_log.detail` 被自己的 CHECK 封在 500 字以内

⇒ D-22 的阈值 200 ⭐ ⭐ **有效区间是 201..500** ⭐⭐ 500 以上 schema 直接拒绝，⭐ 这条规则根本
不会被咨询。⭐ 声明里「审计日志含敏感内容」承诺兜住最坏情况，⭐ **而最坏情况在规则被问之前
就已经不可达了。**
