## 一、这一轮先回答一个问题：**"不讨好用户"在复习界面上长什么样**

spec 018 留了一句债：*"界面必须先回答'不讨好用户怎么落地'"*。现在回答。

### 1.1 答案：它是一个**缺席**，不是一个功能

复习界面的全部输出是三样东西：

| 显示 | 为什么 |
|---|---|
| 卡片的主张 + **来源始终可见** | 这是被复习的东西，而且可以当场核对（provenance rule 的 UI 兑现） |
| 用户自己选的评分 | 红线 15 的反面：判断由用户做，不由系统代劳 |
| **下次什么时候回来**（一个日期） | 这是**事实**。红线 9 允许事实，禁止成绩 |

**界面不会做的**（每一条都对应一条红线，且都会被 E2E 钉住）：

| 不做 | 红线 | 具体到界面 |
|---|---|---|
| 不显示"你记住了 87%" | 9 | **不调用 `get_card_retrievability`**（spec 018 已用 AST 测试钉死） |
| 不显示"连续复习 5 天" | 11 | 不存在任何 streak / 连续天数 字段或组件 |
| 不显示"你今天已复习 3 张" | 11 | 队列**不显示剩余张数进度条** |
| 不在用户答错时说"没关系" | 13 | 评 `Again` 之后**只显示新到期日**，一句话都不评价 |
| 不在用户答错时标红/计数 | 13/14 | 没有"你忘记了 3 次"这种东西 |
| 不弹"要不要现在再复习一遍" | 11/14 | 答完就走 |

> **这是本 spec 最重要的一段**：红线 13 之所以难落地，通常是因为被理解成
> "要设计一些不讨好的提示"。**它恰恰是不要设计任何东西。**
> 复习界面只陈述事实，不评价用户 —— 因为一旦开始评价，就必然有人在评价某个方向。

### 1.2 "现在不是时候"是**一等公民**，不是隐藏出口

S-05 的原话：**「"暂不处理"是特性不是拖延」**。

所以推迟按钮与四个评分按钮**并列、同等显眼**，不折叠进"更多"。
理由不是 UX，是**红线 14**：如果用户现在答不出来而产品只给"忘了"这个选项，
他就必须对自己撒谎（选"记得"）或者干脆放弃队列 —— **两个都是产品造成的**。
给一个诚实的出口，是让他不必撒谎。

而 spec 018 已经保证：**推迟不产生评分、不改记忆强度**（`state_json` 逐字节不变）。
所以"现在不是时候"这个选择**不会让这张卡变得更难记住**。

## 二、两处与已采纳决定的**偏差**，先记录再实现

`13-supermemo.md` 有两条与 spec 018 的实现不一致。**如实处理，不悄悄保留。**

### 2.1 S-07 说记忆有三个独立维度，我们只实现两个

S-07：卡片至少有 `priority`（重要性）/ `stability`（FSRS）/ `retrievability`（FSRS）
三个**独立**维度。

- `priority`：✅ 已有（K1 的 `cards.priority`）
- `stability`：✅ 存在 `state_json` 里（FSRS 内部）
- `retrievability`：❌ **完全不计算**（spec 018）

**偏差理由**：`retrievability` 是「你此刻能记住它的概率」——
**那是关于用户记忆的成绩**，不是关于世界的事实。红线 9 明文禁止展示成绩，
而一个永远不显示的数字，没人会去要求它存在。

S-07 的真正主张是"三个维度**互相独立**、不要互相推导"，这一点我们**遵守**：
`priority` 不参与 FSRS 计算，`stability` 不影响队列顺序。

**但这是一处对已采纳解读的偏离，登记为 ADR-0028。**

### 2.2 S-03 说默认排序按优先级，我们只按到期时间

S-03：「知识条目加 `priority` 字段；**默认排序按优先级，不按创建时间**」。

spec 018 的 `due_cards` 排 `due_at ASC, card_id ASC`，**不排 priority**。

**偏差理由**：S-03 讲的是**知识条目列表**（标的页第 ② 块的展示顺序），
而复习队列的语义是 FSRS 的「到期」。在**都已到期**的卡之间按 priority 排，
会让用户先做重要的那条 —— 听起来合理，但它把「积压的严重程度」变成了
一个用户能感觉到的**排名**，而红线 11 反对的正是这个。

**且 S-03 的场景（列表默认顺序）在标的页那一块仍然成立**，
spec 018 只是没有把它套用到队列上。同样登记进 ADR-0028。

## 三、API

| 端点 | 说明 |
|---|---|
| `POST /api/v1/cards/{id}/schedule` | 排程一张卡（= 生成调度项）。已排程 → 409 `CARD_ALREADY_SCHEDULED` |
| `GET /api/v1/cards/due?as_of=&limit=` | 今日到期队列。**`as_of` 由调用方注入**（可测、可回放） |
| `POST /api/v1/cards/{id}/review` | 交一次交互：`outcome=reviewed` + `rating`，或 `outcome=deferred`（+ `days`） |

- 全部 `extra="forbid"`（S-06 的同一条规则）
- **没有 `PUT` / `PATCH` / `DELETE`**：复习流水是 append-only
- 写端点在**路由层**开事务（项目约定，见回归 0006）
- `duration_ms` **不由客户端提供**：时长是**服务端测的**，
  客户端能填的时长就是"表演出来的时长"

> 响应里**不出现** `retrievability`、`stability`、`priority_rank`
> 任何一个字段。这是把红线 9 写进契约而不只是写进界面。

## 六、明确不做

| 不做 | 为什么 |
|---|---|
| 显示 `retrievability` / 正确率 | **那是成绩**（红线 9）；ADR-0028 记录了与 S-07 的偏差 |
| 复习进度条 / "已复习 3/8" | 红线 11：把清空积压变成可被游戏化的进度 |
| 连续天数 / 打卡 | 红线 11（且 `.ai/eval` 红线 8/11 的 gap 都点到了它） |
| 答错时的安慰文案 | 红线 13 |
| 让客户端填 `duration_ms` | 时长必须由服务端测；客户端能填的就是表演 |
| 队列按 priority 排 | ADR-0028 记录理由 |
| 批量复习 / 键盘流快捷键 | 会把复习变成可快速刷完的机械动作 —— 那正是红线 11 反对的 |
| 复习历史界面 | 有 API 有流水，但**历史是给自己看的**，不是产品表面。独立一轮 |
