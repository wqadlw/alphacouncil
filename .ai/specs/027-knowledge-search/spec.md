# spec 027 · 知识库检索

> 状态：**实现中** · 2026-09-28
> 接 spec 026。上一轮把「记录知识」的能力补上了，但**记了却找不到**，
> 而一个记了却找不到的知识库等于没记。

---

## 一、⭐ 动手前先量，而不是先选

「用 SQLite FTS5，中文用 trigram」是标准答案。**先量，再决定**：

```text
sqlite3 version: 3.53.1
FTS5: available
trigram tokenizer: available
  MATCH '流动性'  -> 1 hit
  MATCH '现金流'  -> 1 hit
  MATCH '不存在的词' -> 0 hit
```

**四个机制全部实测通过**（不是想当然）：

| 要确认的 | 结果 |
|---|---|
| 触发器能否在 **STRICT** 表上写进虚拟表 | ✅ 能（`notes` 是 STRICT，FTS5 表不能是，这正是要用触发器的原因） |
| `DELETE FROM notes_fts WHERE note_id = ?`（该列 UNINDEXED） | ✅ 能，不报错 |
| UPDATE 之后**旧文本是否真的消失** | ✅ 消失（这是最要命的一条，见 §三） |
| `bm25()` 排名 | ✅ 存在，**但不用它**（见 §四） |

---

## 二、⭐⭐ 最要紧的一条：**trigram 有 3 个字的下限，而中文最常搜的就是两个字**

实测：

```text
  2 chars  MATCH '利率'     -> 0 hit(s)      ⭐
  2 chars  MATCH '白酒'     -> 0 hit(s)      ⭐
  2 chars  MATCH '估值'     -> 0 hit(s)      ⭐
  3 chars  MATCH '现金流'   -> 1 hit(s)
  4 chars  MATCH '利率上行'  -> 1 hit(s)
```

`trigram` 索引的是**重叠的 3 字序列**，所以**少于 3 字的查询匹配不到任何东西**。

而「利率」「白酒」「估值」「宏观」「渠道」——**这个领域里最自然的检索词恰好全是两个字**。

⭐ **一个对「利率」返回空结果的搜索框，比没有搜索框更坏**：
没有搜索框，用户知道没有；搜索框返回空，用户会以为**那条笔记不存在**。
而那条笔记可能就在屏幕上。

→ **决定：≥3 字走 FTS5，<3 字走 `LIKE`。**
两条路都在测试里，且**这个分工写在代码注释里**，因为「为什么两个字搜出来的顺序和四个字不一样」
是迟早会被问到的问题。

`LIKE` 在这个规模下不是妥协：宪法 §规模是「个人级几千张卡」，
几千条 × 约 1KB ≈ 1–2 MB 全表扫，SQLite 里是**亚毫秒级**。
FTS5 的价值是「不随规模线性劣化」，不是「LIKE 慢到不能用」。

## 三、⭐ 索引不同步 = 这个功能最坏的失败方式

> 笔记就在屏幕上，搜索说它不存在。

所以索引**由触发器维护，不由仓储维护**：

| 理由 | 说明 |
|---|---|
| 触发器**不可能被忘记** | 仓储里手写 `INSERT INTO notes_fts`，就多了一条「绕过仓储就能写库」的路 —— 而那条路**没人会记得同步索引** |
| 触发器对**每条写路都生效** | 仓储、迁移、手工 SQL，全部覆盖 |
| UPDATE 必须**先删后插** | 触发器写 `DELETE` + `INSERT`，不是 `UPDATE`。**FTS5 虚拟表不支持 UPDATE**，而漏掉删的那一半会留下一条正文已改、索引仍是旧文的行 |

`test_the_index_follows_an_edit` 钉的就是这个：编辑后**旧词搜不到、新词搜得到**。

---

## 四、⭐ 检索**只过滤，不重排**

`bm25()` 可用，但**不用**。

列表的顺序是 `updated_at DESC`，这是一个**承诺**（笔记库的价值是「我最近写了什么」，
不是「哪条最匹配」）。如果打了字就换成相关度排序，**同一批数据会因输入长短呈现两种顺序** ——
这是那种「说不清哪里怪」的不一致。

→ 搜索是**过滤器**：`WHERE` 加上，`ORDER BY updated_at DESC` 不动。

---

## 五、虚拟表与约束台账：一个必须处理的意外

`tests/unit/test_storage.py` 的 `_table_ddl()` 按 `kind == "table"` 过滤，
而 **FTS5 虚拟表在 `sqlite_master` 里就是 `type='table'`** ——
所以 `notes_fts` 会要求一条台账条目。

**FTS5 表不能有 CHECK 约束**（它不是 SQLite 的普通表，约束语法由 fts5 自己解析），
所以那条条目的 `constraints` 只能是 `{}`。

`{}` 本身是个洞：**任何表都能用 `{}` 免掉台账检查**。

→ 加一条测试：**`constraints` 为空的台账条目，只允许是虚拟表**。
把洞变成护栏，而不是靠自觉。

## 六、验收

| # | 项 |
|---|---|
| 1 | ≥3 字的中文查询命中（正文与标题都搜） |
| 2 | ⭐ **2 字查询也命中**（`LIKE` 兜底），且 3 字与 2 字**结果集一致** |
| 3 | ⭐ 编辑后**旧词搜不到、新词搜得到** |
| 4 | 删除后搜不到 |
| 5 | 索引行数与 `notes` 行数一致 |
| 6 | ⭐ 检索**不改变排序**（`updated_at DESC` 恒定） |
| 7 | `LIKE` 兜底路径**不会**被 `%` / `_` 通配符放大成「全库命中」 |
| 8 | `constraints: {}` 的台账条目只允许虚拟表 |
| 9 | 门禁 10/10 + 退出码 0 |
