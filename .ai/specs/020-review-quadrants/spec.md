# Spec 020 · J3 复盘机制：四象限判定与结果分硬门禁（切片 1）

- **状态**：Active
- **目标阶段**：决策层（红线 5 / 红线 10 / 红线 2 / 红线 6）
- **依赖**：J1 决策登记（`decisions`，append-only，id = 服务端毫秒时间戳）
- **依据**：
  - **ADR-0014**（`decisions` / `reviews` / `decision_review_state` **三表分离**）
  - `AlphaCouncil-项目总纲.md` §P0-3（**四象限**与**结果分到期前必须留空**的硬门禁）
  - ADR-0014 第 3 条：`reviews.outcome` **允许 `failed` 为一等值**
  - 红线 2（只做过程优化）· 4（结果之前记录）· 5（过程分与结果分独立）· 6（未成熟留空）· 10（面对不舒服的数据）

---

## 一、三条原始规则（先读原文，不凭印象）

### 1.1 四象限（`项目总纲` P0-3）

| 象限 | 判语 |
|---|---|
| 好决策 + 好结果 | **应重复** |
| 好决策 + 坏结果 | **可接受** |
| **坏决策 + 好结果** | **最危险** |
| 坏决策 + 坏结果 | **必须改** |

### 1.2 硬门禁

> **结果分在到期前必须留空**（不许提前打分，否则就是用结果污染决策评价）。

### 1.3 特别规则（红线 10 的落地）

> 落在"坏决策 + 好结果"时 —— **不显示盈利数字**，只显示警示文案。

---

## 二、三个设计决定，都是上面三条的直接后果

### 2.1 `outcome` 是**分类**，不是数字 —— 所以红线 10 由**数据模型**保证

如果 `reviews` 存的是收益率（`-8.2%` / `+13.5%`），那么"不显示盈利数字"
就变成一条**渲染时的隐藏规则** —— 而**已经存在的数字会泄漏**：日志里、导出里、
将来任何一个新增的 API 字段里。

所以 `outcome` 是一个**枚举**：`good` / `bad` / `failed`。

> **这不是把功能做少，是把红线放在不会被绕过的地方。**
> 「坏决策+好结果」时没有数字可显示，因为**数据里根本没有数字**。

`failed` 是一等值（ADR-0014 第 3 条），它存在的意义是**禁止"失败但…"这类措辞**：
亏损叫 `failed`，不叫"有波动的收获"。

⚠️ **我第一次读这条 ADR 时因为控制台乱码读成了相反的意思**（"不把 `failed`
作为一个值"），差点把枚举设计反了。**已回原文核对。**

### 2.2 「是否已复盘」是**状态**，不是派生量（ADR-0014 的硬规则）

| 表 | 性质 | 本次新增 |
|---|---|---|
| `decisions` | append-only，用户当时写的原始记录，**永不修改** | 已有 |
| `reviews` | **append-only**，一条决策可复盘多次 | **本次新增** |
| `decision_review_state` | **唯一真源**：`due_at` 与 `reviewed_at` 只在这里 | **本次新增** |

> **⚠️ 绝不从 `reviews` 是否存在推断"是否已复盘"。**
> 派生量会被"删掉一行 review"悄悄改变 —— 而"我复盘过"这个事实不该被任何人悄悄改掉。

**而 `review_count` 可以从 `reviews` 数出来** —— 因为 `reviews` 是 append-only 的。
**这两个结论看起来矛盾，其实不是**：一个是从**可变**存储推断状态（不可靠），
一个是从**不可变**存储数出个数（可靠）。写进注释里，否则下一个人会以为是笔误。

### 2.3 硬门禁**下沉到数据库**（第零条 0.2：能移就必须移）

「结果分到期前必须留空」本来可以只在领域层判断。但 ISO-8601 时间戳是**可字典序比较**的
字符串，所以 `reviews` 行里带一份 `due_at_snapshot`（写入时从状态表复制），
就能让**绕过领域层的调用**也被挡住：

```sql
CONSTRAINT reviews_not_scored_early_check
    CHECK (outcome IS NULL OR reviewed_at >= due_at_snapshot)
```

**"能移就必须移"在这里有一个漂亮的实例**：这条纪律本来只能靠自觉，
现在它是一行 `CHECK`，而**没有一个测试需要信任任何人的自觉**。

## 三、数据契约（迁移 0006）

### 3.1 `decision_review_state`（每条决策一行，**可变**）

| 字段 | 说明 |
|---|---|
| `decision_id` | PK，FK `decisions(id)` ON DELETE CASCADE |
| `due_at` | 复盘到期时刻（**到期前结果分必须留空**的门） |
| `reviewed_at` | **可空**，首次复盘时刻。**绝不预填 0**（红线 6） |
| `created_at` / `updated_at` | 服务端时刻 |

### 3.2 `reviews`（append-only，一条决策可多条）

| 字段 | 说明 |
|---|---|
| `id` | `review_<毫秒>`，服务端生成 |
| `decision_id` | FK |
| `process_score` | **过程分** 1..5，**用户自己写**（红线 15） |
| `outcome` | `good` / `bad` / `failed`，**分类，不是数字** |
| `reviewed_at` | 复盘时刻 |
| `due_at_snapshot` | 写入时从状态表复制的到期时刻 —— **门禁的锚** |
| `note` | 可选，≤1000 字。**"失败但…"式的措辞由人负责，字段本身不判断** |
| `created_at` | 服务端时刻 |

条件必填 + 硬门禁：

```sql
CHECK (process_score BETWEEN 1 AND 5)
CHECK (outcome IS NULL OR outcome IN ('good','bad','failed'))
CHECK (reviewed_at >= due_at_snapshot)          -- ⭐ 硬门禁
CHECK (outcome IS NULL OR reviewed_at IS NOT NULL)
```

append-only 两触发器（`reviews` 进入 `APPEND_ONLY_TABLES`）。

### 3.3 为什么不加"盈利数字"列

**§2.1 已经是答案。** 在 SQL 注释里也写一遍，因为下一个人会觉得"少了一列"是 bug。

## 四、领域层：四象限判定

```
好决策 = process_score >= 4        （1..5 制，中位 3 归入"坏"）
坏决策 = process_score <= 3

good   + good/failed → 可接受之外的好结果 → REPEAT（应重复）
good   + bad/failed  → ACCEPTABLE（可接受）
bad    + good        → DANGEROUS（最危险）⚠️ 不显示盈利数字
bad    + bad/failed  → FIX（必须改）
```

**3 分算"坏"的理由**：3 是"过程一般"。把它算作"好"会让四象限失去筛选作用 ——
而"过程一般"恰恰是最该被改的那一类。**判据写死并注释**，因为它是一个判断，不是事实。

> **⚠️ 这套评分的软肋**：过程分是**用户自己打的**。
> 抗后见之明的机制不是"评分客观"，而是
> **① `decisions` 里的原始文字永不修改**（所以过程分是锚在无法事后重建的东西上）
> **② 结果分到期前必须留空**（所以打分时看不到结果）。
> 换句话说：**被评的不是回忆，是那段还在的原话。**

## 五、验收标准

- [ ] **AC-1（Schema）** 0006 建两表 + 索引 + 触发器；CHECK 完整；
      `manifest.json` / `constraints.json` / `APPEND_ONLY_TABLES` 三处同步；down 可执行
- [ ] **AC-2（三表分离）** `reviewed_at` 只在 `decision_review_state`；有测试证明
      **删掉一行 `reviews` 不会让"已复盘"变回未复盘**
- [ ] **AC-3（硬门禁在数据库）** 绕过领域层直接 INSERT，`reviewed_at < due_at_snapshot`
      → **被 CHECK 拒绝**（有行为测试，不只是领域层测试）
- [ ] **AC-4（红线 6）** `reviewed_at` 可空且**永不为 0**；有测试
- [ ] **AC-5（四象限）** 六种组合逐一断言，含 `failed` 归入坏结果
- [ ] **AC-6（红线 10）** `DANGEROUS` 判定后**不产生任何数字**；`reviews` 无金额列（有测试枚举列名）
- [ ] **AC-7（红线 15）** `process_score` 只能来自用户输入；**系统没有任何默认值**（有测试）
- [ ] **AC-8（append-only）** `reviews` 的 UPDATE / DELETE 被触发器拒绝
- [ ] **AC-9（同事务）** 写 review 与更新 state 同事务（照 0006 的 `require_open_transaction`）
- [ ] **AC-10（门禁）** `dev.py check` 10 道全过 + 退出码 0
- [ ] **AC-11（诚实）** `dev.py eval`：红线 5 / 10 的状态按实际结果更新
- [ ] **AC-12（变异）** 逐个变异并确认真的生效

## 六、明确不做

| 不做 | 为什么 |
|---|---|
| API 与复盘界面 | 切片 2。机制先于表面（同 K3 的 018 → 019） |
| 金额 / 收益率列 | **§2.1**：红线 10 由数据模型保证，不是渲染时隐藏 |
| 让系统给过程分打分 | 红线 15：**判断必须由用户下**。系统只有 `PENDING`，没有"AI 估计的过程分" |
| "失败但…"的措辞检查 | 需要 NLP。**字段不判断，人负责**；ADR-0014 要求的是 `failed` 是一等值 |
| 到期日的自动算法 | 「买满 90 天该做第一次复盘」是 `项目总纲` 的建议，**判据未定义**。本次由调用方给定 |
| 复盘次数的"够不够" | 那会变成打卡。**没有第 N 次该复盘这种规则** |
