# 回归 0008 · 假设主键叫 `id`

**发现**：2026-09-28，spec 030（J5 教训转卡）
**性质**：一个假设在四层里各犯一次
**状态**：已修 · 根因已定位 · 防复发措施已落地

---

## 一、现象

一个回合里，同一个假设出现了**四次**，在四个互不相干的地方：

| # | 位置 | 表现 |
|---|---|---|
| 1 | `storage/repositories/lesson.py` 的 `_new_id` 碰撞探测 | `sqlite3.OperationalError: no such column: id` |
| 2 | 迁移 `0010` 的三个外键 | `sqlite3.OperationalError: foreign key mismatch` |
| 3 | `storage/repositories/notes.py` 的链接解析 | **一个合法的链接**在**校验路径**里抛 `no such column: id` |
| 4 | `_LINK_TARGET_COLUMN`（第 3 条的修法本身） | 如果不修，第 3 条会以另一种形式再来一次 |

四次都是**同一个假设**：新增的表和已有的表一样，主键列叫 `id`。

## 二、根因

⭐ **四张表同名不是性质，是巧合。**

本项目实际的主键列是：

```
decisions.id   cards.id   notes.id   reviews.id
lessons.lesson_id          note_schedule.note_id
instruments 的键是 market || '|' || code（复合，且没有单列 id）
```

写下「新增一张 lessons 表」这个动作里，**没有任何东西提醒**新表该用哪个列名。
而项目里已有的四张表恰好都用 `id`，所以那个假设看起来是安全的。

## 三、为什么第 3 条躲过了两个 spec

`notes.py` 的 `LinkKind.LESSON` 在 **spec 026** 就进了枚举**和**解析映射表，
指向一张**当时还不存在**的表。解析函数先查 `sqlite_master`，表不在就返回 `False`。

⭐ **所以那条错误的列名躲在一个让它不可达的守卫后面。**

**让 bug 不可达的守卫，和让 bug 不存在的守卫，长得一模一样。** 而当时那条注释
写的是「the lookup returns False until that table exists」—— 它描述的是**症状**
（会返回 False），不是**事实**（这条路径从未被执行过）。

spec 030 建了表，守卫放行了，bug 出现。**建表这个动作本身是对的**，
而正是它让一个潜伏的假设变成了一个响亮的失败 —— 这是一次**好的**失败。

## 四、防复发

1. **`_LINK_TARGET_COLUMN`：列名是数据，不是查询里的常量。**
   `instrument` 走自己的分支（复合键），`lesson` 用 `lesson_id`，
   其余用 `id`。加一张表是一次**数据**改动。
2. **`notes.py` 的守卫注释改成它真正在防什么**：一个 `LinkKind` 提前于它的表
   被声明。它现在是一个**拒绝**，不是一次通过。
3. **`test_notes.py` 两条测试**：指向**不存在**的教训被拒绝；指向**存在**的
   教训被接受。⭐ 后者才是能抓住「表建了但没接上解析」的那一条 ——
   前者在那种情况下会继续绿。

## 五、留给下一个人的一句

⭐ **新增一张表时，先查它旁边那几张表的主键列叫什么 —— 并且假设它们不一样。**

如果四张表真的都叫 `id`，这个假设会一直成立，而**总有一天**会有第五张表不叫。

## 六、同一个根因的第二个成员：**测试的 fixture 也可以描述产品到不了的状态**

`f71fd3b` 的 E2E fixture 把一条**已复盘**的决策放进了**到期**队列，
于是 spec 030 的 lesson composer 在真实应用里**不可达**，而套件全绿。

⭐ **两个缺陷的形状完全一样：把「本该由代码保证的关系」当成了约定。**

| | 我写的 | 后果 |
|---|---|---|
| 0008 | 四张表都以为主键叫 `id` | 四层各犯一次，其中一条躲在「表还不存在」的守卫后面 |
| 0009 | fixture 假设到期队列里可以有已复盘的条目 | **一个功能不可达，而测试全绿** |

而两者的修法也是同一个：**让那个关系由代码或查询本身保证，而不是由调用点记住。**

* 0008：列名变成 `_LINK_TARGET_COLUMN` 里的**数据**。
* 0009：新增 `/decision-reviews/recent`，**已复盘的决策从「到期」这个概念里搬出去了**，
  不再依赖任何调用点记得区分。

⭐ **判断一个新测试是否可信的问题不是「它断言了吗」，而是「它描述的状态存在吗」。**
第二个问题更难问，也更容易漏 —— 而漏掉的代价是**一个绿色结果说谎**。
