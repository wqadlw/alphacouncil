## 现象

`docs/ARCHITECTURE.md`（我 2026-09-28 重写，commit `ef38fab`）顶部写着：

> "the constitution removed every one of those technologies on 2026-09-26
> (v1.0 → v2.0, item 2 …)"

并把 **LangGraph** 列进 `Deliberate non-goals`：

> "LangGraph / agent graph orchestration | The agent pipeline is a *development*
> discipline (`.ai/`), not a runtime component."

**两句话都不对。**

## 根因

### 直接原因：把一份清单当成全集

宪法 v1.0 → v2.0 变更说明第 2 条原文：

> 技术栈含 LlamaIndex / Qdrant / LightRAG / AKShare / Next.js → **全部移除**

这是**检索栈**（ADR-0002 / 0003 / 0004 / 0006）。**LangGraph 不在这张清单里。**

而我要修的那份旧 `ARCHITECTURE.md` 里，LangGraph 与 Qdrant、LightRAG、RRF
**并排出现**。我读到了"这份文档整段是 v1 遗留"，于是把"文档提到的技术"整包
判成"宪法移除的技术"—— **清单里没有的东西，不因为出现在同一页就属于同一批。**

### 真正的机制原因：编码坏掉的一行 grep

我第一次 grep `decisions.md` 找 LangGraph 时，shell 把中文输出压成了乱码：


**这一行里恰好有"撤回"两个字。** 我据此写下"已从 LangGraph 撤回"。
而它逐字是：

> ⚠️ **理由修订**：原文写的是"投研流程需要条件分支 / 回路 / 人工中断"。
> **现行定位已变** —— agent 不再是"研究流程"，而是**只做抽取与核算的工人**（宪法第一条红线 15）。
> **选型结论不变（仍用 LangGraph）**，但用途变为：**规格 → 实现 → 审查 → 验证 → 归档 的开发流水线**，以及**受限抽取流水线**。

**"撤回"是我读错的，"结论不变"才是原文。** 我在一个编码损坏的输出上
做了一次关于项目方向的判断，然后把判断写进了给别人看的文档。

### 结构性原因：同一份决定存在两个存储

`docs/adr/0001-agent-orchestration-langgraph.md` —— **Status: Accepted**，
描述一套**投研工作流**，并规定 `graph/` 需 ≥90% 覆盖率、每个节点发 Langfuse span。
而 `.ai/memory/decisions.md` 的 ADR-0001 早已重新定位。

**两个存储，一个说"接受并要求实现 graph/"，一个说"接受但改了用途"。**
搜遍全仓库，**没有任何文件引用 `docs/adr/`** —— 它对所有机制不可见，却仍在误导人。

## 真相（逐行核对 2026-09-28）

| 宪法第三条 | 仓库实际 | 状态 |
|---|---|---|
| LangGraph ≥ 0.2 | 无依赖、无 `graph/` 包、零 import | **已采纳 · 未实现** |
| Langfuse（可替换/降级） | `core/trace.py` 手搓其数据模型 | **已采纳 · 以"降级"实现** |
| fastmcp | 无依赖、无 MCP server | **已采纳 · 未实现** |
| **py-fsrs** | 实际包名 `fsrs`；`py-fsrs` **PyPI 上不存在** | **名字是错的** |
| SQLite + SQLAlchemy 2 + Alembic | 裸 `sqlite3` + 自研迁移器；`sqlalchemy`/`aiosqlite` 零 import | **实现已超越原选型** |

**所以真相是第三种状态：已采纳、写在宪法里、从未落地。**
它既不是"已移除"，也不是"已实现"—— 而这两个误判我一天之内都犯了一个方向。

## 修复

1. **`docs/ARCHITECTURE.md`** —— 顶部保留**两次**更正说明（含我的错和为什么错），
   把 LangGraph 从 `Deliberate non-goals` **移出**，新增
   「[Adopted but not implemented]」一节逐行写清状态。
2. **删除 `docs/adr/0001-agent-orchestration-langgraph.md`**，原地留一个 README
   指向 `.ai/memory/decisions.md`。**删掉而不是改对** —— 两个决策存储不是要维护的东西，
   是不该存在的东西（宪法 0.2：能移就必须移）。
3. **宪法第三条加 §3.0 状态标注**（**纯追加，不删表**），五行差异逐条标出，
   注明「**待人工确认**」，与 v3.0 的处理方式一致。
4. **新增 ADR-0027**（本文件即其依据之一），把 agent 三件套的**启用条件**写死：
   ① 出现必须有运行期 agent 的产品能力 **且** ② `make eval` 存在。

## 回归"测试"

这是**文档缺陷**，且它的性质是"断言与真源不符"——与 `regressions/README.md` 规则 5
正好相反（那条说"测试抓不住的缺陷应进 `.ai/checks/static/`"）。

但我**没有加静态检查**，理由要写清楚：

- 宪法 2.2 三问的第一问是「**具体故障**」。我能举出的具体故障是
  "我读错了编码坏掉的一行" —— **静态检查抓不住读错**。
  能抓的是"两个 ADR 文件状态不一致"，而**我已经把第二个存储删了**，
  故障的可能性随之一并消失。
- **删掉重复存储，比加一条规则去巡逻它更符合第零条 0.2。**

所以这一条的"回归"是**结构性**的：`docs/adr/` 现在只有一个 README，
而它本身就在说明"别在这里写决定"。**没有第二个地方可以写错。**

> ⚠️ **诚实的边界**：结构修复防不住**下一个人重新创建 `docs/adr/`**。
> 真要挡住，需要一条检查规则。**没做**，因为按三问它答不出"具体故障"——
> 这是权衡的结果，不是遗漏。若日后真的再现，就补规则。

## 是否可被测试固化？

## 遗留

## 教训（这一条比修复本身重要）

`agent-guide.md` §三 第 8 条写「**未运行却暗示已通过** —— 这句话有证据吗？」

我把它扩展成一条新的自查：

> **在编码损坏的输出上，不要做关于方向的判断。**
> 如果一条 grep 的结果里出现了乱码，那一行就是**不可信的**，
> 正确反应是**换一种方式重读那个文件**（用文件读取工具读原文），
> 而不是从残骸里推断出项目的历史。

**我的错误全部发生在这一个动作上**：从乱码里读出"撤回"，然后把一个关于
项目技术方向的结论写进了给别人看的架构文档。**慢一步重读，成本是 5 秒。**
