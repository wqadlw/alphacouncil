# 0018 · 表单里两个「只是选一下」的按钮，点一下就写下了一条不可改的记录

- **发现日期**：2026-10-01
- **严重级别**：P0（一击即写入不可改事件，且**没有任何测试会红**）
- **状态**：已修复 + 已加门禁（`V-19`，变异 M1/M2 均已确认）

## 现象

spec 047 给关注池加「歧义代码选择器」。两个市场按钮的职责写得很清楚：

> **Choosing does not write.** It arms the submit button, because the write is the
> reader's second deliberate press — a control that records something permanent on its
> first click is not a control you can put a 「选错了」 next to.

探针实测（1440×900，真后端，写请求被拦截以免写入主人的库）：

```
填 000001、填理由、按「加入关注池」   -> 选择器出现，0 个 POST   ✓
点「上交所」                       -> 1 个 POST              ✗
```

点一下就把一条**只增不改**的关注记录写了。

**然后探针报出来的症状是「第二个按钮点了没反应」** —— 表单被清空、按钮禁用、
第二次点击 30 秒超时。距离原因三十秒。

## 根因

三个事实叠在一起：

1. **`<button>` 没有 `type` 属性时，在 `<form>` 里默认是 `type="submit"`。**
   这是 HTML 规范，不是 Tailwind 的默认，也不是 React 的。
2. `Button` 继承 `ButtonHTMLAttributes` 后 `{...props}` 直接透传，
   **所以每个 `<Button>` 都是 submit 按钮，除非它自己写了 `type="submit"`。**
3. 点市场按钮 → 表单提交 → `handleSubmit` 重跑 → 因为 `picked` 还是 `null`
   又解析一次 → 又得到 `ambiguous` → 表单被清空禁用。

## ⭐ 为什么没有任何测试会红

因为**缺陷不在「缺了什么」，而在「多了什么」**：按钮拼写完全正确、有名字、有
onClick、渲染正常 —— 它只是做了别的事。测「按钮出现了」「点了有反应」的测试都会通过。

而且这个 bug 在**功能代码里是新的**，在门禁全绿的状态下写出来的。
⚠️ **它不是被任何检查抓住的，是被一个手写的探针抓住的** —— 探针量了 POST 的个数。

## 修复（两条，缺一不可）

1. **`Button` 默认 `type = 'button'`**（shadcn / Radix 的做法）。
   ⚠️ **动手前实测**：四个 `<form>` 全都已经显式写了 `type="submit"`
   （`CardSection` ×2 / `DecisionForm` / `InstrumentPage` / `PoolPage`），
   **所以这个默认值不破坏任何东西** —— 这条实测是让改动安全的前提，不是事后说明。
2. **`V-19` 守「每个 `<form>` 必须显式声明 submit」** ——
   否则改默认值的那一天，会有一个表单静默不再提交：**按钮在、名字对、点下去什么也没发生。**

## 回归测试

- `frontend/src/styleguide.test.ts` · `V-19`（两条）
  - `Button defaults type to "button"` —— 断言在组件的解构行上，因为**本仓没有
    jsdom 也没有 testing-library**（该文件开头就记着这件事），所以这是**源码事实**
  - `every <form> declares its submit button`
- `frontend/e2e/pool-ambiguity.spec.ts` · `A2` —— 「点哪个市场写进去的就是哪个；
  **选本身不写**」

## 变异检查（⚠️ 必填）

| 改坏哪里 | 哪个测试变红 | 结果 |
|---|---|---|
| M1 `Button` 去掉 `type = 'button'` | `V-19 · Button defaults type…` | ✅ **已确认变红** |
| **M2 给市场按钮显式加 `type="submit"`，而组件修复保留** | **`A2`（`V-19` 的组件那半条如实地绿了）** | ✅ **已确认变红** |
| M3 `handleSubmit` 忽略 `picked` | `A1` / `A2` | ✅ **已确认变红** |

⭐ **M2 是这一条里最重要的一行。** 只做 M1 的话，那只证明了门禁记得我改过的那一行。
M2 **在保留修复的前提下重建了原始缺陷**：组件默认值仍然是 `button`，
而选择器按钮仍然在提交 —— 于是**任何只看 `Button` 默认值的检查都会通过**，
是 e2e 抓住了它。

⇒ **撤销修复只能证明门禁记得修复；重建缺陷的形状才证明门禁理解形状。**
（同一条推理也否掉了 `V-18` 的第一版变异，见 `0015`。）

## 是否可被测试固化？

✅ 可以，而且必须分两层：

- **组件层**（`V-19`）守住「默认值安全」
- **页面层**（e2e `A2`）守住「点了不写」—— **这一层才是缺陷本身**

⚠️ 只有组件层的话，M2 会漏。

## 遗留

⚠️ **`Button` 的默认值改成 `button` 之后，任何新增表单都必须显式写 `type="submit"`** ——
这是 `V-19` 第二条存在的理由，但它是**新增代码要遵守的约定**，不是自动保证。
⚠️ 同类陷阱还有：`<a>` 无 `href` 不可聚焦、`<label>` 包住多个控件 ——
本仓目前没有第二例，**记下来是为了下次遇到时知道这条门禁的形状可以照抄**。
