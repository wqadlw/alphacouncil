# 0023 · 一条门禁把自己的扫描器误报成代码缺陷

**日期** 2026-10-02 · **来源** spec 051（D4 财务数据接线） · **类型** 门禁的自身缺陷（非产品缺陷）

## 发生了什么

给前端增加 `MetricState` 的新值时，我把说明写在了 **union 体内部**（值之间的 `//` 注释块）。
`S-16 no-enum-drift`（两个 spec 前建的禁）报：

```
error: CHECK_ENUM_DRIFT: `CriterionVerdict` = [... 'not_announced'] has no matching union
```

⚠️ **union 是对的，扫描器是错的。**

## 根因

`S-16` 的提取模式在这三个地方收口：`;`、「一个后面不是 `|` 的换行」、文件尾。一行 `//`
注释满足中间那个条件，所以**注释之后的值全部不可见**。

## 为什么这条记录值得写

⭐ ⭐ **一条门禁的第二种失败方式，总是一个还没人写过的形状。** 第一个是多行 union
（`F-202`），这个是「带注释的 union」。

⚠️ **而这次的失败方式比第一次更难发现**：第一次是「误报有一个 union 没有镜像」，这一次是
「说镜像不存在」—— 两种结论都说「代码有问题」，而问题在扫描器。

## 怎么修的

提取前先**整行注释剥离**（保留字符串字面量），并加一条单测。

⭐ **易于引入的是「删掉从 `//` 到行尾」的简单版** —— 它会把字符串里的 `//` 当注释，把一个合法文件变成
「因为被截断而干净」的。⭐ **两者的失败方式相同、方向相反，而只有一个是真的** —— 所以守卫必须
同时证明两件事：**合法文件不被误伤，非法注释确实被忽略。**

## 常记下来的规定

1. → 写字符串字面量的代码，先确认每行标点可以落在哪里。
2. → **规则报「不存在」时先验证扫描器**，再验证代码。
3. → ⭐ 门禁的第二种失败形状出现时，**教它那个形状，而不是绕开不写那个形状** —— 否则下一个人
   会撞上同一堵墙，而墙的名字叫「这个写法不行」。

## 与本轮另外两条的关系

`F-220`（结论已经在文件里而我还是产出了它）与 `F-222`（拿「像那件事的东西」当检查）是同一次
工作的另外两个形状：前者在**读**的环节出错，后者在**检查**的环节出错。三条合起来指向同一句：
**一个看起来像结论的东西，不等于结论。**
