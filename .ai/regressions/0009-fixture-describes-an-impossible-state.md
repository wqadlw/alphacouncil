# 回归 0009 · fixture 描述了产品到不了的状态

**发现**：2026-09-29，spec 030（J5 教训转卡）—— ⭐ **不是被测试抓到的，是被「把项目拉
起来看效果」抓到的**
**状态**：已修 · 根因已定位 · 端点与 fixture 都已改

---

## 一、现象

写完一次决策复盘之后：

```
GET /api/v1/decision-reviews/due   ->  []
```

而复盘页**唯一**的列表端点就是它。于是：

| 时刻 | 决策在哪 | lesson composer |
|---|---|---|
| 写复盘前 | 在到期队列 | **不显示**（还没有复盘 —— 这是对的，服务端是 409） |
| 写复盘后 | **离开**队列 | **永远不出现** |

**没有第二条路。** spec 030 交付的主要功能在真实应用里**不可达**。

## 二、为什么 E2E 全绿

`due_reviews` 按 `reviewed_at IS NULL` 过滤 —— 那是 **regression 0007** 的修复，
存在的理由正是「一条打完分的决策要离开队列，否则今天页上的计数会在复盘前后都
说『1 条决策』，而且会永远这么说」。

而 fixture 把一条**已复盘**的决策放进了**到期**队列。

⭐ **那是服务端永远不可能返回的状态。** fixture 和测试互相印证，而两者都不和产品
印证 —— 于是 82 条 E2E 全绿，其中三条正在测试一个**用户永远看不到的表单**。

## 三、根因，与 0008 同形

两者都是**把「本该由代码保证的关系」当成了约定**：

| | 我写的 | 后果 |
|---|---|---|
| 0008 | 四张表都以为主键叫 `id` | 四层各犯一次 |
| 0009 | 调用点负责区分「到期」和「已复盘」 | 功能不可达，测试全绿 |

修法也是同一个：**让关系由代码保证，而不是由调用点记住。**
0008 把列名变成数据；0009 新增 `/decision-reviews/recent`，
**已复盘的决策从「到期」这个概念里搬了出去**。

## 四、防复发

1. **端点**：新增 `GET /api/v1/decision-reviews/recent`，已复盘的、最近的在前。
   ⭐ `is_due` 永远 `false` —— 一条决策可以既到期又已打分，那正是这个列表存在的理由，
   而这个字段决定页面走哪个分支，不是装饰。
2. **页面**：两个列表合并，到期的在前，按 id 去重；打分按钮按「是否已打分」控制，
   并**显示**那个分数。
3. ⭐ **fixture**：`/due` 返回**空**（真实情况），已复盘的那条搬到 `/recent`。
4. ⭐ **一条可达性测试**：断言 composer 只能通过已复盘这条路到达。fixture 里
   `/due` 故意是空的 —— 所以如果它将来又只能靠一个服务端不可能返回的队列到达，
   这条测试会**红**，而不是让功能悄悄消失。

## 五、留给下一个人的一句

⭐ **问一个新测试是否可信，不要问「它断言了吗」，要问「它描述的状态存在吗」。**

第二个问题更难问，也更容易漏 —— 而漏掉的代价是**一个绿色的结果在说谎**。

⭐ 而且这次是**「把项目跑起来看一眼」**抓到的，不是任何一条测试。
理由和本项目反复记录的一样：**只有渲染出来的东西才会自相矛盾。**
