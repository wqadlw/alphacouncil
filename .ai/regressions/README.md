> **每个缺陷 → 一个测试文件 + 一条变异检查记录。** 目标：**三年后还能跑**。
> 建立：2026-09-26 · 依据 `references/deep-dives/08-portfolio-performance.md`（`issues/Issue<N><描述>Test` + `.xml` fixture）· `10-akshare.md` 决定 3

## 一、为什么需要"回归记录"而不是只有"回归测试"

| 只有测试 | 加一条记录 |
|---|---|
| 三年后的人看到 `test_issue_1042` 不知道它为什么存在 | 记录写明**缺陷现象 + 根因 + 改坏哪里会变红** |
| 不知道测试是否还有效 | **变异检查**证明它真的会红 |
| 可能被"重构"时顺手删掉 | 记录是它的存在理由 |

**判据（宪法 8.3）**：
> **每个缺陷修复必须回答："如果我故意改坏，这个测试会不会红？"** 答案不确定 → **去做变异检查**。

## 二、目录结构

```
.ai/regressions/
├── README.md                    # 本文件（格式与规则）
├── index.md                     # 索引：缺陷编号 → 标题 → 状态
├── 0001-<描述>.md               # 每条缺陷一份记录
└── fixtures/
    └── 0001-<描述>.json         # 触发该缺陷的数据
```

**测试代码本身放在 `backend/tests/regressions/`**（能被 pytest 直接收集），
**本目录放的是"为什么有这个测试"**。

## 三、记录格式

```markdown
# 0001 · 决策日志接受客户端传入的时间戳

- **发现日期**：2026-XX-XX
- **严重级别**：P0（红线 4）
- **状态**：已修复

## 现象

POST /decisions 时客户端可以传 `id`，于是用户能把一条决策写成"三个月前"，
**破坏"结果之前记录"这一红线**。

## 根因

`DecisionCreate` schema 里包含了 `id` 字段（Pydantic 默认允许）。

## 修复

`backend/src/alphacouncil/api/decisions.py:42` —— 从 schema 中移除 `id`，
主键由服务端在插入时生成。

## 回归测试

`backend/tests/regressions/test_issue_0001.py::test_decision_log_rejects_client_supplied_id`

**期望值写死**：断言的是"返回 422"，不引用任何被测常量。

## 变异检查（⚠️ 必填）

| 改坏哪里 | 哪个测试变红 | 结果 |
|---|---|---|
| 把 `id` 字段加回 schema | `test_decision_log_rejects_client_supplied_id` | ✅ **已确认变红** |

## 是否可被测试固化？

✅ 可以（这是运行时行为）。

## 遗留

无。
```

## 四、硬性规则

| # | 规则 |
|---|---|
| 1 | **测试的期望值必须写死**（字面量），**禁止从被测代码导入常量**。需要引用时，在测试文件里**重新写一遍并注明"这里写死，不从被测代码读"**。 |
| 2 | ⭐ **变异检查必填** —— 没做就写"未做"，**不得省略这一节**。 |
| 3 | **每个缺陷一个测试文件**（不是"一个测试函数塞进大文件"）—— 便于独立运行与删除。 |
| 4 | **fixture 必须是数据，不是代码** —— 用 JSON / SQL 快照，不用构造代码。 |
| 5 | ⭐ **如果这个缺陷"测试抓不住"**（如"某段代码不该存在"），**它不该进本目录**，应该进 `.ai/checks/static/`。 |
| 6 | **缺陷编号只增不复用**，与 issue 号对齐（无 issue 时用序号）。 |
