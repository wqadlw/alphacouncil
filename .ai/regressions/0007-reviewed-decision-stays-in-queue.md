# 0007 · 复盘完的决策**永远留在队列里**

- **发现日期**：2026-09-28
- **严重级别**：P1（红线 10 —— 那一行在说谎）
- **状态**：已修复
- **发现方式**：**探测，不是读代码**

---

## 现象

今日页那一行说「到期要看的：N 条决策」。**记完复盘之后，N 不变。**

探测脚本打印了同一条决定在复盘前后的今日页载荷：

```
due before review : {'cards': ..., 'reviews': {'queue': 'reviews', 'count': 1}}
review recorded  : quadrant=repeat
due after review  : {'cards': ..., 'reviews': {'queue': 'reviews', 'count': 1}}
```

不只是当时不变——**永远不变**。做了的事会一直挂在「到期」里。

## 根因

**两个队列的离开机制不同，而只有卡片那套是自动的。**

| | 复盘后怎么离开队列 |
|---|---|
| 卡片（K3） | FSRS 把 `due_at` **往后推** → 不再匹配 `due_at <= as_of` |
| 决策（J3） | `due_at` **一次设定、永不改变** → 永远匹配 |

`due_reviews()` 原本只有 `WHERE due_at <= ?`，**没有"已完成"的过滤**。
卡片队列不需要那个过滤，所以这个不对称一直没被发现。

## 为什么这比"数字错了"更严重

1. `due` 的 count 从「**还欠多少**」退化成「**历史上一共到期过多少**」——
   而它在默认页上，红线 10 指名的就是那一行
2. ⭐ **做完之后那一行还在说有事**，于是读者学会跳过默认页上**唯一一行有时为真**的话
3. 这与今日页已经防住的**另一个方向**完全同构：「计数为零 → 整行不渲染」——
   **两个方向都会教读者忽略那一行**

## 修复

`backend/src/alphacouncil/storage/repositories/reviews.py::due_reviews`

```sql
WHERE due_at <= ? AND reviewed_at IS NULL
```

**⭐ 过滤的是「完成章」，不是「有没有 review 行」。**

只写了过程分（半份复盘）时 `reviewed_at` 仍是 NULL —— 因为**半份复盘是合法状态**，
未完成的事不能藏在读者已经写下的那一行后面（spec 020 §三）。

## ⚠️ 顺带暴露的**限制**（不是缺陷，是记录）

> **一条决策只能复盘一次。** `decision_review_state` 没有 reschedule，
> `due_at` 不会动，所以没有"再进一次队列"的路径。
>
> 要发明第二个间隔就是**发明策略**（spec 020 §六「买满 90 天」；
> spec 023「三天未处理」也是同样处理）。
>
> **想再看一次某条决策 = 记一条新决策**，或者把教训变成卡片走它自己的排程（J5）。
> 若将来要"第二次复盘"，需要**一个会移动的到期日**，并开一条 ADR。

## 遗留

- **没有复盘历史视图。** `reviews_for()` 已在仓储里但**无调用方** —— 复盘完就从界面消失了。
  这**不是缺陷**（队列的定义就是"还欠什么"），但**读者看不到自己过去写过什么**，
  而 `项目总纲` 强调"三年后你能不能说出当时的自己"。**已登记进 `status.md`。**
- 一条决策无法复盘第二次（见上）。

## ⭐ 这条记录本身的一条教训

**第一版回归测试"复现"了缺陷，而它其实什么都没插入。**

seed 用 `NOW.isoformat()` 写 `created_at`，而 schema 的 identity CHECK
要的是 `utc_millis()` 的 `...Z` 规范形式 → fixture 报错 → 队列为空 →
`assert 0 == 1` —— **看起来正是缺陷的症状**。

> **一个从未成功写入的 fixture，会精确地产生"队列是空的"这个症状。**
> 而"队列是空的"**正是**这个缺陷的表面现象。

如果当时没去看错误信息（只看到 `assert 0 == 1` 与预期一致的方向），
就会把一条**假**回归记录归档。今天第四次：**先确认测试真的跑到了要测的地方，
再相信它的失败。**
